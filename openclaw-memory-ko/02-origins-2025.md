# 2장. 기원: 메모리 모듈이 생기기 전

OpenClaw가 처음 해결하려던 문제는 거창한 지식 검색이 아니었다. 재시작 뒤에도 같은 대화를 이어 가고, 새 대화를 시작할 때 필요한 사실과 선호를 되살리며, 그 내용을 사용자가 직접 살펴보고 고칠 수 있는 곳에 남기는 일이 먼저였다. 그래서 의미 메모리의 출발점은 데이터베이스가 아니라 사람이 읽고 편집할 수 있는 워크스페이스 파일이었다.

이 출발점을 이해하려면 서로 닮아 보이는 세 기능을 먼저 구분해야 한다. **세션 연속성**은 이미 진행하던 대화를 재개하는 기능이다. **의미 메모리**는 여러 세션에 걸쳐 다시 쓸 사실·선호·결정을 별도 원본에 남기는 기능이다. **대화 기록 회상**은 의미 메모리로 선별되지 않은 내용까지 과거 대화 로그에서 찾아오는 기능이다. 세 기능은 같은 문제를 조금씩 확장한 단계가 아니라, 서로 다른 원본을 쓰고 만들어지고 읽히고 지워지는 시점도 다른 보완 관계다.

2025년 말에는 일일 기록과 장기 파일이라는 두 시간축이 생겼다. 이 단순한 구조는 투명성과 이동성을 얻었지만, 파일이 쌓일수록 무엇을 찾아야 하는지, 어떤 내용을 오래 남겨야 하는지, 개인 정보를 어느 대화에서 불러와도 되는지라는 다음 문제가 드러났다. 장 제목은 2025년의 기원을 강조하지만, 이 장은 그 압력이 수동 대화 기록 회상으로 이어진 2026-01-07까지 추적한다.

## 의미 메모리보다 먼저 세션 연속성이 생기다 — 2025-11-24

가장 먼저 필요했던 것은 이미 시작한 대화를 다시 이어 가는 능력이었다. 초기 웹 공급자는 발신자별 또는 전역으로 Claude 세션 ID와 마지막 활동 시각을 저장했다. 이 정보로 기존 세션 재개, 새 세션 시작, `/new`, 일정 시간 사용하지 않은 세션의 만료를 처리했다. 근거가 되는 [`9b4dceecfe69`](https://github.com/openclaw/openclaw/commit/9b4dceecfe69bb224a369a33a1c064003040aedd)는 `v0.1.0`에 처음 포함되었다.

> **변화의 동기.** 실제 압력은 재시작과 유휴 만료 뒤에도 대화의 연속성을 지키는 일이었다. 동기 출처는 초기 웹 공급자 구현의 커밋과 코드 구조이며, 증거 강도는 **코드에서 추론**이다. 대화 본문까지 보관하기보다 발신자별·전역 ID와 시각만 저장하는 최소 형태를 골라 세션의 시작·재개·만료부터 해결했다.

이 선택은 “어느 대화를 이어 갈 것인가”에는 답했지만 “그 대화에서 무엇을 오래 기억할 것인가”에는 답하지 않았다. 대화 본문이나 선별된 사실을 별도 기억으로 저장하지 않았기 때문이다. 오늘날 세션 보관소로 이어지는 계보에는 속하지만, 워크스페이스 의미 메모리의 시작으로 보아서는 안 된다.

## 사용자 전용 파일이 시작 맥락에 들어오다 — 2025-11-27

세션 ID만으로는 사용자의 사실과 선호를 새 세션에 되살릴 수 없었다. 2025-11-27의 Claude/WhatsApp 설정 예시는 워크스페이스에 메모와 파일을 보관하고, 세션을 시작할 때 사용자별 파일 `peter.md`와 소문자 `memory.md`를 읽도록 했다. 이 변경은 [`c43cdc5ac3d3`](https://github.com/openclaw/openclaw/commit/c43cdc5ac3d3058238b1ea5579d4700e5345c3b2)에 있다. 이 책에서 확인한 출시 이력 가운데 가장 이른 메모리 파일명이며 `v1.2.0`에 처음 포함되었다.

> **변화의 동기.** 실제 목표는 세션 ID로는 복원할 수 없는 사용자 사실과 선호를 시작 맥락에 다시 넣는 일이었다. 동기 출처는 사용자별 Claude/WhatsApp 설정 예시라는 설계 자료이고, 증거 강도는 **코드에서 추론**이다. 별도 데이터베이스보다 사람이 읽는 파일을 시작할 때 불러오는 형태가 당시 구성 방식과 가장 잘 맞았다.

여기서 처음으로 사람이 읽는 파일이 모델의 시작 맥락으로 돌아왔다. 다만 저장소 전체가 따르는 공통 워크스페이스 규칙도, 날짜별 기록 관례도, 독립된 메모리 기능도 아니었다. 한 사용자에 맞춘 설정 예시를 일반 에이전트의 규칙으로 넓히는 일이 남았다.

## 워크스페이스가 에이전트의 내구성 있는 상태가 되다 — 2025-12-14

사용자 한 명의 설정 예시를 모든 에이전트가 따를 수 있는 공통 규칙으로 넓힐 필요가 있었다. 여기서 **내구성 있는 상태**란 프로세스나 세션이 끝나도 사라지지 않고 다음 실행에서 다시 읽을 수 있는 상태를 뜻한다. 일반 에이전트 워크스페이스를 초기화하고 메모, 임시 파일, “메모리”가 그곳에 속한다고 명시한 [`073285409b4c`](https://github.com/openclaw/openclaw/commit/073285409b4cd24eb7888832b917f423b20b6d10)는 `v2.0.0-beta1`에 처음 포함되었다. 이어 [`a5b3b8743a27`](https://github.com/openclaw/openclaw/commit/a5b3b8743a2782856172975cb8896ca4978290d2)은 복구와 이력 추적을 위해 워크스페이스를 비공개 Git 저장소에 백업하라고 권고했다.

> **변화의 동기.** 실제 압력은 한 사용자에게 묶인 예시를 모든 에이전트가 따르는 지속성 규칙으로 넓히고, 그 상태를 사용자가 백업할 수 있게 하는 일이었다. 동기 출처는 워크스페이스 초기화와 백업 지침을 잇달아 정리한 설계 커밋이며, 증거 강도는 **코드에서 추론**이다. 그래서 지속할 상태를 워크스페이스 한곳에 모으고 기존 Git 도구로 복구할 수 있는 형태를 택했다.

이로써 사용자가 직접 열어 보고 옮기고 백업할 수 있는 워크스페이스가 에이전트 상태의 공통 소유 지점이 되었다. 그러나 템플릿에는 아직 표준 메모리 파일명과 읽기 시점이 없었다. 저장 위치를 정한 다음에는 기록 관례를 정해야 했다.

## 일일 Markdown이 공통 메모리 관례가 되다 — 2025-12-19

일관된 파일명이 없으면 에이전트도 사람도 어디에 무엇을 쓰고 언제 다시 읽어야 하는지 알기 어려웠다. 중앙화된 워크스페이스 템플릿은 이 문제를 날짜별 Markdown 관례로 풀었다. 현재까지의 이력에서 찾은 가장 이른 표준 메모리 배치는 [`590f3d0e8f28`](https://github.com/openclaw/openclaw/commit/590f3d0e8f285d02e594cd718bfe9350ea5ee267)이며 `v2.0.0-beta2`에 처음 포함되었다.

- 일일 기록을 `memory/YYYY-MM-DD.md`에 만든다.
- 세션 시작 때 오늘과 어제의 기록을 읽는다.
- 사실, 선호, 결정처럼 나중에도 필요한 맥락을 기록한다.
- 명시적으로 요청받지 않는 한 비밀 정보를 피한다.

> **변화의 동기.** 실제 목표는 에이전트와 사람이 기록 위치와 읽기 시점을 매번 새로 정하지 않게 하는 일이었다. 동기 출처는 중앙 워크스페이스 템플릿을 만든 설계 정리이고, 증거 강도는 **코드에서 추론**이다. 날짜별 Markdown과 평범한 파일 도구를 골라 투명성·이동성을 지키면서도 최소한의 공통 관례를 만들었다.

이 선택으로 **에이전트는 평범한 파일 도구로 메모리를 쓰고, 사람은 전용 서비스 없이 그 결과를 검사하거나 편집할 수 있게 되었다.** 이때 Markdown은 검색 색인을 다시 만들어도 그대로 남는 원본, 즉 정본 역할을 했다. 반면 검색 데이터베이스, 전용 도구, 플러그인, 구조화된 데이터 형식은 없었다. 메모리는 아직 워크스페이스 지침에 적힌 행동 규약이었으므로 파일이 늘어난 뒤 원하는 사실을 찾는 문제는 그대로 남았다.

> **예시 — 합성 사례:** 2025-12-19의 관례만으로도 에이전트는 `memory/2025-12-19.md`에 “사용자는 배포 전에 변경 요약을 원한다” 같은 문장을 쓸 수 있었다. 하지만 이를 의미 검색으로 찾거나 자동 승격하는 제품 기능은 아직 없었다. 이 문장은 형식을 설명하는 가상 내용이며 실제 기록이 아니다.

## 일일 기록과 장기 기억이라는 두 시간축이 생기다 — 2025-12-20

날짜별 기록은 쓰기 쉽지만, 자주 다시 쓸 사실과 선호를 찾으려고 매번 연대기를 훑기에는 불편하다. 이를 보완하기 위해 일일 기록과 나란히 오래 유지할 사실·선호·결정을 담는 소문자 `memory.md`를 워크스페이스 최상위에 두었다. 근거인 [`cfd3efb6e767`](https://github.com/openclaw/openclaw/commit/cfd3efb6e767bcab8bbc2617913be2259e953bbb)도 `v2.0.0-beta2`에 처음 포함되었다.

> **변화의 동기.** 실제 압력은 최근 기록의 상세함을 잃지 않으면서 반복해서 쓸 사실을 짧게 읽는 일이었다. 동기 출처는 템플릿 지침의 설계 변경이며, 증거 강도는 **코드에서 추론**이다. 기존 일일 기록을 대체하지 않고 워크스페이스 최상위에 장기 파일을 나란히 두어 두 시간축을 분리했다.

두 파일의 역할은 다음처럼 갈렸다.

| 시간축    | 파일                   | 맡은 역할                                               |
| --------- | ---------------------- | ------------------------------------------------------- |
| 최근 기록 | `memory/YYYY-MM-DD.md` | 그날의 사건과 맥락을 비교적 자세히 남긴다.              |
| 장기 기억 | `memory.md`            | 여러 세션에서 반복해 쓸 사실·선호·결정을 짧게 유지한다. |

이 선택으로 **상세한 최근 연대기와 압축된 장기 기억**이라는 두 계층 모델을 얻었다. 1월의 대문자 `MEMORY.md`가 이 모델을 처음 만든 것은 아니다. 다만 무엇을 장기 계층으로 옮길지, 오래된 항목을 언제 고칠지, 커지는 기록을 어떻게 찾을지는 여전히 사람이나 모델의 규율에 달려 있었다.

## 오프라인 메모리 제안이 파일 관례의 한계를 정리하다 — 2025-12-23

두 파일 계층이 생기자 약점도 구체적으로 보였다. 날짜별 파일만으로는 관련 기록을 빠뜨리지 않고 찾기 어려웠다. 한 사람이나 프로젝트에 관한 사실이 여러 날짜에 흩어지면 한데 모아 답하기 어려웠고, 시간이 지나며 바뀐 선호나 서로 충돌하는 기록의 근거도 설명하기 어려웠다.

나중에 삭제되었지만 초기 의도를 가장 분명하게 밝힌 오프라인 메모리 제안은 이 문제를 검색과 정리의 문제로 풀었다. 제안은 [`760a83d256d6`](https://github.com/openclaw/openclaw/commit/760a83d256d63b55905681cadac60bebca684b73)에서 추가되어 `v2.0.0-beta3`에 처음 포함되었다.

> **변화의 동기.** 실제 압력과 목표는 관련 결과가 빠지는 검색, 서로 다른 시점의 기록 충돌, 불분명한 출처를 보완하되 사용자가 읽는 Markdown을 정본으로 지키는 일이었다. 동기 출처는 제안서 자체의 문제 진술이며, 증거 강도는 **명시적**이다. 그래서 곧바로 복잡한 SuCo를 채택하지 않고 재구축 가능한 SQLite FTS5와 선택적 임베딩부터 검증하는 점진적 형태를 골랐다.

- 네트워크 없이도 동작하고 결과의 출처를 설명할 수 있어야 한다.
- 사람이 읽는 Markdown은 계속 정본으로 남아야 한다.
- 파생 색인은 언제든 Markdown에서 다시 만들 수 있어야 한다.
- 처음에는 SQLite FTS5만으로도 유용해야 하고 임베딩과 그래프는 선택적으로 더해야 한다.
- 기억의 흐름을 보존(retain), 회상(recall), 성찰(reflect)로 나누어야 한다.

여기서 **FTS5**는 SQLite에 포함된 전체 텍스트 검색 기능이다. 단어가 나타난 위치와 빈도를 바탕으로 관련 문서를 찾는다. **임베딩**은 문장의 의미를 수치 벡터로 바꾸어 표현이 달라도 뜻이 가까운 문장을 찾게 한다. 둘 다 Markdown을 대신하는 기억이 아니라, 원본에서 관련 부분을 찾아내기 위한 파생 색인이다.

보존·회상·성찰도 추상적인 구호가 아니었다. 보존은 대화나 일일 기록에서 나중에 쓸 내용을 남기는 단계이고, 회상은 저장된 내용 가운데 현재 질문과 관련된 항목을 찾는 단계다. 성찰은 여러 기록을 비교해 사람·프로젝트별 요약이나 바뀐 선호처럼 더 안정된 설명을 만드는 단계다.

제안은 [Letta 메모리 블록](https://docs.letta.com/guides/core-concepts/memory/memory-blocks)과 [맥락 계층](https://docs.letta.com/guides/core-concepts/memory/context-hierarchy), [Hindsight](https://arxiv.org/abs/2512.12818), [SuCo](https://arxiv.org/abs/2411.14754)를 인용했다. 이 이름들은 완제품 후보의 목록이 아니라, 서로 다른 설계 아이디어와 도입 시점을 비교하기 위한 나침반이었다.

따라서 제안의 시작점은 재구축 가능한 SQLite 전체 텍스트 검색과 선택적인 단순 임베딩 검색이었다. 검색 대상 문서 집합이 충분히 커져 모든 벡터를 비교하는 방식이 느려질 때만 더 복잡한 근사 검색을 검토하자는 점진적 계획이었다. 이는 아키텍처 방향을 비교한 것이지 외부 구현을 가져오자는 제안이 아니었다.

이 제안은 투명한 원본과 재구축 가능한 검색이라는 방향을 기록했다. 그러나 이후 구현이 이 제안을 직접 따랐다는 근거는 없고, 실제 단계의 순서도 제안과 달랐다.

- FTS 우선 계획과 달리 벡터 검색이 먼저 출시되었다.
- 형식화된 개체·의견 저장소는 내장 코어가 되지 않았다.
- 이후 FTS 전용 검색, 로컬 임베딩, QMD가 네트워크 의존을 줄이는 경로를 보완했다.
- Dreaming은 의견의 신뢰도를 직접 관리하는 대신 실제 검색 사용량을 승격 신호로 삼았다.
- Memory Wiki는 주장·출처·모순과, 어떤 문서가 무엇을 가리키는지 보여 주는 역방향 링크를 다루는 별도의 선택 계층으로 등장했다.

## 공개 유지보수자 요청이 검색과 승격을 한 문제로 묶다 — 2026-01-02

파일을 잘 찾는 일과 중요한 내용을 오래 남기는 일은 서로 떨어진 문제가 아니었다. [Issue #102, “Better Memory System”](https://github.com/openclaw/openclaw/issues/102)은 벡터 기반 메모리 검색과 일일 기록을 장기 기억으로 **승격**하는 방법을 함께 요구했고 Hindsight 논문도 링크했다. 여기서 승격은 최근의 상세 기록을 검토해 반복해서 쓸 내용을 장기 파일로 정제하는 일을 뜻한다. 이 이슈는 이후 아키텍처의 검색과 승격을 한 문제로 묶어 표현한 가장 분명한 공개 유지보수자 요청이다.

> **변화의 동기.** 실제 목표는 검색과 승격을 하나의 메모리 문제로 다루는 일이었다. 동기 출처는 유지보수자가 작성한 Issue #102이고, 증거 강도는 그 요청 자체에는 **명시적**이다. 다만 뒤의 벡터 검색·Dreaming이 이 요청에 대응한다는 사실은 기능의 대응 관계일 뿐, 그 구현 형태가 Hindsight에서 직접 나왔다는 인과는 입증되지 않았다.

두 요구는 서로 다른 시점과 방식으로 구체화되었다. 벡터 검색은 1월에 출시되었다. 에이전트가 수행하는 승격은 1월 6일 워크스페이스 지침에 먼저 들어가, 하트비트 작업이 일일 기록을 검토하고 오래 유지할 항목을 `MEMORY.md`로 정제하도록 했다. 4월의 Dreaming은 검색에 반복해서 쓰인 기록에 점수를 매기고, 자동 승격을 시작할 점수 기준과 일정·상태를 두어 승격을 관찰하고 측정할 수 있게 했다.

이것은 **기능의 대응 관계**이지 직접 인과관계의 증명이 아니다. 이 조사에서 확인한 후속 Dreaming PR과 코드는 Hindsight를 인용하지 않는다.

구현 형태는 여전히 열려 있었다. 초기 커뮤니티 제안인 [PR #302](https://github.com/openclaw/openclaw/pull/302)는 새 기억을 먼저 수신함에 모으고, 예약된 “사서” 작업이 이를 장기 저장소로 통합하는 흐름을 탐색했다. 기억·회상·통합 도구뿐 아니라 저장량 상한, 오래된 항목을 먼저 지우는 규칙, 그룹별 격리도 함께 제안했다. 작성자가 더 많은 개인 테스트를 위해 닫았으므로 출시된 기능은 아니다. 다만 메모리 설계가 안정되기 전부터 통합, 무제한 증가 방지, 프라이버시를 한 묶음으로 보았다는 맥락적 증거는 된다.

> **변화의 동기.** PR #302가 가정한 설계 압력은 통합 과정의 저장량 증가와 그룹 프라이버시였다. 이는 당시 커뮤니티가 탐색한 **맥락적 증거**이며 이후 구현의 직접 원인은 입증되지 않았다. 수신함·사서 구조는 한 후보였을 뿐이며, 닫힌 미출시 PR을 이후 제품 설계의 원인으로 읽어서는 안 된다.

## 외부 QMD 실험과 “기록하라”는 원칙이 나란히 등장하다 — 2026-01-03

자체 검색 엔진이 없던 시기에도 늘어난 파일에서 뜻이 가까운 내용을 찾을 필요는 있었다. [QMD(Query Markup Documents)](01-current-architecture.md#qmd-explained)는 문서를 기기 안에서 색인하고 정확한 단어와 의미 유사성을 함께 이용해 질의하는 별도 로컬 검색 프로그램이다. [`7e4e9ecdeaf8`](https://github.com/openclaw/openclaw/commit/7e4e9ecdeaf8849dbe464f31e50f4932c88904a3)은 워크스페이스 에이전트가 외부 `qmd` 명령으로 관련 기억을 찾도록 지시했고 `v2.0.0-beta5`에 처음 포함되었다. 이때 QMD는 아직 OpenClaw가 설치·색인·실패 처리를 관리하는 백엔드가 아니었다. 제품 내부 검색이 자리 잡기 전에 외부 명령을 빌려 시도한 로컬 의미 검색이었다.

같은 날 [`c2a74d6d2a1b`](https://github.com/openclaw/openclaw/commit/c2a74d6d2a1bd57889ff4bb1d7e43621f49e3c63)은 더 근본적인 지속성 원칙을 추가했다. 모델이 현재 대화 안에서만 기억하는 내용은 세션이 끝나면 사라지지만, 파일에 쓴 내용은 다음 세션에서도 다시 읽을 수 있다는 “기록하라”는 규칙이었다.

두 변화는 메모리의 양쪽을 보여 준다. 먼저 내용을 파일에 남겨야 하고, 남긴 뒤에는 관련 내용을 다시 찾을 수 있어야 한다. 그러나 외부 명령에 기대는 검색에는 설치, 색인 갱신, 오류 처리를 제품이 책임지지 않는 한계가 있었다. 자체 검색이 자리 잡은 뒤 외부 QMD 지침은 1월 12일 [`31752aa9445c`](https://github.com/openclaw/openclaw/commit/31752aa9445cb4b16b14f0e3d5a0a822a25cd436)에 의해 제거되었다. QMD는 한 달 뒤인 2월에 OpenClaw가 실행과 색인 상태를 관리하는 선택형 백엔드로 돌아왔다.

> **변화의 동기.** 외부 `qmd`로 의미 검색을 시도한 이유와 후속 제거 이유는 커밋 흐름에서 **코드로 추론**한다. 반면 [`c2a74d6d2a1b`](https://github.com/openclaw/openclaw/commit/c2a74d6d2a1bd57889ff4bb1d7e43621f49e3c63)은 “머릿속 메모는 세션을 넘지 못하지만 파일은 남는다”는 영속화 이유를 직접 밝혀 **명시적 증거**다. QMD 지침은 OpenClaw 자체 검색이 자리 잡은 뒤 제거되었지만, 제거 커밋이 그 인과를 설명하지는 않는다.

## 대문자 `MEMORY.md`가 선별과 프라이버시를 함께 맡다 — 2026-01-06

일일 기록은 새로운 내용을 덧붙이기에는 좋지만, 반복해서 쓸 핵심 사실을 짧게 보여 주는 파일은 아니다. 오래 유지되는 개인 맥락은 잘못된 대화에 노출될 위험도 있다. 이 두 문제를 함께 다루기 위한 준비는 조금 앞서 시작되었다. 2025-12-22의 [`ca806897c251`](https://github.com/openclaw/openclaw/commit/ca806897c251cfbc333e11b4bdf71d18478783ae)은 **하트비트** 지침에 메모리 파일 정리를 포함했다. 하트비트는 사용자의 새 메시지가 없어도 정해진 주기에 실행되어 메일·일정 점검이나 배경 유지보수를 수행하는 에이전트 실행이다.

1월 6일의 선택은 장기 계층을 대문자 선별 파일 `MEMORY.md`로 다듬고, 여기에 명시적인 보안 원칙을 붙이는 것이었다. 이 파일에는 개인 정보가 들어 있을 수 있으므로 템플릿은 여러 사람이 보는 공유 맥락이 아니라 사용자와 직접 대화하는 주 세션에서만 읽도록 지시했다. [`7d1fee70e76f`](https://github.com/openclaw/openclaw/commit/7d1fee70e76f2f634f1b41fca927ee663914183a)는 `v2026.1.8`에 처음 포함되었다. 이어 [`9ffea23f31ca`](https://github.com/openclaw/openclaw/commit/9ffea23f31ca1df5183b25668f8f814bee0fb34e)는 하트비트가 최근 일일 기록을 다시 읽고, 오래 유지할 사실을 `MEMORY.md`로 정제하며, 낡은 항목을 제거하도록 했다.

> **변화의 동기.** 실제 압력은 일일 기록을 압축된 장기 모델로 정제하면서 개인 맥락이 공유 대화로 새지 않게 하는 일이었다. 동기 출처는 보안 경계와 정제 목적을 직접 밝힌 [`7d1fee70e76f`](https://github.com/openclaw/openclaw/commit/7d1fee70e76f2f634f1b41fca927ee663914183a)와 [`9ffea23f31ca`](https://github.com/openclaw/openclaw/commit/9ffea23f31ca1df5183b25668f8f814bee0fb34e)이며, 증거 강도는 **명시적**이다. 대문자 선별 파일, 주기적 정제, 직접 대화 중심의 읽기 제한을 함께 두어 장기 계층의 역할과 공개 범위를 분리했다.

1월이 두 시간축 자체를 발명한 것은 아니다. 새로 생긴 것은 장기 계층을 선별된 대문자 파일로 명확히 하고, 주기적으로 관리하며, 개인용 맥락으로 취급하라는 규칙이었다. 그러나 어떤 항목을 승격하거나 삭제할지는 여전히 에이전트의 판단과 지침에 의존했다. 이후 Dreaming이 검색 사용량에 따라 승격을 자동화하고 측정 가능한 상태로 만들지만 기본 비활성인 선택 기능이므로 이 지침을 대체하지 않는다. 기본 템플릿에는 하트비트 정제 지침이 지금도 남아 있지만, 실제 승격은 하트비트 실행과 에이전트 판단, 파일 쓰기에 달려 있어 런타임이 보장하는 기본 동작으로 읽어서는 안 된다.

## 수동 검색이 메모리 파일 밖의 대화 기록에 닿다 — 2026-01-07

아무리 기록 지침이 좋아도 모든 중요한 사실이 메모리 파일로 선별되지는 않는다. 빠진 내용은 과거 대화 자체에만 남아 있을 수 있다. 이 공백을 메우기 위해 전체 대화 이력을 검색하는 `session-logs` 스킬이 생겼다. [`388796253a03`](https://github.com/openclaw/openclaw/commit/388796253a0380f47cae15a434f1f1e33b034ce1)은 `v2026.1.8`에 처음 포함되었다.

이 스킬은 세션 로그의 JSONL, 즉 한 줄마다 하나의 JSON 기록이 있는 파일을 `jq` 명령으로 읽었다. 사용자와 에이전트의 텍스트를 추출한 뒤 여러 세션에서 정확한 단어나 문자열을 찾았다. 오늘날의 통합 검색 도구처럼 모델이 구조화된 결과를 받는 방식이 아니라, 필요할 때 사람이 또는 에이전트가 스킬 절차를 따라 셸 명령을 실행하는 수동 회상이었다.

> **변화의 동기.** 실제 압력은 메모리 파일에 선별되지 않은 사실도 과거 대화에서 되찾는 일이었다. 동기 출처는 대화 이력 검색 스킬을 추가한 구현 커밋이며, 증거 강도는 **코드에서 추론**이다. 여러 원본을 아우르는 색인과 접근 권한 검사가 없던 시기라 `jq`와 셸에서 정확한 단어를 찾는 수동·저비용 형태를 택했다.

이 변화는 의미 메모리와 대화 기록 회상이 서로 다른 원본을 다룬다는 사실을 분명히 했다. 전자는 선별된 파일에서 오래 쓸 사실을 찾고, 후자는 선별되지 않은 과거 발화까지 원본 로그에서 찾는다. 대화 기록 회상의 필요는 과거 대화를 임베딩으로 찾는 실험 기능보다 열흘 먼저 드러났지만, 이때의 구현은 스킬이 이끄는 수동 셸 조회였다. 통합 색인, 대화별 접근 권한, 모델이 직접 호출하는 검색 도구는 다음 시기의 과제로 남았다.

## 다음 장으로

2025년 말과 2026년 1월 초의 변화는 사람이 이해하고 소유할 수 있는 메모리 원본을 만들었다. 그 과정에서 세션 연속성과 의미 메모리, 대화 기록 회상의 역할도 갈라졌다. 동시에 세 가지 과제가 남았다.

1. 중요한 내용은 먼저 파일에 써야 세션을 넘어 남는다.
2. 파일에 남아 있어도 현재 질문과 관련된 부분을 찾아야 답변에 쓸 수 있다.
3. 개인 기억과 대화 기록은 허용된 맥락에서만 불러와야 한다.

다음 장은 이 과제들이 컴팩션 전 마지막 저장 기회, 자체 검색, 두 가지 수집 모델, 한 번에 하나만 선택하는 메모리 플러그인 슬롯, 실행과 색인 상태를 제품이 관리하는 QMD 백엔드로 구체화되는 2026년 1월과 2월을 따라간다.
