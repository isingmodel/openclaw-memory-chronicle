# 11장. 기존 평가 자산과 권고 로드맵

앞 장에서 확인한 계약 간극은 평가가 다뤄야 할 범위를 정한다. 검색 정확도만 높이는 것으로는 비공개 부트스트랩, 트랜스크립트 물질화, 플러그인 소유권, 마이그레이션과 폴백의 의미를 증명할 수 없다. 평가 로드맵은 이 OpenClaw 고유의 의무에서 출발해야 한다.

그렇다고 새로운 벤치마크 체계를 처음부터 만들 필요는 없다. 외부 데이터셋과 실행기를 작은 어댑터로 재사용하면 검색, 충돌, 교정, 삭제, 규모 같은 문제를 더 빨리 시험할 수 있다. 다만 생명주기·범위·프라이버시에 관한 OpenClaw 자체 QA는 최종 권위로 남아야 한다.

이 장에 인용한 외부 프로젝트, 리비전, 체크섬, 라이선스는 2026-07-18에 확인한 현황이다. 반면 도입 순서, 실행 주기, P0–P3는 그 자산을 어떻게 조합할지에 관한 이 책의 제안이며, 유지보수자가 채택한 로드맵이나 현재 CI 계약이 아니다.

## 프로젝트 이름보다 평가 과제를 먼저 고른다

벤치마크는 하나의 종합 시험이 아니다. 먼저 고치려는 실패를 정하고, 그 실패를 실제로 재현하는 자료를 골라야 한다. 다음 과제 분류는 뒤의 프로젝트 표를 읽는 기준이다. 예시는 모두 이 책의 `ORBIT` 합성 장면을 확장한 것이며 실제 사용자 자료가 아니다.

| 평가 과제        | `ORBIT` 합성 예시                                                                  | 주로 활용할 자산                           |
| ---------------- | ---------------------------------------------------------------------------------- | ------------------------------------------ |
| 정확 회상        | “코드명이 정확히 무엇인가?”에 `ORBIT-10`이라는 식별자를 그대로 찾는다              | LongMemEval, MEME                          |
| 의미 회상        | “그 프로젝트를 뭐라고 부르기로 했지?”처럼 표현이 달라도 같은 근거를 찾는다         | LongMemEval, MemoryAgentBench              |
| 갱신·충돌 해결   | 오래된 `ORBIT-9`보다 새 `ORBIT-10`을 우선하고 대체 관계를 설명한다                 | MEME, MemoryAgentBench, BEAM               |
| 삭제             | “코드명을 잊어 줘” 뒤에는 검색·주입·승격 후보에서 사라졌는지 확인한다              | MEME                                       |
| 정답 없음·기권   | 코드명을 한 번도 알려 주지 않은 사례에서 값을 지어내지 않고 멈춘다                 | LongMemEval, MEME, BEAM                    |
| 장거리 작업 흐름 | 여러 세션과 도구 실행 사이에 생긴 결정·환경 변화가 나중 단계에 반영된다            | MemoryAgentBench, LongMemEval-V2           |
| 규모             | 같은 종류의 기록이 10만–100만 건일 때 순위·지연·비용이 유지되는지 본다             | BEAM                                       |
| 생명주기 전체    | 대화 제시부터 기록, 재설정(`reset`), 색인, 검색, 교정까지 실제 런타임으로 통과한다 | OpenClaw QA와 얇은 외부 데이터 어댑터 조합 |

외부 자산은 주로 앞 여섯 과제의 입력과 정답을 제공한다. 그러나 OpenClaw가 실제로 메모를 썼는지, 대화 범위를 지켰는지, 채널에 올바르게 전달했는지까지 증명하려면 마지막 행의 자체 QA가 필요하다. “검색 벤치마크 점수가 높다”와 “메모리 하네스 전체가 안전하게 동작한다”를 같은 주장으로 취급해서는 안 된다.

## 기존 해법을 먼저 확인한다

OpenClaw에 필요한 것은 독자적인 벤치마크 세계를 새로 만드는 일이 아니라, 외부 자료를 OpenClaw 평가 입력으로 바꾸는 얇은 **어댑터**(adapter)다. 이 어댑터는 외부 산출물을 각자의 라이선스에 맞춰 들여오면서도 OpenClaw 자체의 생명주기·프라이버시 시험을 권위 있는 기준으로 유지해야 한다.

아래 저장소 링크는 2026-07-18에 확인한 정확한 리비전을 고정한다. 데이터셋을 받을 때도 바뀔 수 있는 기본 브랜치를 따라가지 말고 Hugging Face 리비전과 파일 체크섬을 함께 고정해야 한다.

### 왜 코드·데이터·채점기 라이선스를 따로 보는가

하나의 벤치마크도 실행 코드, 문제 데이터, 답을 판정하는 채점기가 서로 다른 저작물일 수 있다. **저작자 표시(attribution)** 조건은 배포물에 출처를 남기라는 뜻이고, **동일조건변경허락**(share-alike)은 수정·재배포한 파생 자료에도 같은 계열의 조건을 이어야 한다는 뜻이다. **비상업(noncommercial)** 조건은 상업적 제품의 기본 CI에서 자유롭게 쓸 수 있다는 뜻이 아니다. **각색·파생**(adaptation)은 원본을 OpenClaw 형식으로 바꾸거나 일부를 재구성한 결과를 가리킨다.

따라서 결과 명세(manifest)는 코드·데이터·채점기 라이선스를 서로 다른 필드로 관리한다. MEME의 저작자 표시를 보존하고, BEAM 파생 자료를 재배포하기 전에는 동일조건변경허락 의무를 검토한다. LoCoMo의 비상업 조건을 명시적으로 승인받지 않았다면 기본 상업 CI에서 제외한다. 이 설명은 법률 자문이 아니라, 기술 평가에서 서로 다른 배포 의무를 한데 섞지 않기 위한 운영 원칙이다.

외부 평가 묶음의 좋은 점을 가져오되, “결과 추적의 어느 단계를 실제로 시험하는가”를 표시해야 한다. 검색 질문에 잘 답하는 묶음이 포획, 프라이버시, 삭제까지 검증했다고 확장 해석해서는 안 된다.

체크섬과 고정 리비전은 선택 논리와 분리해 [13장의 평가 자산 무결성 표](13-references-reproduction-and-conclusion.md#평가-자산의-고정-리비전과-데이터-무결성-값)에 모았다. 실제 실행기는 그 표를 입수 명세로 읽고 다운로드한 파일을 다시 검증해야 한다.

## 두 실행 경로를 분리한다

### 검색 전용 경로(`retrieval-only`)

정본 Markdown·대화 기록 출처를 미리 적재하고 선택한 인덱스를 구축한다. 접근 적격성, 근거 회상·순위, 인용, 답변, 지연, 비용을 측정한다. 검색 자체를 고립해서 볼 수 있지만 모델 주도 포획과 생명주기는 우회한다.

### 생명주기 종단간 경로(`end-to-end`)

평가 대화를 실제 세션과 런타임에 전달한다. 기록, 재설정, 컴팩션, 통합을 실행한 뒤 전체 결과 추적을 측정한다. 더 느리고 확률적으로 달라질 수 있지만 포획과 승격을 함께 평가할 수 있는 유일한 경로다.

모든 결과 명세는 데이터셋과 어댑터가 어느 추적 단계를 실제로 다루는지 표시해야 한다. 검색 전용 LongMemEval 점수를 메모리 시스템 전체의 품질로 발표해서는 안 된다.

> **예시 — 합성 사례(결과 표지):** 같은 LongMemEval 하위 집합을 사용해도 원본 파일을 미리 넣고 검색만 측정했다면 `retrieval-only`다. 대화를 실제 런타임에 전달해 에이전트가 메모를 쓰게 한 뒤 초기화와 검색까지 수행했다면 `end-to-end`다. 두 결과는 서로 다른 질문에 답하므로 한 순위표 열로 합치면 안 된다.

## 우선순위가 낮거나 주의가 필요한 선택지

- [LoCoMo](https://github.com/snap-research/locomo/tree/3eb6f2c585f5e1699204e3c3bdf7adc5c28cb376)는 역사 비교에는 유용하지만 작고 CC BY-NC 4.0이다. 확인한 기본 브랜치 리비전의 마지막 업데이트는 2024-08-13이었다.
- Mem0의 오래된 [OpenMemory UI/MCP 묶음](https://github.com/mem0ai/mem0/tree/ddaa655edf41e3ed375b263fb227da0bcd42ccb9/openmemory)에는 종료 예정 안내가 있다. 비교 백엔드가 필요할 때만 유지보수 중인 서버를 사용한다.
- [MemBench](https://github.com/import-myself/Membench)와 공개 [MemoryArena](https://memoryarena.github.io/) 코드는 현재까지 명확한 루트 코드 라이선스가 없다. 분류 체계는 흥미롭지만 코드 재사용은 라이선스가 분명해질 때까지 기다린다. [MemoryArena 데이터셋](https://huggingface.co/datasets/ZexueHe/memoryarena) 자체는 CC BY 4.0이다.

## 권고 도입 순서

가장 작고 결정적인 검색 회귀에서 시작해 교정·충돌·규모·멀티모달로 넓혀 가는 도입 순서는 다음과 같다. 이는 현재 채택된 순서가 아니라 앞의 장부와 계약 간극에서 도출한 제안이다.

1. 작은 OpenClaw 어댑터로 결정적인 LongMemEval-cleaned 근거 검색 하위 집합을 추가하고, 답변 채점은 예약 실행 경로에서 수행한다.
2. MEME의 교정·삭제·연쇄 삭제·부재 하위 집합을 추가한다.
3. MemoryAgentBench의 충돌·장거리 하위 집합을 추가한다.
4. BEAM 10만·100만 건 자료를 예약된 규모·비용 시험 경로에서 실행한다.
5. 작업 흐름과 멀티모달 메모리를 위해 LongMemEval-V2 Small을 추가한다.
6. 채널, 범위, 폴백, 마이그레이션, 생명주기는 OpenClaw QA를 권위 있는 기준으로 유지한다. 열거된 적합성 행렬에서 관찰된 프라이버시 위반 0건을 요구한다.

어떤 외부 평가 묶음도 편집 가능한 Markdown, 파생 인덱스, 모델 주도 포획, Active Memory, Dreaming, 플러그인 대체, 채널 전달, 비공개 대화 기록 경계의 조합 전체를 모델링하지 않는다. 라이선스가 서로 다른 데이터셋과 채점기를 산출물 명세 아래에서 어댑터로 연결해야 한다. MEME의 저작자 표시를 보존하고, 재배포하는 BEAM 파생 평가 사례는 CC BY-SA 검토를 통과시킨다. 명시적 승인이 없으면 LoCoMo를 기본 상업 CI에서 제외한다. OpenClaw 자체 적합성 증명을 대체해서도 안 된다.

## 실행 주기 제안

같은 평가도 비용과 불확실성에 따라 실행 주기가 달라져야 한다. 다음 실행 주기는 변경마다 돌릴 결정적 검증과 예산 승인이 필요한 원격 검증을 나눈 제안이며, 현재 CI 계약은 아니다.

- **변경마다:** 격리되고 결정적인 QA와 정답을 미리 표시한 작은 LongMemEval·MEME 검색 카나리를 실행한다. 네트워크, 실제 사용자 코퍼스, 모델 판정자는 사용하지 않는다. 범위에 영향을 주는 변경은 직접 대화·비공개·직접 스레드의 허용 사례와 그룹·공유 스레드의 차단·격리 사례도 실행한다.
- **매일 밤:** 예산 승인을 받은 원격 LongMemEval·MemoryAgentBench 하위 집합을 메모리 백엔드·플러그인과 임베딩 공급자 설정 조합에서 실행한다. 토큰, 비용, 경과 시간, 동시 실행 상한을 명시한다.
- **매주:** 예산 승인을 받은 원격 BEAM 10만·100만 건, LongMemEval-V2 Small, 통합, 마이그레이션, 인덱스 신선도 부하 시험을 실행한다.
- **릴리스:** 전체 프라이버시 행렬, 폴백, 멀티모달, CJK, 최초 시작·초기화·압축, 가져오기, 교차 대화 증명을 실행하고 벤치마크 명세와 잔여 위험 요약을 보관한다.

## 권고 개선 우선순위

마지막 표는 앞선 계약 간극과 평가 자산을 하나의 개선 순서로 겹쳐 본다. P0–P3는 위험과 선행조건을 읽기 위한 이 책의 우선순위이며, 유지보수자가 채택한 계획도 역사적 기록만으로 확정된 결론도 아니다. 각 행은 작업보다 오른쪽의 출시 전 증명을 함께 읽어야 한다.

## 다음 장으로

이 로드맵은 새로운 저장소나 하나의 종합 점수를 결론으로 내세우지 않는다. 먼저 경계를 합의하고, 실패 단계를 관찰하며, 외부 자산이 답하는 질문과 OpenClaw 자체 QA가 맡아야 할 질문을 분리하는 순서를 제시한다.

맺음말은 이 순서를 다시 한 문장의 기억이 지나가는 생애로 압축한다. 파일에서 시작한 역사가 어떻게 검색·상태·범위·평가의 책임 구조로 이어졌는지 되짚으며 책의 논증을 닫는다.
