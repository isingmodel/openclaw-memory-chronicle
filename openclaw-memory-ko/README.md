# OpenClaw Memory: The Past and Present of Its Memory Architecture—and How It Evolved

## OpenClaw 메모리 구조의 과거와 현재, 그리고 진화 과정

AI 어시스턴트는 기억하는 것처럼 보인다. 그러나 모델은 지난 호출의 입력을 스스로 보존하지 않는다. 호출이 끝나면 그 문맥도 끝난다.

가상의 사용자가 어제 “`ORBIT-10`의 배포 검토는 금요일 오후 4시이고, Mina가 승인해”라고 말했다고 하자. 오늘 새 대화에서 “승인자는 누구였지?”라고 물었을 때 정확히 답하려면 비슷한 문장을 찾는 것만으로는 부족하다. 원래 대화를 보존하거나 오래 쓸 사실을 따로 기록해야 하고, 그 기록을 검색할 수 있어야 하며, 지금 대화가 그 내용을 볼 수 있는지도 확인해야 한다. 사용자가 나중에 승인자를 바꾸면 오래된 값보다 새 값이 앞서야 한다.

OpenClaw는 사용자가 자신의 기기에서 운영하며 여러 대화 채널, 도구, 자동화 작업을 하나의 게이트웨이(Gateway)로 연결하는 개인용 AI 어시스턴트다. 같은 세션이 이어지는 것은 모델이 기억해서가 아니라 런타임이 대화 기록과 컴팩션 요약을 다음 입력으로 다시 조립하기 때문이다. 여러 세션에서 오래 쓸 사실은 사람이 읽고 고칠 수 있는 의미 기억으로 선별할 수 있고, 선별되지 않은 과거 표현은 권한이 허용하는 대화 기록 검색으로 되찾을 수 있다.

이 책의 중심 생각은 단순하다. **OpenClaw의 기억은 하나의 저장소가 아니라 책임의 구조다.** 사람이 뜻을 고치는 Markdown, 원래 발화를 보존하는 대화 기록, 원본에서 다시 만드는 검색 색인, 런타임이 관리하는 운영 상태가 서로 다른 일을 맡는다. 이 구분을 놓치면 검색 실패를 데이터 손실로 오해하고, 관련성이 높은 과거 문장을 현재의 행동 승인으로 잘못 받아들이며, 인덱스를 기억의 원본처럼 다루게 된다.

이 구조도 처음부터 완성되어 있지 않았다. 의미 메모리보다 세션 ID 연속성이 먼저 있었고, 의미 메모리는 벡터 데이터베이스가 아니라 사람이 읽는 파일을 다음 실행에서 다시 읽는 관례로 시작했다. 파일 경로에는 수명주기 포획, 파생 검색 인덱스, 플러그인 소유권, 능동적 회상과 통합이 더해졌다. 그와 별개로 대화 기록 경로는 수동 로그 검색에서 정식 SQLite 보존·정확 검색·범위가 제한된 대화 간 회상으로 발전했다.

## 이 책이 따라가는 세 질문

이 책은 기능 목록보다 다음 세 질문을 따라간다.

1. **무엇이 실제로 남는가?** 같은 대화를 이어 가는 것, 원래 발화를 보존하는 것, 오래 쓸 사실을 선별하는 것, 필요한 내용을 다시 가져오는 것은 어떻게 다른가?
2. **누가 소유하고 누가 볼 수 있는가?** Markdown, SQLite, 검색 인덱스와 플러그인은 각각 무엇을 책임지며, 어느 대화와 에이전트까지 결과를 보여 줄 수 있는가?
3. **정말 더 잘 기억하게 되었는가?** 검색 횟수나 결과 수가 아니라 정확성·권한·시간·모순·프라이버시를 포함해 개선을 어떻게 검증할 것인가?

이 책은 그 답의 **과거와 현재**, 그리고 변화가 일어난 **방법과 이유**를 코드·커밋·PR·이슈·공식 문서·외부 1차 자료로 추적한다. 2장부터 7장까지는 각 업그레이드 곁에 `변화의 동기`를 붙여 사용자·유지보수자 요청, 관측된 장애·회귀, 운영 측정, 설계·소유권 압력을 구분한다. 이유가 1차 자료에 적혀 있는지, 코드에서만 추론되는지, 비슷하지만 직접 연결되지 않은 맥락인지도 표시한다. 마지막에는 더 나은 메모리 시스템을 만들기 위해 어떤 신호를 수집하고 어떤 실험을 설계해야 하는지 제안한다. 12장에 있는 41개 이정표의 동기·근거 색인은 이 판정을 다시 대조하는 자료편이다.

## 30초 전체 지도

오래 이어지는 에이전트의 기억을 이해하려면 먼저 네 질문만 구분하면 된다. 아래 표는 한 번의 모델 호출이 끝난 뒤에도 남는 **네 저장 장부**를 설명한다. 답변을 만드는 동안만 존재하는 현재 모델 문맥은 저장 장부가 아니므로 여기서는 세지 않는다. 1장에서는 이 일시적 문맥을 더해 다섯 상태가 다음 답변에서 어떻게 합쳐지는지 보여 준다.

| 질문                                              | 짧은 답                                                    | 잃거나 망가졌을 때                                                      |
| ------------------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------- |
| 사람이 읽고 직접 고칠 의미 원본은 무엇인가?       | 장기 사실과 날짜별 작업 노트를 담은 Markdown 파일이다.     | 기억하려던 의미 자체를 잃거나 낡은 내용을 고치기 어려워진다.            |
| 빠르게 찾기 위해 다시 만드는 것은 무엇인가?       | 원본에서 만든 전체 텍스트·의미 검색용 색인이다.            | 검색은 느리거나 부정확해지지만 원본이 남아 있으면 다시 만들 수 있다.    |
| 실행 중 시스템이 스스로 관리하는 상태는 무엇인가? | 처리 위치, 회상 횟수, 잠금, 캐시 같은 운영 정보다.         | 작업이 중복되거나 멈출 수 있지만 그 자체가 사용자의 기억 원문은 아니다. |
| 실제로 오간 대화는 어디에 남는가?                 | 에이전트별 SQLite가 소유하는 정식 세션·대화 기록에 남는다. | 과거의 정확한 표현과 대화 흐름을 되찾기 어려워진다.                     |

따라서 “무엇을 오래 기억하는가”, “어떻게 빨리 찾는가”, “시스템이 어디까지 처리했는가”, “과거에 정확히 무슨 말을 했는가”는 서로 다른 질문이다. 대화 기록이 남았다고 모든 발화가 장기 의미 기억이 되는 것도 아니고, 의미 기억을 찾았다고 현재 대화에서 볼 권한이나 행동할 권한이 생기는 것도 아니다. 네 답을 한 저장소나 한 점수로 뭉뚱그리지 않는 것이 이 책의 출발점이다.

기본 경로가 보이면 선택 구성 요소의 자리도 단순해진다. 이들은 모두 같은 종류의 “더 좋은 메모리”가 아니라 서로 다른 단계를 바꾼다.

- **[QMD](01-current-architecture.md#qmd-explained)**는 Query Markup Documents의 약자다. 새 기억을 쓰는 기능이 아니라, `memory-core` 안에서 내장 SQLite 검색을 대신할 수 있는 별도 로컬 검색 프로그램이다.
- **Dreaming**은 기본적으로 꺼져 있는 `memory-core` 통합 기능이다. 자격 있는 회상 신호를 점수화하고, Deep 단계에서 검증된 후보를 장기 기억으로 승격한다.
- **Active Memory**는 주 메모리 슬롯을 바꾸지 않고 답변 전에 제한된 별도 에이전트가 필요한 기억을 찾게 하는 선택 플러그인이다. 플러그인이 활성화된 개인형 `memory-core` 설치에서는 보호된 대화 간 회상이 조건부 기본값으로 켜질 수 있지만, 결과마다 비공개 범위를 다시 검사한다. 찾은 내용을 현재 답변 문맥에 잠시 더할 뿐 새 장기 기억을 쓰지는 않는다.
- **LanceDB**는 주 메모리 슬롯에서 `memory-core`를 대신해 자체 벡터 저장소와 자동 수집·회상을 소유하는 선택지다. Dreaming을 함께 불러오는 예외는 별도로 존재한다.
- **Memory Wiki**는 선택된 주 메모리 옆에 구조화된 로컬 지식을 더하고, **Honcho**는 외부 대화 보존과 사용자·에이전트 모델링을 더한다.

[1장](01-current-architecture.md)은 이 구성 요소들이 현재 구조의 어느 단계에 놓이는지 설명한다. [3장](03-january-february-2026.md#qmd-managed-backend)부터 [7장](07-july-2026.md)까지는 검색 백엔드, 능동적 회상, 통합과 대화 간 권한이 어떤 순서로 생겼는지를 추적한다.

책의 후반부는 더 많은 기억이 언제나 더 좋은지 묻는다. 검색 빈도는 진실이나 유용성의 확정적 증거가 아니다. 회상 범위를 넓히기 전에 권한·시간·모순·개인정보 경계를 측정할 수 있어야 한다. 그래서 이 책은 역사와 현재 계약을 먼저 확인한 뒤, 개선 제안과 검증 방법을 분리해 다룬다.

## 추천 읽기 경로

처음 OpenClaw 메모리를 만난 독자라면 0장에서 이 책의 렌즈를 익히고 1장에서 현재 구조를 본 다음, 2장부터 7장까지 시간을 따라가는 길이 가장 자연스럽다. 현재 모습과 그 모습이 생긴 이유를 함께 이해할 수 있다.

구현이나 제품 결정을 검토한다면 1장에서 소유권과 상태 경계를 잡은 뒤 8장, 9장, 10장, 11장으로 이동하라. 과거의 설계 선택, 평가 신호, 현재 계약의 간극, 권고 로드맵이 한 흐름으로 이어진다.

평가 체계를 설계하려면 9장, 10장, 11장을 차례로 읽는 편이 좋다. 9장은 어떤 결과를 추적할지 설명하고, 10장은 그 평가가 닫아야 할 현재 계약의 간극을 드러내며, 11장은 기존 벤치마크와 권고 로드맵을 실제 검증 순서로 연결한다.

근거를 직접 재현하려는 독자는 12장의 이정표 색인에서 출발해 13장 ‘출처와 재현 안내’와 부록 A의 근거 감사 지도를 오가면 된다. 낯선 용어가 막을 때는 14장을 곁에 두면 된다.

## 이 책의 두 나침반

이 책 전체를 관통하는 명제는 두 가지다.

- 기본 `memory-core` 경로에서는 사용자가 이해하고 편집할 수 있는 의미 기억을 유지하고, 인덱스와 운영 상태는 파생되거나 기계 소유 상태로 분리한다.
- 검색 빈도는 진실이나 유용성의 확정적 증거가 아니다. 회상 범위를 넓히기 전에 권한·시간·모순·개인정보 경계를 측정할 수 있어야 한다.
