# 7장. 2026년 7월: 정식 대화 기록 검색, 가져오기, 보호된 대화 간 회상

7월의 과제는 기억의 양을 늘리는 일이 아니었다. 평범한 검색 실패 하나가 답변을 약 70초 늦출 수 있었고, 과거 대화의 정확한 오류 문구를 찾으려면 어느 세션인지 미리 알아야 했다. 같은 개인 에이전트도 비공개 채널이 달라지면 앞선 대화를 활용하지 못했다. 다른 실행 환경에서 쌓은 Markdown 기억을 안전하게 옮기는 공식 경로도 없었다.

OpenClaw는 먼저 사용자가 답을 기다리는 동안 실행되는 검색과 오래 걸릴 수 있는 복구 작업을 분리했다. 이어 세션과 대화 기록의 유일한 런타임 원본을 SQLite로 옮기고, 정확한 용어를 찾는 `sessions_search`, 다른 하네스의 Markdown 기억 가져오기, 개인 에이전트를 위한 제한된 대화 간 회상을 차례로 더했다. 마지막 기능과 일부 상태 통합은 이 책의 아키텍처 기준일에는 `main`에만 있었지만, 며칠 안에 베타 태그에 포함되었다. 이 장은 **기준일의 코드 상태**와 **2026-07-26에 다시 확인한 최초 출시 태그**를 구분해 살펴본다.

## 전경 검색에서 유지보수를 분리하다

**전경 검색**은 사용자가 현재 답변을 기다리는 동안 요청 경로에서 바로 실행되는 조회다. 이 경로에서는 지연 시간이 곧 대화 지연이 된다. 그런데 결과가 없는 평범한 [QMD](01-current-architecture.md#qmd-explained) 질의가 강제 동기화와 임베딩 같은 유지보수까지 시작하면서, 기억을 찾지 못한 한 번의 검색이 대화를 약 70초 멈추는 장애로 커졌다. QMD는 새 기억을 쓰는 기능이 아니라 `memory-core`가 선택적으로 사용하는 별도의 로컬 검색 프로그램이다. 실제 사례는 [Issue #90023](https://github.com/openclaw/openclaw/issues/90023)에 보고되었다.

해결책은 검색 요청 안에서 복구까지 끝내려 하지 않는 것이었다. `v2026.7.1`에 출시된 [PR #90030](https://github.com/openclaw/openclaw/pull/90030)은 장기 실행 QMD 관리자가 검색 실패를 즉시 반환하도록 바꾸고, 기존 유지보수 동작은 운영자가 명시적으로 실행하는 일회성 복구 경로에만 남겼다.

이 선택으로 정상 대화의 응답 시간과 복구 비용이 분리되었다. 대신 검색이 실패했다고 해서 저장소가 자동으로 고쳐지지는 않는다. 전경 조회는 진단 가능한 실패나 성능 저하 결과를 돌려주고, 동기화나 진단·수리 명령인 `doctor`처럼 소유자가 통제하는 경로가 복구를 맡는다.

> **변화의 동기.** 운영 장애에서 나온 **명시적 증거**다. Issue #90023과 PR #90030은 QMD의 평범한 검색 실패가 강제 동기화·임베딩으로 이어져 대화를 수십 초 멈춘 경로를 직접 연결한다. 장기 실행 QMD 관리자가 실패를 즉시 반환하고 명시적 일회성 경로에만 복구를 남긴 것은, 대화형 지연 상한과 인덱스 유지보수의 소유자를 분리하기 위해서다.

## 6월 인덱스 통합의 업그레이드 비용을 회수하다

앞 장의 에이전트별 데이터베이스 통합은 첫 구현에서 이전 독립 인덱스를 새 데이터베이스로 가져오지 않았다. 그 누락은 실제 업그레이드 비용으로 드러났다. 한 보고자는 인덱스 위치가 안내 없이 바뀐 뒤 1,499개 파일을 다시 임베딩해야 했다. [Issue #95495](https://github.com/openclaw/openclaw/issues/95495)가 이 비용을 기록했다.

[PR #95631](https://github.com/openclaw/openclaw/pull/95631)은 [`414c250af90d`](https://github.com/openclaw/openclaw/commit/414c250af90d0e19d44b407cf31b32a2221956c4)으로 병합되었고 `v2026.7.1-beta.1`에 처음 포함되었다. `doctor`가 이전 보조 인덱스를 검사해 새 에이전트 데이터베이스로 가져오되, 정상 런타임은 새 정식 저장소 하나만 읽도록 했다.

이 사례는 “원본에서 다시 만들 수 있다”와 “버려도 비용이 없다”가 같은 말이 아님을 보여 준다. 인덱스는 Markdown 원본에서 재구축할 수 있는 파생 상태지만, 재임베딩에는 시간·대역폭·공급자 비용이 들 수 있다. 따라서 파생 상태에도 가져올지 다시 만들지에 대한 명시적 결정, 진행 상황, 실패 경고가 필요하다.

> **변화의 동기.** Issue #95495는 기존 보조 인덱스를 옮기지 않아 1,499개 파일을 다시 임베딩한 실제 업그레이드 비용을 보고했고, PR #95631은 이를 직접 닫은 **명시적 사건 근거**다. 후속 수정이 런타임 이중 읽기 대신 `doctor`의 검증된 가져오기와 재시도 가능한 원본 보존을 택한 것은, 정상 경로를 하나로 유지하면서 유료·장시간 파생 상태도 안전하게 승계하기 위해서다.

## 세션과 대화 기록을 정식 SQLite 상태로 만들다

복구 작업을 분리해도 세션과 대화 기록이 여러 활성 저장소에 나뉘어 있으면 문제가 남는다. 세션 목록, 이력 조회, 검색, 컴팩션, 기억 코퍼스가 각기 다른 시점의 대화 상태를 볼 수 있기 때문이다. 여기서 **정식 SQLite 상태**란 단순히 파일 내용을 데이터베이스에도 복사한다는 뜻이 아니다. 정상 실행 중에는 에이전트별 SQLite만 권위 있는 원본으로 읽고 쓰며, 다른 형식은 더 이상 대체 저장소로 사용하지 않는다는 뜻이다.

이 원칙에 따라 세션 메타데이터와 대화 기록 이벤트를 SQLite로 옮겼다. [PR #98236](https://github.com/openclaw/openclaw/pull/98236)은 [`0a8e3604ba24`](https://github.com/openclaw/openclaw/commit/0a8e3604ba24de4791d3505b7a442e8017276dd0)로 병합되었고 `v2026.7.2-beta.1`에 처음 포함되었다. 기존 `sessions.json`과 줄마다 JSON 객체를 기록한 JSONL 파일은 정상 실행의 폴백이 아니라, `doctor`가 이전 상태를 옮길 때 읽는 입력이나 사람이 보관할 산출물이 되었다.

그 결과 여러 소비자는 한 트랜잭션으로 확정된 같은 상태를 볼 수 있게 되었다. 그 대가로 예전 파일을 정상 운용 중 몰래 읽어 주는 호환 경로는 사라졌다. 이전 상태를 계속 사용하려면 `doctor`의 마이그레이션을 거쳐 정식 저장소로 옮겨야 한다.

> **변화의 동기.** 저장소 소유권 정리에 대한 유지보수자 요청에서 나온 **명시적 증거**다. PR #98236은 세션 메타데이터와 대화 기록 이벤트를 여러 활성 저장소에서 읽는 혼합 상태가 소비자마다 다른 현실을 만들 수 있다고 직접 설명했다. 에이전트별 SQLite를 유일한 런타임 저장소로 삼고 예전 JSON/JSONL을 doctor 입력이나 보관 산출물로만 둔 것은, 모든 소비자가 같은 확정 상태를 보게 하고 정상 경로의 폴백 어긋남을 끝내기 위해서다.

## 의미 메모리 검색을 보완하는 정확한 대화 기록 검색

대화 기록이 한 저장소에 모여도 원하는 대화를 찾는 방법에는 공백이 있었다. 세션 목록은 제목과 시각 같은 메타데이터만 보여 주고, 이력 조회는 이미 세션 키를 알아야 했다. 기존 세션 기억 코퍼스는 실험 기능이었으며 임베딩 설정에 의존했다. [Issue #100978](https://github.com/openclaw/openclaw/issues/100978)은 이 발견성 문제를 지적했다.

OpenClaw는 의미 검색의 순위 계산을 더 복잡하게 만드는 대신, SQLite FTS5를 사용하는 `sessions_search`를 별도 도구로 추가했다. **FTS5**는 SQLite의 전체 텍스트 검색 기능으로, 대화문에 실제로 등장한 단어와 구절을 인덱싱해 찾는다. 따라서 이 장에서 말하는 **정확 검색**은 문장 전체가 바이트 단위로 같아야 한다는 뜻이 아니라, 임베딩으로 뜻이 비슷한 표현을 추정하지 않고 입력한 용어·식별자·오류 문구의 어휘 일치를 찾는다는 뜻이다. [PR #105057](https://github.com/openclaw/openclaw/pull/105057)은 [`6fc564278dbb`](https://github.com/openclaw/openclaw/commit/6fc564278dbb61691b0b07ec269b0bb60d225111)으로 병합되었고 `v2026.7.2-beta.1`에 처음 포함되었다.

`sessions_search`는 의도적으로 `memory_search`의 다른 이름이 아니다.

- 권한 검사를 통과한 원시 대화 기록 행을 검색한다.
- 임베딩이나 기억 설정이 필요 없다.
- 정확한 용어, 식별자, 오류, 인용문을 찾는 데 적합하다.
- 이미 아는 세션의 이력을 읽는 `sessions_history`와 같은 가시성 규칙을 적용한다.

이로써 영속 의미 메모리를 되살리는 일과 대화 보관 자료에서 정확한 표현을 찾는 일이 서로 보완하는 기능이 되었다. 호출자는 뜻이 비슷한 기억을 찾을 때와 실제 문자열을 찾을 때를 구분해야 한다. 제품 지침과 평가도 두 문제를 하나의 순위 계산으로 억지로 합치지 말아야 한다.

> **변화의 동기.** 사용자 요청에서 나온 **명시적 증거**다. Issue #100978과 이를 닫은 PR #105057은 목록은 본문을 찾지 못하고, 이력 조회는 이미 세션 키를 알아야 하며, 의미 검색은 실험 설정과 임베딩에 의존한다는 발견성 공백을 직접 밝혔다. 그래서 의미 순위 결정기를 확장하지 않고 대화 기록 행과 같은 트랜잭션에 FTS5 인덱스를 두고, `sessions_history`와 같은 가시성 판정을 쓰는 정확 검색 도구를 별도로 만들었다.

> **예시 — 합성 사례:** 과거 대화에 나온 정확한 오류 코드 `E_CONN_RESET_42`를 찾는 일은 `sessions_search`에 잘 맞는다. 반면 “이 사용자가 배포 전에 선호하는 검토 방식”처럼 의미가 비슷한 표현까지 찾아야 하는 일은 영속 의미 메모리 회상의 영역이다. 이는 도구 구분을 설명하는 가상 예시다.

## 하네스 사이의 기억 이동성을 인정한 가져오기

여기서 **하네스**는 Codex나 Claude Code처럼 모델을 실행하고 도구·설정·세션 상태를 관리하는 실행 환경을 뜻한다. 기억이 사용자 소유의 Markdown이라면 하네스를 바꿀 때 같은 사실과 선호를 처음부터 다시 가르치지 않고 옮길 수 있어야 한다. 그러나 하네스마다 형식과 수명주기가 다른 내부 데이터베이스, 인증 정보, 실행 기록까지 함께 복사하면 새 런타임의 경계와 충돌한다.

[Issue #106215](https://github.com/openclaw/openclaw/issues/106215)는 이 이동성 문제를 제기했다. [PR #106406](https://github.com/openclaw/openclaw/pull/106406)은 설정 전체가 아니라 기억 파일만 다루는 공용 가져오기 엔진을 만들고, Control UI에서 Codex와 Claude Code의 영속 Markdown을 가져올 수 있게 했다. 이 PR은 [`4319ddbe8cb0`](https://github.com/openclaw/openclaw/commit/4319ddbe8cb08a49335eff22b82e3a7afe3d3201)으로 병합되었고 `v2026.7.2-beta.1`에 처음 포함되었다.

엔진이 있어도 설치 과정에서 찾을 수 없다면 사용자는 기능의 존재를 알기 어렵다. [PR #108977](https://github.com/openclaw/openclaw/pull/108977)은 감지된 가져오기 후보를 다음 온보딩 흐름에 노출하고, Hermes의 기억 파일도 지원했다. 이 PR은 [`e71ef76e8ed7`](https://github.com/openclaw/openclaw/commit/e71ef76e8ed74179699af1feacbd5a9042345c1c)으로 병합되었고 `v2026.7.2-beta.2`에 처음 포함되었다.

- 로컬 기본·안내형 CLI 온보딩
- 로컬 macOS 온보딩
- Linux 보조 앱에서 Control UI로 이어지는 온보딩 흐름

가져오기는 곧바로 파일을 복사하지 않는다. 먼저 후보를 감지해 미리 보여 주고, 사용자가 고른 에이전트의 목적지를 정한다. **원본 지문**은 검토한 파일의 SHA-256 요약값으로, 검토와 실제 적용 사이에 원본이 바뀌지 않았는지 확인한다. 목적지 충돌은 기본적으로 막고, 덮어쓰기를 명시적으로 선택한 경우에만 백업과 복구 기록을 만든다. 심볼릭 링크를 따라 예상 범위 밖의 파일까지 읽지도 않는다.

이 경계 덕분에 원본은 그대로 남고, 가져온 기억은 `memory/imports/` 아래에서 출처별로 구분된다. 반대로 원본 하네스의 전체 실행 환경은 재현하지 않는다. 다음 표는 이 **기억 전용 가져오기**가 옮기는 파일과 목적지만 좁혀 보여 준다. 설정·인증·스킬·플러그인까지 옮기는 전체 하네스 마이그레이션은 별개의 문제다.

| 원본 하네스 | 기억으로 인정하는 파일                                                                                     | OpenClaw 목적지                                                            |
| ----------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Claude Code | 발견된 자동 기억 디렉터리 아래의 일반 `.md` 파일을 파일 수와 탐색 항목 수의 상한 안에서 재귀적으로 찾는다. | `memory/imports/claude-code/<collection-slug>-<id>/…`                      |
| Codex       | `memories/MEMORY.md`, `memories/memory_summary.md`                                                         | `memory/imports/codex/MEMORY.md`, `memory/imports/codex/memory_summary.md` |
| Hermes      | `memories/MEMORY.md`, `memories/USER.md`                                                                   | `memory/imports/hermes/MEMORY.md`, `memory/imports/hermes/USER.md`         |

세 하네스는 다음 안전 계약을 공유한다.

- 설정과 인증은 원본에 남겨 둔다. 대화 보관 자료와 실행 기록도 옮기지 않는다. 캐시, 계획, 데이터베이스 같은 기계 상태 역시 가져오기 대상이 아니다.
- 각 항목에는 가져온 기억의 출처를 나타내는 `sourceType`, 원본 표지나 컬렉션, 상대 경로를 기록한다. 값은 각각 `claude-auto-memory`, `codex-memory`, `hermes-memory`다.
- 검토된 내장 흐름은 파일 바이트의 SHA-256 원본 지문을 적용 계획에 묶는다.
- 목적지 충돌은 기본으로 차단한다. 덮어쓰기를 명시적으로 선택하면 바뀌는 목적지만 항목별로 백업하고 복구 기록을 만든다.

Claude Code의 발견·복사 경계는 [자동 기억 계획](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/migrate-claude/memory.ts#L62-L181), Codex는 [기억 소스 발견](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/codex/src/migration/source-files.ts#L133-L185), Hermes는 [기억 계획](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/migrate-hermes/memory.ts#L43-L117)에 있다. 세 하네스 모두 공용 [안전한 메모리 복사](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/src/plugin-sdk/migration-runtime.ts#L245-L394)를 사용한다.

적용 직전의 원본이 미리 검토한 SHA-256과 다르면 가져오기를 멈추고 새 계획을 요구한다. 목적지를 덮어쓰는 도중 실패하면 준비해 둔 복구 기록과 백업으로 원래 목적지 파일을 복원하려 한다. 따라서 여기서 **되돌리기**는 원본 하네스 전체를 과거 상태로 되돌린다는 뜻이 아니다. OpenClaw 목적지에서 이번 가져오기가 바꾼 파일을 복구할 수 있게 한다는 뜻이다.

이 변화는 초기에 Markdown을 선택한 전략적 가치를 보여 준다. 기억은 불투명한 모델 쪽 프로필만이 아니라, 사용자가 살펴보고 하네스 사이에서 옮길 수 있는 개인 자산이 되었다.

> **변화의 동기.** 사용자 요청과 온보딩 관찰에서 나온 **명시적 증거**다. Issue #106215와 PR #106406은 Control UI에 Codex·Claude Code 기억을 검토해 가져올 공식 경로가 없음을 연결했고, PR #108977은 이미 있는 엔진을 CLI·macOS·Linux 첫 실행에서 발견할 수 없다는 공백과 Hermes 지원 부재를 직접 적었다. 설정 전체를 복제하지 않고 지문이 있는 기억 전용 계획·미리보기·백업·되돌리기를 택한 것은 사용자 자산만 옮기고 원본 하네스의 실행 상태와 새 런타임 경계를 섞지 않기 위해서다.

## 개인 에이전트에 보호된 대화 간 회상을 추가하다

1장은 이 기능의 현재 계약을 정지 화면으로 설명했다. 이 절은 같은 조건을 다시 새로운 규칙으로 제시하는 것이 아니라, 어떤 사용자 공백과 PR을 거쳐 그 계약이 생겼는지 시간순으로 기록한다.

가져오기는 서로 다른 하네스 사이의 연속성을 다뤘다. 같은 하네스 안에도 별도의 공백이 남아 있었다. 한 개인 에이전트가 비공개 채널을 바꾸면 앞선 대화를 활용하지 못했다. [Issue #99611](https://github.com/openclaw/openclaw/issues/99611)은 한 채널에서 알던 사실을 다른 채널에서는 활용하지 못하는 현상을 “표면 간 기억 상실”이라고 설명했다.

OpenClaw는 이를 해결하기 위해 대화 기록을 새 장기 기억으로 복사하거나 `MEMORY.md`로 승격하지 않았다. 대신 과거 대화를 검색 전용으로 인덱싱하고, Active Memory가 주 답변 전에 실행하는 제한된 회상에서만 사용하게 했다. 이때 **보호된 대화 간 회상**이란 다른 비공개 대화의 검색 결과를 곧바로 믿는 것이 아니라, 같은 에이전트의 다른 비공개 대화인지 결과마다 확인한 뒤에만 답변 컨텍스트에 넣는 기능을 뜻한다. [PR #100140](https://github.com/openclaw/openclaw/pull/100140)은 [`4b3ee5e7eb62`](https://github.com/openclaw/openclaw/commit/4b3ee5e7eb623368d367a5fc2fa3712bc8095f16)로 병합되어 이 동작을 `rememberAcrossConversations`로 추가했다.

이 권한 경계를 이해하려면 “누가 누구의 과거를 찾는가”를 다섯 종류의 정체성으로 나눠 보아야 한다.

| 판단 입력                                 | 뜻                                                                                                                 | 권한 검사에서 하는 일                                                                                                                                                              |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 현재 요청과 기준 대화(`anchorSessionKey`) | 사용자가 지금 답을 받을 비공개 대화다. Active Memory 작업자는 이 키에 정해진 접미사를 붙여 대신 검색할 수 있다.    | 기준 대화가 인식된 비공개 대화인지, 요청자가 기준 대화 자체이거나 허용된 Active Memory 작업자인지 먼저 확인한다.                                                                   |
| 에이전트 ID                               | 현재 요청과 후보 대화 기록을 소유한 OpenClaw 에이전트다.                                                           | 기준 대화와 후보가 같은 에이전트에 속해야 한다.                                                                                                                                    |
| 대화 정체성                               | `sessionId` 또는 같은 저장 대화 기록을 가리키는 파일 정체성이다.                                                   | 현재 대화와 같은 대화 기록은 다른 키로 보이더라도 제외한다.                                                                                                                        |
| 대화 유형                                 | 정식 세션 행의 `chatType`·`origin.chatType`과 세션 키가 나타내는 `direct`, `group`, `channel`, 내부 실행 유형이다. | 직접·비공개라고 확인되는 대화만 허용한다. 그룹·채널·공유 전역·내부 실행·유형 불명은 차단한다.                                                                                      |
| 참여자와 세션 별칭                        | 참여자는 채널의 발신자다. 세션 별칭은 하나의 저장 대화를 가리키는 여러 세션 키다.                                  | 결과별 검사에서 참여자 동일성을 직접 비교하지는 않는다. 개인형 설치의 기본값은 DM 격리 설정으로 판단한다. 같은 대화의 모든 별칭이 비공개여야 하며 하나라도 공유 유형이면 차단한다. |

여기서 **기준 대화**는 현재 답변을 보낼 대화이고, **후보 대화**는 과거 검색 결과가 나온 대화다. **세션 별칭**은 키가 달라도 같은 저장 대화를 가리키는 경우를 뜻한다. 한 별칭만 보고 비공개라고 판단하면 다른 별칭으로 공유된 같은 대화가 새어 나갈 수 있으므로, 모든 별칭을 함께 검사한다. 비공개임을 확정할 수 없으면 허용하지 않는 이 원칙을 **실패 시 차단**(fail-closed)이라고 한다.

`session.dmScope = main`의 `main`은 기본 활성화를 판단하는 DM 범위 값이다. 모든 `main` 세션을 자동으로 비공개라고 선언하는 표지는 아니다. **바인딩**(binding)은 채널·계정·상대 같은 입력을 에이전트와 세션 정책에 연결하는 설정이다. 바인딩 하나라도 별도의 DM 범위를 지정하면, OpenClaw는 이를 여러 사용자를 격리하는 신호로 보고 개인형 설치라는 자동 가정을 중단한다.

**Active Memory 작업자**는 주 모델을 대신해 답변 전에 검색만 수행하는 내부 보조 실행이다. 표의 `:active-memory:<12자리 16진수>` 접미사는 이 내부 실행이 어느 기준 대화를 대신하는지 식별하는 표지다. 사용자가 참여하는 별도 대화나 새 기억의 소유자를 뜻하지 않는다.

**샌드박스**는 호스트의 신뢰된 세션 권한을 직접 사용할 수 없도록 격리된 실행 환경이다. 보호된 대화 간 회상은 기준 대화와 요청자의 신뢰 관계를 확인해야 하므로 샌드박스 요청에는 열리지 않는다.

### 허용·차단 행렬

다음 행렬은 기능이 켜진 뒤에도 각 결과에 적용되는 계약이다. “허용”은 나머지 점검도 통과한다는 전제다. 기능을 자동으로 켤지는 다음 절에서 별도로 다룬다.

| 기준 또는 후보 상황                                            | 기준 대화로 사용                            | 과거 후보로 노출                       | 이유                                                                                     |
| -------------------------------------------------------------- | ------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------- |
| 직접 DM, 정식 `direct` 메타데이터, 모든 별칭이 비공개          | 허용                                        | 같은 에이전트의 **다른** 대화라면 허용 | 인식된 비공개 정체성이다.                                                                |
| 직접·비공개 주제 스레드                                        | `direct`로 분류되고 공유 별칭이 없으면 허용 | 같은 조건에서 허용                     | 스레드 접미사보다 저장된 대화 유형과 전체 별칭 판정이 우선한다.                          |

구현은 먼저 기준 대화가 비공개인지와 요청자가 신뢰된 주체인지 확인한다. 그런 다음 `source=sessions`인 각 검색 결과에 같은 에이전트인지, 현재 대화가 아닌지, 비공개 유형인지, 모든 별칭의 판정이 일치하는지를 차례로 검사한다. 세부 판정은 [세션 결과 가시성 검사](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/src/session-search-visibility.ts#L157-L375)에 있다.

### 기본 활성화와 결과 권한은 다른 결정이다

**기본 활성화**는 설정을 생략했을 때 기능을 자동으로 켤지 정하는 제품 선택이다. **결과 권한**은 검색에서 찾은 개별 대화를 이번 답변에 사용해도 되는지 판정하는 보안 경계다. 기능이 켜졌다는 사실만으로 검색 결과의 사용 권한까지 생기지는 않는다.

DM 범위 값 가운데 `per-peer`는 상대별, `per-channel-peer`는 채널·상대 조합별, `per-account-channel-peer`는 계정·채널·상대 조합별로 세션을 나눈다. 값이 세밀해질수록 여러 사용자의 직접 대화를 하나의 개인형 세션으로 간주해서는 안 된다는 신호가 된다.

| `rememberAcrossConversations` 설정 | 설치 형태 신호                                                                                     | 현재 `main`의 기본값 |
| ---------------------------------- | -------------------------------------------------------------------------------------------------- | -------------------- |
| 명시적 `true` 또는 `false`         | 어떤 DM 범위나 바인딩이 있어도 명시값이 우선                                                       | 명시값 사용          |
| 미설정                             | `session.dmScope`가 없거나 `main`이고, 어떤 바인딩도 별도 `session.dmScope`를 두지 않음            | 켬                   |
| 미설정                             | `per-peer`, `per-channel-peer`, `per-account-channel-peer`이거나 바인딩 하나라도 별도 DM 범위를 둠 | 끔                   |

설정을 명시하면 설치 형태와 관계없이 그 값이 우선한다. 설정하지 않았을 때는 전역 DM 범위가 없거나 `main`이고, 어떤 바인딩에도 별도 DM 범위가 없는 개인형 설치에서만 기본으로 켜진다. `per-peer`, `per-channel-peer`, `per-account-channel-peer`처럼 상대나 채널별 격리가 설정되었거나 바인딩이 별도 DM 범위를 가지면 기본값은 꺼진다. 계산 규칙은 [메모리 호스트 설정](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/packages/memory-host-sdk/src/host/config-utils.ts#L177-L199)에 있다.

이 기본값은 대화 기록을 검색 대상으로 준비할지만 정한다. 기능이 켜져 있어도 그룹·다른 에이전트·현재 대화·비공개와 공유가 섞인 별칭·샌드박스 결과는 계속 차단된다.

검색 실행은 [1장의 정식 권한 순서](01-current-architecture.md#canonical-session-authorization)를 따른다. 먼저 백엔드가 세션 소스에서 후보를 찾고, 그 뒤 각 후보에 같은 에이전트·비공개 대화 등의 가시성 검사를 적용한다. 검사를 통과한 결과만 인용, 답변 노출, Dreaming 회상 추적으로 넘어간다. 반면 정확 대화 검색 도구 `sessions_search`는 보이는 결과를 먼저 모은 뒤 최종 개수 상한을 적용한다. 두 검색은 권한을 지키지만 결과 상한을 채우는 순서가 다르다.

이 권한 검사와 격리 조건을 전제로 [PR #110597](https://github.com/openclaw/openclaw/pull/110597)은 [`01a9e1d398fd`](https://github.com/openclaw/openclaw/commit/01a9e1d398fd12970e936335811f13ee913e29c1)으로 병합되어 개인형 설치에서 기능을 조건부 기본값으로 켰다.

2026-07-18의 아키텍처 고정본에서 두 대화 간 회상 커밋은 모두 출시 태그 밖에 있었다. 이후 [`4b3ee5e7eb62`](https://github.com/openclaw/openclaw/commit/4b3ee5e7eb623368d367a5fc2fa3712bc8095f16)는 `v2026.7.2-beta.3`, 조건부 기본값을 더한 [`01a9e1d398fd`](https://github.com/openclaw/openclaw/commit/01a9e1d398fd12970e936335811f13ee913e29c1)는 `v2026.7.2-beta.4`에 처음 포함되었다. **마지막 출시 상태 검증: 2026-07-26.**

> **변화의 동기.** 사용자 보고와 호환성에 민감한 유지보수자 요청에서 나온 **명시적 증거**다. Issue #99611을 닫은 PR #100140은 같은 개인 에이전트가 비공개 표면마다 컨텍스트를 잃는 문제를 직접 해결했고, 후속 PR #110597은 개인형 설치에서만 그 보호된 경로를 조건부 기본값으로 열었다. 대화 기록을 새 영속 기억으로 복사하지 않고 회상 전용 인덱스와 검색 후 가시성 검사를 택한 명시적 이유는 연속성을 주되 현재 대화·공유 표면·다른 에이전트의 자료가 노출되지 않게 하는 데 있다. 차단된 적중이 Dreaming 회상 신호가 되지 않는다는 점은 현재 코드의 실행 순서로 확인되는 **현재 계약**이지, PR이 별도로 밝힌 역사적 동기는 아니다.

## 대안 저장소의 소유권을 바로잡다

대화 기록의 권한만 엄격해져도 다른 메모리 저장소가 에이전트 사이에서 섞이면 경계는 완성되지 않는다. 그래서 같은 시기에 Memory Wiki와 LanceDB의 저장 소유권도 정리했다.

Memory Wiki의 **볼트**는 위키의 원본과 파생 페이지를 한데 관리하는 저장 영역이다. 기존 구성에서는 검색, 회상, 가져오기, 프롬프트 주입에 걸쳐 여러 에이전트가 하나의 전역 볼트를 공유할 수 있었다. [PR #103349](https://github.com/openclaw/openclaw/pull/103349)은 [`98b8c8c4ae29`](https://github.com/openclaw/openclaw/commit/98b8c8c4ae298c55ad42a99020ee689b1c3ed1c1)으로 병합되어 선택적인 에이전트별 볼트 격리를 추가했다.

기존 전역 볼트는 호환성을 위해 기본값으로 남았다. 대신 에이전트 범위를 선택했는데 정체성을 확인할 수 없으면 실패 시 차단한다. 이미 여러 에이전트의 자료가 섞인 볼트도 시스템이 소유자를 추측해 자동 분할하지 않는다.

> **변화의 동기.** 여러 에이전트가 지식 저장소를 공유한 실제 소유권 문제에서 나온 **명시적 증거**다. PR #103349은 지원 에이전트와 마케팅 에이전트가 같은 볼트를 검색·가져오기·프롬프트 주입에 쓸 수 있던 문제를 직접 적었다. 새 설치 전체를 즉시 분할하지 않고 선택적 에이전트별 볼트를 추가하며 전역 볼트를 호환 기본값으로 둔 것은, 새 격리 계약을 제공하되 이미 섞인 자료의 소유자를 추측해 자동 이동하지 않기 위해서다.

벡터 데이터베이스를 사용하는 LanceDB 플러그인도 이전에는 하나의 공유 저장소에서 여러 에이전트가 기억을 나열하고 읽고 지우고 자동 회상할 수 있었다. [Issue #103590](https://github.com/openclaw/openclaw/issues/103590)은 `v2026.6.11` 설치에서 `main` 에이전트의 비공개 기억이 다른 에이전트의 프롬프트에 자동 회상되는 환경과 재현 절차를 기록했다. 이 이슈를 닫은 [PR #103799](https://github.com/openclaw/openclaw/pull/103799)은 [`6390edec25e2`](https://github.com/openclaw/openclaw/commit/6390edec25e2614962a424f555ca7616eca8b340)로 2026-07-16에 병합되어 각 레코드에 소유 에이전트를 기록하고, 질의를 실행하는 에이전트의 자격과 맞는 레코드만 사용하게 했다.

기존 공유 테이블에는 각 행의 실제 소유자를 입증할 정보가 없다. 따라서 `doctor`는 과거 행의 소유자를 추측하지 않는다. 운영자가 설정한 기본 에이전트에 모든 과거 행을 명시적으로 일괄 할당하고, 그 뒤 스키마와 행 수를 검증한다. 마이그레이션 전에는 이전 공유 테이블의 읽기를 차단한다. 소유권을 프롬프트의 관례가 아니라 저장된 정체성과 질의 자격으로 강제한 것이다.

> **변화의 동기.** 사용자에게 관측된 에이전트 간 노출 사건과 격리 결함에서 나온 **명시적 증거**다. Issue #103590의 실제 재현과 이를 닫은 PR #103799가 원인과 수리를 직접 잇는다. 모든 저장·검색·삭제 경로에 정규화된 소유 에이전트 ID를 요구한 것은 프롬프트나 자동 검색 토글이 아니라 저장 행과 질의 자격 자체에서 경계를 강제하기 위해서다. 과거 행에 신뢰할 수 있는 소유자가 없다는 한계 때문에 마이그레이션은 기본 에이전트로의 명시적 귀속을 택했으며, 이 선택은 소유자를 사후에 증명한 것과는 다르다.

소유권이 올바르더라도 파일 쓰기가 중간에 끊기면 사용자의 장기 기억이 손상될 수 있다. 같은 7월 개발 구간에서 [`0317d7e62801`](https://github.com/openclaw/openclaw/commit/0317d7e628010d6e51a2a09f9d7e9af677216981)은 Dreaming이 승격 내용을 `MEMORY.md`에 원자적으로 쓰도록 바꿨다. **원자적 쓰기**는 새 내용을 별도 임시 파일에 완성한 뒤 한 번에 교체해, 중단되더라도 절반만 기록된 파일을 남기지 않는 방식이다. 이어 [`48866bbc405f`](https://github.com/openclaw/openclaw/commit/48866bbc405f09f1a924e87ede89a82cbd391666)은 `MEMORY.md`가 심볼릭 링크일 때 링크가 가리키는 실제 파일에 쓰는 기존 동작을 보존했다.

이 두 변경으로 파일 쓰기는 중단에 견디면서 사용자의 파일 배치도 존중하게 되었다. 다만 좋은 후보를 고르는 **승격 자격**과, 선택한 내용을 손상 없이 기록하는 **쓰기 안전성**은 여전히 별개의 문제다.

> **변화의 동기.** 구체적으로 입증된 잠재 파일 쓰기 실패 경로에서 나온 **명시적 증거**다. PR #108397은 예약된 승격 중 `fs.writeFile`이 일부만 기록하면 `MEMORY.md`의 뒤쪽 장기 기억이 영구 손실될 수 있음을 코드 경로로 설명했지만, 실제 데이터 손실 사건이 보고되었다고 주장하지는 않는다. 후속 #108921은 원자적 이름 바꾸기가 심볼릭 링크 대상을 바꾸는 호환 문제를 고쳤다. 임시 파일·동기화·원자적 교체를 쓰되 링크의 쓰기 가능한 실제 대상을 보존한 것은 중단 내구성과 사용자의 파일 시스템 계약을 함께 지키기 위해서다.

2026-07-18 기준 `main`에는 당시 태그에 들지 않은 상태 통합 세 가지가 더 있었다. **조정 상태**는 여러 작업이 동시에 같은 자원을 바꾸지 않도록 순서를 정하는 정보이고, **컴파일 캐시**는 원본에서 다시 만들 수 있는 기계용 스냅샷이다. **런타임 저널**은 운영·감사 사건을 시간순으로 남긴 기록이다. 셋 다 SQLite로 옮겼지만, 사라졌을 때의 영향은 서로 다르다.

**[QMD 조정 상태](https://github.com/openclaw/openclaw/commit/e873a7f955f8b354b8d0d3cb82da1da3dc5b161b).** QMD 관리자와 컬렉션 제어기는 에이전트별 갱신·임베딩 작업을 시작할 때 유효 시간이 제한된 잠금인 임대를 쓰고 읽으며, `doctor`는 퇴역한 파일 잠금을 정리한다. 여러 프로세스의 쓰기를 직렬화하고 에이전트 사이의 임베딩 동시성을 제한하려면 원자적 임대와 명시적 소유자가 필요하므로 파일 잠금보다 SQLite가 맞다. 이 상태를 잃어도 사용자 Markdown이나 QMD 자체 인덱스가 사라지지는 않는다. 조정 임대를 다시 얻고 필요한 동기화를 해야 하며, 세션에서 유래한 결과의 정체성 매핑을 확인할 수 없으면 해당 결과는 실패 시 차단된다. 최초 포함 태그는 `v2026.7.2-beta.3`이다.

**[Memory Wiki 컴파일 캐시](https://github.com/openclaw/openclaw/commit/d8f2645c2cedbe1f8986a01974c5f6e45dbbf652).** 위키 컴파일러는 볼트의 페이지·주장을 기계용 스냅샷으로 저장하고, 비동기 프롬프트 준비와 검색·조회·보고가 이를 읽는다. 원본 볼트 버전과 현재 게시본 버전에 묶인 수명주기 소유 캐시이므로, 프롬프트 조립 중 Markdown을 다시 훑지 않고 원자적으로 게시·격리하기에 플러그인 SQLite가 맞다. 캐시를 잃어도 사용자가 관리하는 의미 정보는 로컬 볼트에 남으며 다음 컴파일에서 다시 만들 수 있다. 오래된 버전의 캐시는 마이그레이션하지 않는다. 최초 포함 태그는 `v2026.7.2-beta.3`이다.

**[세션 외 런타임 저널](https://github.com/openclaw/openclaw/commit/9d97e10efe08c3b5e3043da19b80883e933e26be).** 메모리 호스트 이벤트, 설정 감사, 외부 에이전트 실행의 상위 스트림 이벤트 같은 런타임 생산자가 쓰고 진단·감사·`doctor`·공개 내보내기 경로가 읽는다. 여러 JSONL 파일에 흩어진 순서·보존 기간·마이그레이션을 한 트랜잭션 소유자 아래 두기 위해 SQLite가 권위 저장소가 되었다. 이 상태를 잃어도 `MEMORY.md`의 의미 정보는 남지만, 아직 내보내지 않은 운영·감사 이력은 단순 재인덱싱으로 복구되지 않는다. 메모리 이벤트의 제한된 공개 내보내기는 별도 산출물로 다시 만들 수 있다. 최초 포함 태그는 `v2026.7.2-beta.4`다.

마지막 변경은 SQLite를 권위 있는 원본으로 삼으면서도, 외부에서 읽을 수 있도록 범위와 이름이 정해진 `memory/events/.../memory-host-events.jsonl` 내보내기를 유지했다. 세 변경은 각각 `v2026.7.2-beta.3` 또는 `v2026.7.2-beta.4`에 출시되었다. 이들은 Markdown 의미 메모리를 데이터베이스로 대체한 것이 아니라, 조정·캐시·운영 기록처럼 기계가 관리하는 상태의 소유자를 SQLite로 모은 변화다. **마지막 출시 상태 검증: 2026-07-26.**

> **변화의 동기.** 데이터베이스 우선 소유권 정리에 대한 유지보수자 요청에서 나온 **명시적 증거**다. 세 PR은 QMD 잠금 보조 파일의 정체·경쟁, Memory Wiki 프롬프트 경로의 낡은 캐시 소유자, 여러 JSONL 런타임 저널의 분산된 수명주기를 각각 직접 설명했다. 그래서 조정·캐시·권위 저널은 SQLite 소유 상태로 모으고, 외부 계약인 제한된 이벤트 내보내기만 이름 있는 산출물로 남겼다. 이는 Markdown 의미 메모리를 SQLite로 대체한 변화가 아니다.

## 다음 장으로

7월까지 OpenClaw는 사람이 편집하는 기억, 검색을 위한 파생 인덱스, 정식 대화 기록, 플러그인별 대안 저장소의 책임을 더 뚜렷하게 나눴다. 의미가 비슷한 기억을 찾는 검색과 정확한 대화 문구를 찾는 검색을 구분했고, 사용자가 기다리는 조회와 오래 걸리는 복구도 분리했다. 대화나 기억의 소유자를 확인할 수 없을 때는 추측하지 않고 실패 시 차단하도록 했다.

보호된 대화 간 회상과 일부 상태 통합은 2026-07-18의 아키텍처 고정본에서는 아직 `main`에만 있었지만, 2026-07-26의 별도 출시 상태 재검증에서는 `v2026.7.2-beta.3`과 `v2026.7.2-beta.4`에 단계적으로 포함된 것으로 확인되었다. 따라서 아키텍처 기준일의 코드 상태와 이후 사용자가 받은 출시 상태를 같은 시점의 사실로 읽어서는 안 된다.

다음 장은 연대기에서 한 걸음 물러난다. 2025년 제안부터 2026년 7월까지 반복해서 등장한 문제를 몇 가지 설계 전환으로 묶고, 초기의 큰 구상을 실제로 구현된 더 작은 경계들과 비교해 재검토한다.
