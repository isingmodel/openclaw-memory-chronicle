# 3장. 2026년 1월과 2월: 보존에서 검색으로

파일 관례만으로는 맥락이 사라지는 시점을 통제할 수 없었다. 모델이 중요한 내용을 파일에 옮기기 전에 대화 압축이 일어날 수 있었고, 기록이 쌓이면 관련 구절을 찾기 어려웠다. 다른 메모리 구현을 선택하더라도 코어가 기존 구현의 작업 흐름을 계속 가정할 위험도 있었다.

2026년 1월과 2월의 작업은 이 세 문제를 런타임과 검색 계층이 책임지는 제품 기능으로 바꾸었다. 런타임은 맥락이 줄어들기 전에 마지막 저장 기회를 열었고, 내장 검색은 늘어난 기록에서 필요한 구절을 찾게 했다. 이어 대화 기록까지 검색 대상에 들어왔으며, 배타적 플러그인 슬롯과 관리형 QMD가 구현의 소유권을 나누었다. 그 대가로 무엇을 어떤 품질로 수집할지, 외부 검색 프로세스를 어떻게 관리할지, 검색 결과를 어떤 기준으로 정렬할지라는 새 문제가 생겼다.

## 맥락 손실이 수명주기 수집을 이끌다

첫 문제는 맥락을 압축할 때가 되면 에이전트가 기록에 쓸 토큰 공간조차 남지 않는다는 점이었다. **토큰**은 모델이 텍스트 양을 세는 기본 단위다. 여기서 **압축**은 길어진 대화의 오래된 부분을 요약해 모델에 넣을 맥락을 줄이는 처리이고, **메모리 플러시**는 그 직전에 별도 에이전트 실행을 열어 오래 남길 내용을 파일에 쓰게 하는 절차다.

런타임은 먼저 압축용 토큰 여유분을 예약했다. 이어진 변경은 사용자에게 답을 보내지 않는 조용한 압축 전 플러시를 추가해, 압축 주기마다 한 번씩 마지막 저장 기회를 보장했다. 남길 내용이 없을 때 쓰는 `NO_REPLY`는 이 실행에서 사용자에게 별도 메시지를 보내지 말라는 제어 응답이었다. 각각의 근거는 [`a3747b1ee3ae`](https://github.com/openclaw/openclaw/commit/a3747b1ee3ae3d1bcdb29a7306daf48c7236d0bf)와 [`7dbb21be8e57`](https://github.com/openclaw/openclaw/commit/7dbb21be8e5778deeb63ed3db9abc243ffa83cac)이며, 후자는 `v2026.1.11`에 처음 포함되었다.

> **변화의 동기.** 실제 압력은 압축 직전에 토큰 여유가 사라져 기록 기회까지 잃는 문제였다. 동기 출처는 압축 여유분과 플러시를 잇달아 추가한 장애 예방 커밋이며, 증거 강도는 **코드에서 추론**이다. 런타임이 여유분과 주기당 한 번의 조용한 실행을 보장하는 형태를 골라 모델의 자발성에만 기대지 않았다.

얻은 것은 “**에이전트가 기억해야 한다**”에서 “**런타임이 기억할 수 있는 마지막 안전한 기회를 만든다**”로의 전환이었다.

동시에 자연어 프롬프트를 쓰기 규약으로 사용할 때의 위험도 드러났다. [Issue #6877](https://github.com/openclaw/openclaw/issues/6877)은 프롬프트가 메모리를 저장하라고만 하고 기존 파일을 읽어 덧붙이라고 하지 않아, 에이전트가 기존 일일 파일을 덮어쓴 사례를 보여 주었다. [PR #6878](https://github.com/openclaw/openclaw/pull/6878)이 프롬프트를 고쳤다. 증거는 가상의 예외 상황이 아니라 구체적인 파일 이력의 데이터 손실이었다.

> **변화의 동기.** 실제 압력은 이미 기록된 일일 파일이 플러시 때 통째로 덮이는 회귀였다. 동기 출처는 사용자 장애 보고 Issue #6877과 이를 직접 닫은 PR #6878이고, 증거 강도는 **명시적**이다. 기존 파일을 먼저 읽고 덧붙이라고 정확한 모델·도구 경계에 적는 형태를 골라 관측된 손실 원인을 바로 막았다.

여기서 오래 남는 설계 규칙이 나온다. 기존 내용을 지우면 안 된다는 **불변 조건**, 즉 실행 전후에 반드시 지켜져야 할 규칙은 가능하면 파일 쓰기 방식 자체로 강제해야 한다. 구조적으로 막을 수 없다면 모델이 파일 도구를 호출하는 바로 그 지점에 규칙을 명시하고 회귀 테스트로 지켜야 한다.

> **예시 — 합성 사례:** “오늘의 중요한 내용을 저장하라”는 지시만 있으면 모델이 `memory/2026-01-10.md`를 새로 쓰는 동작으로 해석할 수 있다. “기존 파일을 먼저 읽고 보존한 채 덧붙여라”라는 경계 조건이 있어야 누적 기록 계약이 드러난다. 실제 손실 근거는 위 Issue #6877이고, 이 문장은 메커니즘을 단순화한 가상 예시다.

## 검색이 제품 기능이 되다

파일이 늘어나자 오늘과 어제의 기록만 읽는 방식으로는 관련 구절을 빠르게 찾기 어려웠다. **어휘 검색**은 질의와 문서에 실제로 겹치는 단어를 찾고, **의미 검색**은 문장을 수치 벡터로 바꿔 표현이 달라도 뜻이 가까운 구절을 찾는다. 둘의 차이는 한 장면으로 보면 분명하다.

> **예시 — 합성 사례:** 기록에 “새 코드명은 `ORBIT-10`”이라고 적혀 있을 때 질의도 `ORBIT-10`이라면, 정확한 문자와 희귀 식별자를 찾는 어휘 검색이 가장 직접적이다. 반대로 기록이 “사용자는 배포 전에 변경 요약을 원한다”인데 질의가 “릴리스 직전에 무엇을 알려 줘야 하지?”라면 겹치는 단어가 적어도 뜻이 가까운 구절을 찾는 벡터 검색이 유리할 수 있다. 혼합 검색은 둘 중 하나를 승자로 고정하지 않고, 정확한 단어 신호와 바꿔 말한 의미 신호를 함께 순위에 반영한다. 이는 검색 차이를 설명하는 가상 예시이며 실제 품질 측정 결과가 아니다.

최초의 내장 벡터 메모리 검색은 파일 회상을 에이전트별 색인과 모델 도구를 갖춘 제품 기능으로 바꾸었다. 여기서 **색인**은 원문을 대신하는 저장소가 아니라, 관련 구절을 빨리 찾도록 원문에서 다시 만들 수 있는 검색용 구조다. [`bf11a42c372b`](https://github.com/openclaw/openclaw/commit/bf11a42c372b72cbe030c05b80e18f42dd9fdd59)은 `v2026.1.12`에 처음 포함되었고 다음 구성을 제공했다.

- 에이전트별 SQLite 색인
- OpenAI 또는 로컬 임베딩
- 관련 구절을 찾는 `memory_search`와 원문의 특정 부분을 읽는 `memory_get` 도구
- 명령줄 관리 기능, 파일 변경 감시기, 잦은 갱신을 한데 모아 처리하는 지연 동기화
- 원문을 나누는 400토큰 크기의 청크와 문맥 단절을 줄이는 80토큰 겹침
- 최대 결과 6개와 최소 관련성 점수의 기본값

검색을 빠르고 재사용 가능하게 만들기 위해 SQLite에서 벡터 유사도를 계산하는 `sqlite-vec` 가속과, 이미 계산한 벡터를 재사용하는 임베딩 캐시가 뒤따랐다. 근거는 [`5a08471dcd1b`](https://github.com/openclaw/openclaw/commit/5a08471dcd1b92e87d4c7d87dbd0b7b3a5723784)과 [`0fb2777c6de9`](https://github.com/openclaw/openclaw/commit/0fb2777c6de919673b62dad9208dcb47784895b9)이다.

의미 신호만으로는 코드명이나 고유명사처럼 정확히 일치해야 할 단어를 놓칠 수 있었다. 그래서 벡터 유사도와 BM25/FTS 점수를 결합했다. **FTS**는 문서의 단어를 색인하는 전체 텍스트 검색이고, **BM25**는 질의 단어의 빈도와 희소성을 이용해 결과의 관련성을 매기는 대표적인 순위 공식이다. [`ccb30665f7c5`](https://github.com/openclaw/openclaw/commit/ccb30665f7c5e2e386aa5db28f4c8c461ca60773)은 `v2026.1.20`에 처음 포함되었고, 지금도 남아 있는 혼합 가중치의 기원이 되었다.

> **변화의 동기.** 실제 목표는 늘어나는 파일에서 관련 구절을 모델이 호출할 수 있는 속도와 형태로 찾고, 의미 유사도만으로 놓치는 정확한 단어도 살리는 일이었다. 동기 출처는 벡터 검색·가속·캐시·혼합 검색으로 이어진 구현 묶음이며, 증거 강도는 **코드에서 추론**이다. 에이전트별 SQLite 색인과 벡터·BM25/FTS 결합을 골라 로컬 상태 소유권과 두 검색 신호를 함께 유지했다.

이 시기에는 여러 문서를 원격 서비스에 한꺼번에 보내 벡터로 바꾸는 일괄 임베딩도 등장했다. 이어 [`757522fb48ae`](https://github.com/openclaw/openclaw/commit/757522fb48aedbbd2d3c6292cb5b26d2993551f3)이 비동기 원격 일괄 방식을 선택 기능으로 바꿨다. [PR #13069](https://github.com/openclaw/openclaw/pull/13069)은 이유를 명시한다. 보통 크기의 메모리 재색인도 대규모 오프라인 작업용 비동기 서비스의 작업 순서를 기다리고 있었던 반면, 요청 안에서 결과를 돌려주는 동기식 일괄 처리 엔드포인트는 보고된 **코퍼스**, 즉 검색 대상으로 묶은 문서 집합을 1분 안에 처리했다. 높은 대량 처리량만 보고 긴 대기 시간과 별도의 실패 양상을 모든 사용자의 기본값으로 삼을 이유는 없었다.

> **변화의 동기.** 실제 압력은 약 30개 파일·900개 청크 규모에서도 비동기 작업이 15분 넘게 걸리던 운영 측정이었다. 동기 출처는 PR #13069의 측정과 비교이며, 증거 강도는 **명시적**이다. 같은 코퍼스를 1분 안에 처리한 동기식 일괄 엔드포인트를 기본으로 두고, 대규모 오프라인 처리만 원격 일괄 기능을 선택하게 했다.

구현 순서는 앞선 설계 제안과 달랐다. 제안은 로컬 어휘 회상을 먼저 두었지만, 실제 제품은 의미 회상을 먼저 출시하고 뒤이어 FTS와 혼합 검색을 더했다. 후속 작업은 임베딩 없이도 작동하는 견고한 FTS 경로를 만들었다. [`65aedac20e53`](https://github.com/openclaw/openclaw/commit/65aedac20e535bea40a74a5f96f988738a5a8307)은 임베딩 공급자를 사용할 수 없을 때 FTS로 검색할 수 있게 했다. 3월의 공급자 `none` 작업은 이를 임시 대체 동작이 아니라 명시적인 FTS 전용 방식으로 굳혔다.

> **변화의 동기.** 실제 압력은 임베딩 API 키를 따로 제공하지 않은 OAuth 로그인 사용자의 `memory_search`가 비활성화되던 사용자 보고였다. 동기 출처는 [Issue #17725](https://github.com/openclaw/openclaw/issues/17725)와 이를 직접 고친 [`65aedac20e53`](https://github.com/openclaw/openclaw/commit/65aedac20e535bea40a74a5f96f988738a5a8307)이며, 증거 강도는 **명시적**이다. 벡터 검색이 되는 것처럼 가장하지 않고 FTS 전용 대체 경로를 별도의 정상 검색 방식으로 열었으며, 3월에는 이를 명시적 지원 방식으로 굳혔다.

이 단계에서 메모리 검색은 하나의 기법이 아니라 세 층으로 이해해야 한다. Markdown은 사람이 읽고 고치는 원본이고, SQLite·FTS·벡터 데이터는 다시 만들 수 있는 색인이며, `memory_search`와 `memory_get`은 모델이 그 색인을 거쳐 원문에 접근하는 도구다. 이 구분은 뒤에서 검색 엔진이 바뀌더라도 원본과 도구 계약을 따로 판단하는 기준이 된다.

## 두 가지 수집 모델이 나타나다

압축만이 대화의 맥락이 끊기는 경계는 아니었다. `/new`나 `/reset`으로 새 대화를 시작할 때도 방금 전 대화의 흔적을 남길 방법이 필요했다. **수명주기 훅**은 새 세션 시작이나 재설정처럼 정해진 사건이 일어날 때 실행되는 연결 지점이다. 내부 훅과 `/new`용 번들 세션 메모리 훅은 대화 끝부분의 제한된 범위를 읽고, 내용을 나타내는 짧은 이름인 슬러그를 붙여 일일 기록으로 추출했다. [`faba508fe0ae`](https://github.com/openclaw/openclaw/commit/faba508fe0ae4dd4de453f4eccb62e452950880d)는 `v2026.1.16-2`에 처음 포함되었고, [`d583399c9240`](https://github.com/openclaw/openclaw/commit/d583399c92401f64261da28a6531f72f052e96d8)은 이를 `/reset`으로 확장해 `v2026.2.21-beta.1`에 처음 포함시켰다.

> **변화의 동기.** 실제 압력은 압축이 아닌 `/new`와 `/reset`에서도 직전 대화의 증거가 사라지는 일이었다. 동기 출처는 내부 훅과 재설정 지원을 확장한 구현 커밋이며, 증거 강도는 **코드에서 추론**이다. 별도 모델 실행보다 제한된 대화 꼬리를 일일 기록으로 남기는 기계적 수집을 골라 수명주기 경계에서 최소 증거를 보존했다.

이렇게 두 가지 수집 모델이 갈렸다.

| 수집 모델               | 실행 시점                  | 남기는 방식                                       | 얻는 것과 한계                                                             |
| ----------------------- | -------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------- |
| 기계적인 대화 기록 수집 | `/new`, `/reset` 같은 경계 | 대화 끝부분을 정해진 규칙대로 일일 기록에 옮긴다. | 별도 모델 실행 없이 증거를 보존하지만 중요도를 판단하거나 정제하지 않는다. |
| 에이전트형 선별         | 압축 직전                  | 모델이 오래 유지할 내용을 판단해 기록한다.        | 의미 있는 요약을 만들 수 있지만 모델 실행과 올바른 쓰기 규약이 필요하다.   |

이 차이는 지금도 중요하다. [Issue #45608](https://github.com/openclaw/openclaw/issues/45608)은 지금도 열려 있다. 재설정·새 세션 수명주기에는 압축과 같은 에이전트형 정제 기회가 없기 때문이다. 대화 기록의 꼬리는 증거를 보존할 수 있어도 좋은 장기 메모리를 만들지는 못한다.

> **변화의 동기.** Issue #45608이 명시한 실제 목표는 재설정 때도 에이전트가 무엇을 남길지 선별할 기회를 주는 것이다. 다만 이 이슈는 앞선 기계적 수집 커밋의 직접 원인이 아니라 남은 비대칭을 설명하는 자료이므로, 증거 강도는 **맥락적이며 직접 인과는 입증되지 않음**이다. 기존 구현이 값싼 증거 보존을 택한 이유와 좋은 장기 메모리까지 만들지 못하는 한계를 구분해야 한다.

수집과 별개로, 대화 기록 자체를 검색하는 첫 통합 실험도 `memory_search`에 들어왔다. [`0e49dca53c3b`](https://github.com/openclaw/openclaw/commit/0e49dca53c3be33a40565f653e38bd966181b639)은 앞선 셸 기반 수동 검색 명령인 `session-logs`와 기능상 대응하지만, 그 불편이 이 커밋을 직접 촉발했다는 기록은 없다. 새 구현은 대화 이력을 검색 코퍼스로 삼았다. 다만 어디에 저장하고 어떤 대화와 에이전트의 기록으로 식별하며 누가 볼 수 있고 어떤 결과를 먼저 보여 줄지에 관한 계약이 계속 변하고 있었으므로, 별도 실험 기능으로 남았다.

> **변화의 동기.** 구현에서 확인되는 목표는 대화 이력을 `memory_search`의 실험 코퍼스로 만드는 일이었고, 증거 강도는 **코드에서 추론**이다. 앞선 `session-logs`와는 기능상 대응하지만 직접 인과는 입증되지 않았다. 기존 검색 도구를 재사용하되 저장소·정체성·권한 계약이 안정될 때까지 별도 실험 소스로 두었다.

## 메모리가 배타적 플러그인 기능이 되다

Markdown 중심 구현과 벡터 데이터베이스 중심 구현은 원본의 형태뿐 아니라 언제 무엇을 수집하고 회상하는지도 달랐다. 두 구현을 동시에 주 메모리로 취급하면 어느 쪽이 기록과 회상을 책임지는지 모호해진다. 이를 막기 위해 **배타적 메모리 플러그인 슬롯**, 즉 메모리 역할을 한 번에 한 플러그인에만 맡기는 선택 지점을 만들었다. `memory-core`가 기본 플러그인이 되었고, `none`을 선택하면 주 메모리 플러그인을 사용하지 않는다는 설정도 문서화했다. 이 선택은 [`9fd9f4c8962e`](https://github.com/openclaw/openclaw/commit/9fd9f4c8962eb2f783db791cc0a62e290183cc77)에 담겨 `v2026.1.20`에 처음 포함되었다.

그러나 첫 설정 정규화, 즉 여러 입력 형태를 런타임이 읽는 한 가지 형태로 바꾸는 과정은 `none`에서 해석된 `null`을 실수로 다시 `memory-core`로 바꿨다. [`c4c01089ab9b`](https://github.com/openclaw/openclaw/commit/c4c01089ab9b8c8f3f23286859a3fadf7445bd4a)은 값을 지정하지 않은 상태와 명시적으로 비활성화한 상태를 구별해 실제로 끌 수 있게 했고, `v2026.1.23`에 처음 포함되었다. [`bb8f08734a12`](https://github.com/openclaw/openclaw/commit/bb8f08734a12f17d86360fa64aa8ba8673157989)은 내장 구현을 워크스페이스 플러그인으로 묶었다.

> **변화의 동기.** 한 플러그인만 주 메모리를 소유하게 한 초기 경계는 커밋 구조에서 **코드로 추론**한다. 반면 명시적 `none`이 다시 `memory-core`로 바뀌던 정규화 회귀와 그 수정은 [`c4c01089ab9b`](https://github.com/openclaw/openclaw/commit/c4c01089ab9b8c8f3f23286859a3fadf7445bd4a)가 직접 밝혀 **명시적 증거**다. 미설정과 명시적 비활성화를 구분해 선택과 비활성화의 뜻을 보존했다.

거의 같은 시기에 수명주기 자동 수집과 자동 회상을 갖춘 LanceDB 플러그인이 워크스페이스 Markdown과 다른 선택지를 보여 주었다. 추출한 메모리 항목을 벡터 데이터베이스에 저장한 근거는 [`ebfeb7a6bf53`](https://github.com/openclaw/openclaw/commit/ebfeb7a6bf533b733d2a08a527dc77f4ae793900)이다. 얻은 것은 뜻이 비슷한 기억을 찾는 대안 저장소였지만, [Issue #25202](https://github.com/openclaw/openclaw/issues/25202)는 나중에 자동 회상이 없으면 수집 자체도 작동하지 않는 것처럼 느껴진다고 보고했다. **내용을 오래 저장하는 것만으로는 충분하지 않다. 관련 내용이 다음 답변을 만드는 맥락에 안정적으로 돌아와야 사용자가 메모리 기능을 체감할 수 있다.**

외부 기록은 이 플러그인 경계가 만들어진 과정을 이례적으로 분명하게 보여 준다. [PR #808](https://github.com/openclaw/openclaw/pull/808)은 대화 시작과 종료에 자연스럽게 연결되는 회상과 수집을 요청했다. 유지관리자는 메모리 플러그인 하나만 이 기능을 소유해야 한다고 답하고 새 `9fd9f4c` 슬롯을 가리켰다. [PR #1149](https://github.com/openclaw/openclaw/pull/1149)은 그 결과로 생긴 플러그인 개발 인터페이스인 SDK를 바탕으로 LanceDB 설계를 다시 구현했다. 이 경우에는 외부 구현 요청이 코어의 확장 지점을 직접 빚었다는 연결 근거가 있다.

> **변화의 동기.** 실제 목표는 대화 시작 전 자동 회상과 종료 후 자동 수집을 지원하되, 기존 메모리 구현과 소유권이 충돌하지 않게 하는 일이었다. 동기 출처는 외부 구현 요청 PR #808, 유지관리자 답변, 이를 새 SDK를 바탕으로 다시 구현한 PR #1149이며, 증거 강도는 **명시적**이다. 그래서 LanceDB를 코어에 섞지 않고 배타적 플러그인 슬롯과 수명주기 훅을 통해 연결했다.

LanceDB 자동 수집의 초기 기본값은 켜짐이었다. [`ed7d83bcfc7f`](https://github.com/openclaw/openclaw/commit/ed7d83bcfc7ff0b1abd139ec035af577468a9190)은 자동 회상은 기본으로 유지하되 자동 수집은 사용자가 명시적으로 켜야 하는 기능으로 바꾸었고, `v2026.2.14`에 처음 포함되었다. 읽기는 이번 답변의 맥락에 한정해 결과를 버릴 수 있지만, 수집은 추출한 내용을 다음 세션에도 남는 사용자 상태에 기록한다. 두 기본값이 달라진 이유는 이 상태 변경의 비대칭으로 읽을 수 있다.

> **변화의 동기.** 실제 압력은 자동 수집이 사용자의 내구성 있는 상태를 동의 없이 바꿀 수 있다는 위험이었다. 동기 출처는 기본값을 뒤집은 안전성 수정 커밋이며, 증거 강도는 **코드에서 추론**이다. 읽기인 자동 회상은 기본으로 남기되 쓰기인 자동 수집만 명시적으로 선택하게 해 변경 권한을 분리했다.

## 선별 메모리가 상시 초기 맥락이 되다

검색 기능이 생겨도 임베딩 공급자가 없으면 첫 답변에서 선별 메모리를 찾지 못할 수 있었다. 작은 장기 메모리라면 검색 요청을 기다리지 않고 처음부터 모델 맥락에 넣는 편이 더 확실했다. 이를 위해 워크스페이스 최상위의 `MEMORY.md`를 초기 맥락 파일에 추가하되, 하위 에이전트에는 주입하지 않고 파일도 자동으로 만들지 않았다. 이 명시적 동기를 밝힌 [PR #2318](https://github.com/openclaw/openclaw/pull/2318)은 [`2cbc991bfe7c`](https://github.com/openclaw/openclaw/commit/2cbc991bfe7cdc8a722fc98d419826c982b06231)로 병합되어 `v2026.1.29`에 처음 포함되었다.

> **변화의 동기.** 실제 압력은 임베딩 공급자가 없으면 내용이 있는 `MEMORY.md`조차 비어 있다고 답하는 실패였다. 동기 출처는 이 증상을 직접 적은 PR #2318이며, 증거 강도는 **명시적**이다. 작은 선별 파일만 시작 맥락에 넣고 하위 에이전트와 자동 생성을 제외해 가용성과 개인 정보 범위를 함께 제한했다.

이 변경은 서로 목적이 다른 두 읽기 경로를 분명히 했다.

| 읽기 경로           | 대상                    | 장점                                                  | 주의할 점                                                   |
| ------------------- | ----------------------- | ----------------------------------------------------- | ----------------------------------------------------------- |
| 시작할 때 직접 주입 | 짧게 선별한 `MEMORY.md` | 검색 성공 여부와 무관하게 첫 답변부터 사용할 수 있다. | 매번 맥락을 차지하므로 작고 신뢰할 수 있는 내용이어야 한다. |
| 필요할 때 검색      | 상세한 일일 메모리      | 많은 기록 가운데 현재 질문과 관련된 부분만 가져온다.  | 검색 품질과 도구 호출 여부에 따라 회상 결과가 달라진다.     |

다만 템플릿과 문서에 적힌 주 세션·비공개 제한과 실제 초기 맥락 동작은 지금도 불일치한다. 자세한 내용은 [현재 계약 차이](10-current-contract-gaps.md)를 보라.

## QMD가 운영자 도구에서 관리형 백엔드로 바뀌다

외부 [`qmd`](01-current-architecture.md#qmd-explained) 명령 실험이 남긴 과제는 검색 품질보다 운영 책임이었다. QMD의 공식 풀이는 Query Markup Documents다. 문서 원본을 쓰거나 일일 기록을 장기 기억으로 승격하는 기능이 아니라, 이미 있는 문서를 색인하고 찾는 별도 로컬 검색 프로그램이다.

여기서 **사이드카**(sidecar)란 OpenClaw 코드 안의 함수가 아니라, 같은 기기에서 OpenClaw 곁에 별도 실행 파일과 프로세스로 동작하는 프로그램을 뜻한다. 반드시 하나의 프로세스가 계속 실행된다는 뜻은 아니며, OpenClaw가 필요할 때 `qmd` 하위 프로세스를 실행하는 형태도 포함한다. **관리형 백엔드**가 된다는 것은 검색 계산을 QMD가 맡더라도 설치 확인, 에이전트별 격리, 갱신 시점, 실패 처리 같은 운영 수명주기는 OpenClaw가 조율한다는 뜻이다.

두 프로그램의 경계는 다음처럼 읽으면 쉽다.

| 주체     | 맡는 일                                                                                                | 실패했을 때의 책임 경계                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| OpenClaw | QMD 사용 설정, 에이전트별 격리, 실행과 갱신 시점, 결과 제한·경로 검사·인용, 조건부 대체 경로를 정한다. | 실행 파일 누락이나 호환되지 않는 출력처럼 QMD를 쓸 수 없는 상태를 진단하고, 계약이 허용할 때만 내장 검색으로 돌아간다. |
| QMD      | 에이전트별 문서 묶음인 컬렉션과 색인·임베딩·질의 처리 흐름을 실행하고 검색 결과를 돌려준다.            | 컬렉션 잠금, 버전 차이, 질의·갱신 실패는 외부 프로세스의 실패로 드러나며 OpenClaw가 그 의미를 해석해야 한다.           |

선택 설정인 `memory.backend = "qmd"`는 이 책임 분담을 제품 계약으로 받아들였다. [PR #3160](https://github.com/openclaw/openclaw/pull/3160)의 병합 묶음은 [`5d3af3bc6226`](https://github.com/openclaw/openclaw/commit/5d3af3bc6226026826c5eef48e2ad2eb9f6a01f2)에서 시작해 2026-02-03의 [`1ee57cf7277e`](https://github.com/openclaw/openclaw/commit/1ee57cf7277ec70043dfca8a0747909ab7207950)에 착지했고, `v2026.2.2`에 처음 포함되었다.

> **변화의 동기.** PR #3160은 선택형 QMD 백엔드, 에이전트별 사이드카, 결과 제한과 인용, 경로 검사, QMD 누락·오동작 때의 내장 메모리 대체 경로(fallback)를 **명시된 계약**으로 남겼다. 다만 외부 도구를 제품이 관리하는 수명주기 안에 넣은 더 넓은 선택 이유는 구현 계보에서 **코드로 추론**한다. 특정 대체 사건이 이 도입을 촉발했다는 근거도 없으므로, 설계된 복구 계약과 관측 사건을 혼동하지 않는다.

PR 본문은 다음을 명시적으로 열거했다.

- 추가 컬렉션과 선택적 세션 색인
- 에이전트별 설정과 사이드카 격리
- 정규화되고 제한되며 인용을 포함한 결과
- 경로 안전성 검사
- QMD가 없거나 잘못 동작할 때 내장 메모리로 자동 대체

이 백엔드 뒤에는 긴 안정화 작업이 따라왔다. 실행 파일 누락, SQLite 잠금 충돌을 뜻하는 `SQLITE_BUSY`, 컬렉션 이름, 파일 선택 패턴 변경, QMD 결과의 세션 경로를 OpenClaw 경로로 되돌리는 처리, 출력 제한, 결과가 없을 때의 처리, 파일 감시기가 쓰는 운영체제 자원, 인용 동작, QMD 버전 호환성 모두 후속 수정이 필요했다.

이 안정화 이력은 사이드카를 채택하면 검색 기능만 추가되는 것이 아님을 보여 준다. 프로세스 수명주기, 버전 차이, 경로 정체성, 장애 때 어느 검색으로 돌아갈지까지 모두 메모리 계약의 일부가 된다.

## 순위화가 조정 가능한 처리 흐름이 되다

검색이 가능해지자 “관련 결과를 찾았는가”만큼 “그중 무엇을 먼저 보여 주는가”가 중요해졌다. 원문을 나눈 조각인 **청크** 가운데 비슷한 것들이 상위를 차지할 수 있었고, 최근의 일일 기록과 오래되었지만 여전히 유효한 사실이 같은 방식으로 경쟁했다. 최초 검색 점수를 받은 후보의 순서를 다시 조정하는 **재순위화**가 이 문제를 맡았다.

- [`fa9420069ab3`](https://github.com/openclaw/openclaw/commit/fa9420069ab39f36fc47ca23b0ea909025a0a447): 질의 관련성과 결과끼리의 차이를 함께 보아 비슷한 청크의 반복을 줄이는 MMR(Maximal Marginal Relevance)
- [`6b3e0710f4a0`](https://github.com/openclaw/openclaw/commit/6b3e0710f4a05135fa57798dcc3ff9668e6a061a): 상시 유효한 자료는 제외하고 날짜별 기록은 오래될수록 점수를 낮춰 최근 기록을 우선하는 시간 감쇠

MMR은 처음 내부 보조 함수의 기본값으로는 켜진 채 착지했다. 바로 이어진 시간 감쇠 커밋이 두 재순위화 방식을 제품 설정으로 노출하면서 기본값을 꺼짐으로 바꿨다. 두 커밋 사이에는 릴리스 태그가 없었으므로, 사용자가 받은 `v2026.2.17`에서는 둘 다 선택 기능이었다.

처리 흐름은 다음 순서가 되었다.

`벡터·키워드 후보 수집 → 두 점수의 가중 병합 → 선택적 시간 감쇠 → 점수순 정렬 → 선택적 MMR → 요청한 개수만큼 반환`

둘은 지금도 기본값이 꺼져 있다. MMR과 시간 감쇠는 정답을 보장하는 규칙이 아니라, 다양성과 최신성이 유용하다는 가정으로 순서를 조정하는 **휴리스틱**이다. 어느 쪽이든 사용자가 필요로 하는 정확한 오래된 사실을 뒤로 밀 수 있으므로, 그럴듯한 예시만이 아니라 언어·기간·질의 유형을 나눈 평가가 필요하다.

> **변화의 동기.** 실제 목표는 중복 청크를 줄이고 날짜별 메모의 최신성을 선택적으로 반영하는 일이었다. 동기 출처는 두 커밋과 [PR #13391](https://github.com/openclaw/openclaw/pull/13391)의 직접 설명이며, 증거 강도는 **명시적**이다. 두 휴리스틱은 독립된 선택 단계로 넣고 기본값을 꺼 두었다. 정확한 오래된 사실을 밀어낼 수 있다는 평가는 관측 사건이 아니라 이 설계에서 도출한 잠재 위험이다.

구현과 제품 설명을 함께 출시하는 과정에서도 한계가 드러났다. [PR #18097](https://github.com/openclaw/openclaw/pull/18097)의 병합 묶음에는 두 재순위화 구현, 후속 수정, 설정·스키마·문서, 설정 화면에서 쓰는 레이블과 도움말이 모두 있었다. [`563df5638947`](https://github.com/openclaw/openclaw/commit/563df5638947d6caea4d6e837b55eb8bc295687d)은 레이블·도움말 메타데이터만 되돌렸고, [PR #18786](https://github.com/openclaw/openclaw/pull/18786)은 [`a87b5fb00901`](https://github.com/openclaw/openclaw/commit/a87b5fb0090156b6a2d636f23d42bad0397bc476)을 통해 그 메타데이터를 복원했다.

> **변화의 동기.** 실제 목표는 이미 존재하는 런타임 설정을 UI에서 다시 발견하고 정확히 설명하게 하는 일이었다. 동기 출처는 되돌림을 후속 처리한다고 밝힌 PR #18786이며, 증거 강도는 **명시적**이다. 동작과 기본값은 건드리지 않고 레이블·도움말 메타데이터만 복원해 출시된 실행 계약과 제품 설명을 다시 맞췄다.

따라서 `v2026.2.17`에는 런타임·설정 동작이 있었지만 되돌린 레이블과 도움말은 없었다. `v2026.2.21`에는 복원된 UI 메타데이터가 포함되었다.

2월 말에는 검색 질의를 언어별 형태로 넓히고 텍스트를 검색 단위로 나누는 토큰화 규칙을 보완해 한국어, 일본어, 아랍어, 스페인어, 포르투갈어 변형을 추가했다. 그러나 이는 질의 쪽의 언어 처리를 넓힌 변화였다. FTS5가 중국어·일본어·한국어(CJK) 문서를 제대로 나누지 못하는 더 깊은 색인 문제는 3월이 되어서야 해결되었다.

> **변화의 동기.** 실제 목표는 영어 중심 질의 확장을 한국어·일본어·아랍어·스페인어·포르투갈어로 넓히는 일이었다. 동기 출처는 언어별 지원을 직접 밝힌 [한국어 PR #18899](https://github.com/openclaw/openclaw/pull/18899), [일본어 PR #23156](https://github.com/openclaw/openclaw/pull/23156), [스페인어·포르투갈어 PR #23710](https://github.com/openclaw/openclaw/pull/23710), [아랍어 PR #23717](https://github.com/openclaw/openclaw/pull/23717)과 각 커밋이며, 증거 강도는 **명시적**이다. 이는 질의 확장의 언어 범위를 넓힌 변경이며, FTS5 토크나이저 자체의 CJK 실패를 해결한 것으로 확대해서는 안 된다.

## 다음 장으로

두 달 동안 OpenClaw 메모리는 네 단계에서 파일 관례를 제품 계약으로 바꾸었다.

1. 압축과 세션 전환이라는 수명주기 경계에서 기록 기회를 만들었다.
2. Markdown 원본 위에 어휘·벡터 색인과 모델용 검색 도구를 놓았다.
3. 주 메모리 구현을 한 플러그인이 소유하게 하고, QMD 같은 외부 검색기의 운영 경계를 정했다.
4. 검색 결과의 다양성과 최신성을 선택적으로 조정할 수 있게 했다.

그러나 각 해법은 다음 질문도 남겼다. 원격 임베딩 없이도 충분히 검색할 수 있는가, 미디어까지 검색한다면 어떤 자료를 코퍼스에 포함할 것인가, 이벤트가 발생한 횟수가 아니라 실제 내용의 최신성을 어떻게 식별할 것인가, 대안 플러그인을 선택했을 때 모델에게 주는 프롬프트도 올바른 소유자를 따르는가 하는 문제다.

3월의 변화는 이 질문을 로컬 실행, 언어별 정확성, 내용 정체성, 플러그인 소유권이라는 더 엄격한 계약으로 바꾼다.
