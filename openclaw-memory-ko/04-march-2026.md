# 4장. 2026년 3월: 로컬 실행·언어·소유권의 재편

1월과 2월에 검색이 제품 기능으로 자리 잡자 질문의 초점이 달라졌다. 이제 중요한 것은 검색 기능의 존재가 아니라, 어떤 실행 환경과 언어에서 무엇을 얼마나 정확하게 찾으며 그 동작을 누가 책임지는가였다. 원격 OpenAI 공급자에 기댄 초기 경로는 오프라인 사용이라는 목표를 충분히 채우지 못했다. 영어의 단어 경계를 전제로 한 전체 텍스트 검색은 중국어·일본어·한국어에서 크게 약해졌고, 대안 메모리 플러그인을 선택해도 코어 프롬프트는 내장 도구를 계속 설명했다.

3월의 변화는 이 문제를 세 축에서 정리했다. 첫째, 로컬 임베딩과 이미지·오디오 임베딩을 추가하되 검색할 원본 집합인 **코퍼스**를 명시적으로 제한했다. 둘째, 수명주기 판단을 이벤트 횟수가 아니라 실제 내용의 개정본에 연결하고 언어별 색인 규칙을 색인의 정체성에 포함했다. 셋째, 프롬프트·플러시·도구·엔진의 정책을 선택된 메모리 플러그인으로 옮기고, 호스트 기능은 안정된 SDK 경계 뒤에 두었다. 선택지는 넓어졌지만, 여러 엔진이 함께 지켜야 할 가시성·인용·삭제·평가 계약은 그만큼 더 중요해졌다.

## 로컬·멀티모달 임베딩이 검색 범위를 넓히다

**임베딩**은 문장이나 미디어의 의미를 수치 벡터로 바꾸어, 표현이 달라도 의미가 가까운 항목을 찾게 하는 방식이다. 초기 내장 검색은 원격 공급자에 의존할 수 있었으므로, 네트워크나 외부 API 키 없이 벡터 검색을 운영하려는 사용자에게는 로컬 경로가 필요했다. Ollama 임베딩을 공급자와 대체 경로로 추가한 [PR #26349](https://github.com/openclaw/openclaw/pull/26349)와 병합 커밋 [`3eec79bd6cb7`](https://github.com/openclaw/openclaw/commit/3eec79bd6cb71f2e11dea10a10bd93922d9a7345)은 이 선택지를 열었다.

> **변화의 동기.** Ollama를 임베딩 공급자와 대체 경로로 추가한다는 기능 목표는 PR #26349에 **명시되어 있다**. 이 선택이 원격 API가 없는 벡터 경로를 만들고 초기 오프라인 목표와 구현 사이의 간격을 줄였다는 평가는 **코드에서 추론**한 설계 해석이다. 별도 메모리 엔진을 만들지 않고 기존 공급자 인터페이스를 재사용해 실행 위치의 선택권을 넓혔다.

검색 대상도 텍스트에서 이미지와 오디오로 넓어졌다. 여기서 **멀티모달 임베딩**은 서로 다른 형식의 내용을 같은 의미 검색 흐름에서 비교할 수 있도록 벡터로 표현하는 방식이다. 다만 모든 미디어를 자동 수집하지는 않았다. [PR #43460](https://github.com/openclaw/openclaw/pull/43460)은 사용자가 설정한 추가 경로만 특정 Gemini 멀티모달 임베딩 모델로 색인하는 선택 기능을 추가했고, [`d79ca5296054`](https://github.com/openclaw/openclaw/commit/d79ca5296054058930bd97dd43540fd52ede15a3)로 병합되어 `v2026.3.11-beta.1`에 처음 포함되었다.

그 범위에는 네 가지 경계가 있었다.

- 기본 메모리 원본은 계속 텍스트 Markdown이었다.
- 이미지와 오디오는 사용자가 설정한 추가 경로에 있을 때만 검색 후보가 되었다.
- 기능을 켰다는 이유만으로 워크스페이스 전체를 미디어 수집 대상으로 삼지 않았다.
- 지원되지 않는 공급자와 대체 경로 조합은 임의의 다른 동작으로 넘어가지 않고 실패했다.

> **변화의 동기.** 이미지·오디오 색인이라는 목표와 명시적으로 선택한 경로만 다룬다는 범위는 PR #43460에 **명시되어 있다**. 반면 워크스페이스 전체 수집의 비용과 프라이버시 위험 때문에 이 형태를 골랐다는 설명은 **코드에서 추론**한 설계 해석이다. 실제 무단 수집 사건이 관측되었다는 뜻은 아니다.

이 변경의 핵심은 기능 확장과 수집 범위 확대를 같은 결정으로 취급하지 않았다는 데 있다. 새 형식을 검색할 수 있게 하면서도, 어떤 자료가 코퍼스에 들어가는지는 사용자가 검토할 수 있는 설정으로 남겼다.

> **예시 — 합성 사례:** 사용자가 사진 폴더를 추가 경로로 지정하지 않았다면, 멀티모달 기능이 켜져 있다는 이유만으로 그 폴더의 이미지가 자동 색인되지는 않았다. 이 문장은 명시적 코퍼스 선택 계약을 설명하기 위한 가상 사례이며 실제 사용자 설정을 인용한 것이 아니다.

## 수명주기 판단이 이벤트 횟수에서 내용 개정본으로 옮겨가다

압축이나 재시도 같은 **수명주기 이벤트**는 작업이 일어났다는 사실만 알려 준다. 그 이벤트가 가리키는 내용이 실제로 바뀌었는지, 이미 처리한 내용과 같은지는 따로 확인해야 한다. 3월에는 이 구분을 대화 기록 색인의 최신성과 메모리 플러시의 중복 제거에 각각 적용했다.

먼저 [PR #25561](https://github.com/openclaw/openclaw/pull/25561)은 압축으로 대화 기록이 바뀌었음을 알리는 갱신 이벤트를 추가했다. 세션 소스의 압축 후 강제 갱신이 켜져 있으면 바뀐 대화 기록의 색인만 즉시 갱신하고, 더 넓은 메모리 파일 동기화는 기존 주기 작업에 맡겼다. 모든 메모리를 다시 훑지 않고 변경된 원본만 빠르게 반영하는 선택이었다.

별개의 문제인 압축 전 메모리 플러시에서는 같은 내용이 중단과 재시도를 거치며 여러 번 기록될 수 있었다. [PR #34222](https://github.com/openclaw/openclaw/pull/34222)은 중복 제거 기준을 압축 이벤트 카운터에서 대화 기록의 **내용 해시**로 바꿨다. 내용 해시는 원문에서 계산한 고정 길이 식별값이다. 원문이 같으면 같은 값이 나오므로, 이벤트 번호가 달라도 이미 처리한 내용인지를 판별할 수 있다.

두 변경의 차이와 공통점은 다음과 같다.

| 상황                        | 이전의 실패 흐름                                                                  | 바뀐 흐름                                                     | 내용 기준의 효과                                                       |
| --------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 압축 뒤 대화 기록 색인 갱신 | `압축으로 내용 변경 → 갱신 통지 없음 → 세션 색인이 이전 개정본을 계속 사용`       | `내용 변경 → 갱신 이벤트 → 바뀐 대화 기록의 색인만 즉시 갱신` | 최신 개정본을 빠르게 반영하면서 더 넓은 메모리 동기화와 작업을 나눴다. |
| 압축 플러시 재시도          | `같은 내용 → 중단·재시도로 이벤트 번호 증가 → 같은 플러시가 4–7회 기록될 수 있음` | `같은 내용 → 같은 내용 해시 → 이미 처리한 플러시를 건너뜀`    | 이벤트 횟수와 무관하게 동일 내용의 반복 저장을 막았다.                 |

공통된 교훈은 수명주기 카운터를 내용의 정체성으로 대신 쓰지 말아야 한다는 것이다. 이벤트는 다시 확인할 시점을 알려 주는 힌트이고, 최신성이나 중복 여부는 실제 원본의 개정본에 묶여야 한다.

> **변화의 동기.** PR #25561은 압축 실행 경로가 대화 기록 갱신을 알리지 않아 세션 색인이 오래될 수 있는 코드상 결함을 직접 설명했다. 연결된 [Issue #19207](https://github.com/openclaw/openclaw/issues/19207)은 압축 뒤 정확한 식별자를 잃은 사용자 보고이지만, 오래된 색인 자체를 관측한 보고로 확대해서는 안 된다. 반면 [Issue #30115](https://github.com/openclaw/openclaw/issues/30115)과 PR #34222는 압축 중단·재시도 때 같은 내용이 4–7회 기록된 실제 장애를 직접 연결한다. 두 근거 모두 **명시적**이지만, 전자는 입증된 코드 경로이고 후자는 관측된 사건이다. 전자는 변경된 대화 기록만 즉시 갱신하고, 후자는 이벤트 횟수 대신 내용 해시를 사용해 각각의 문제를 실제 내용에 연결했다.

## 대안 메모리 플러그인이 프롬프트 소유권 버그를 드러내다

OpenClaw의 메모리 슬롯에는 한 번에 하나의 메모리 플러그인이 선택된다. 여기서 **플러그인 소유권**이란 선택된 플러그인이 도구만 등록하는 데 그치지 않고, 어떤 메모리 작업 흐름을 모델에게 설명하며 언제 저장하고 검색할지도 책임진다는 뜻이다. 그런데 초기 시스템 프롬프트는 어느 플러그인을 선택해도 내장 Markdown 메모리 도구를 설명했다. 대안 플러그인이 슬롯을 맡으면 실제 도구와 모델이 받은 지침이 서로 어긋났다.

해결책은 선택된 플러그인이 시스템 프롬프트 안의 메모리 구역을 직접 제공하게 하는 것이었다. [PR #40126](https://github.com/openclaw/openclaw/pull/40126)은 이 변경을 [`fd2b3ed6af9c`](https://github.com/openclaw/openclaw/commit/fd2b3ed6af9c3ec6ee9e5e0f16410cf286159002)로 병합했다.

> **변화의 동기.** 실제 압력은 대안 플러그인을 선택해도 시스템 프롬프트가 `memory-core` 전용 도구를 가르치는 소유권 오류였다. 동기 출처는 이 문제와 범위를 직접 적은 PR #40126이며, 증거 강도는 **명시적**이다. 선택된 플러그인이 프롬프트 구역을 등록하게 해 도구 소유자와 모델 지침의 소유자를 일치시켰다.

코어가 계속 이전 구현의 도구와 작업 흐름을 가르친다면, 설정에서 플러그인을 바꿔도 모델의 행동은 완전히 바뀌지 않는다. 따라서 이 수정은 단순히 프롬프트 문구를 확장한 일이 아니라, 도구와 지침이 같은 소유자를 따르도록 모델 경계의 계약을 바로잡은 일이었다. 다만 프롬프트만 옮겨서는 엔진·플러시·도구·호스트 기능에 흩어진 메모리 정책까지 정리할 수 없었다.

## 메모리 하위 시스템이 범용 에이전트 코어 밖으로 이동하다

프롬프트에서 드러난 소유권 충돌은 더 넓은 구조에도 있었다. 범용 에이전트 코어가 메모리 프롬프트·플러시·도구·검색 엔진을 직접 알고 있으면, 대안 플러그인이 일부만 대체하고 나머지 정책은 코어에 남게 된다. 3월 말 리팩터링은 메모리 고유 정책을 플러그인으로 모으고, 범용 코어에는 선택된 플러그인을 호출하는 공통 접점만 남겼다.

이때 **호스트 SDK**는 플러그인이 파일 시스템, 저장소, 임베딩 공급자, 외부 프로세스 같은 OpenClaw 호스트 기능을 안정된 형식으로 사용할 수 있게 하는 인터페이스다. SDK는 어떤 기억을 선별하거나 검색할지 결정하지 않는다. 그 정책은 메모리 플러그인이 소유하고, SDK 뒤의 메모리 호스트는 요청받은 기능을 실제 환경에서 수행한다.

```text
이전: 범용 에이전트 코어 ──직접 소유──> 프롬프트 · 플러시 · 도구 · 엔진

이후: 범용 에이전트 코어 ──호출──> 범용 플러그인 어댑터 ──전달──> 선택된 메모리 플러그인
                                                        │
                                                        └──사용──> 호스트 SDK ──노출──> 메모리 호스트 기능
```

비슷해 보이는 네 역할은 다음처럼 구분할 수 있다.

| 역할                 | 맡는 일                                                                  | 맡지 않는 일                                     |
| -------------------- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| 메모리 엔진          | 설정된 원본을 색인하고 질의를 실행해 검색 결과와 상태를 만든다.          | 범용 에이전트 실행 전체를 조율하지 않는다.       |
| 범용 플러그인 어댑터 | 코어의 수명주기·도구 호출을 현재 선택된 플러그인에 공통 형식으로 넘긴다. | 특정 메모리 구현의 정책을 결정하지 않는다.       |
| 호스트 SDK           | 플러그인이 호스트 기능을 요청할 수 있는 안정된 형식과 함수를 제공한다.   | 어느 플러그인을 선택할지 결정하지 않는다.        |
| 메모리 호스트        | SDK로 받은 파일·저장·공급자·프로세스 요청을 실제 환경에서 수행한다.      | 선별·회상·승격 같은 메모리 정책을 정하지 않는다. |

2026-03-26부터 2026-03-27까지 이어진 리팩터링은 이 소유권 이동을 다음 커밋으로 한 흐름에 묶었다.

- [`e0dfc776bba8`](https://github.com/openclaw/openclaw/commit/e0dfc776bba8ca9d235e5a8124344abac6aee931): 플러시 소유권이 메모리 플러그인으로 이동했다.
- [`e955d574b237`](https://github.com/openclaw/openclaw/commit/e955d574b237a68632ebaa899d37928270d0171d): 도구가 `memory-core`로 이동했다.
- [`cad83db8b2f7`](https://github.com/openclaw/openclaw/commit/cad83db8b2f7664230df50f63cfff3106a5a8154): 엔진이 플러그인으로 이동했다.
- [`dbf78de7c680`](https://github.com/openclaw/openclaw/commit/dbf78de7c680405245cadee06a8ddb9e787616aa): 엔진의 직접 소유를 범용 플러그인 어댑터가 대체했다.
- [`bd6c7969ea9c`](https://github.com/openclaw/openclaw/commit/bd6c7969ea9c40c56ccdbe50301aeb8621321ba4): 호스트 SDK가 추출되었다.
- [`eebce9e9c7cb`](https://github.com/openclaw/openclaw/commit/eebce9e9c7cb423794d3fde480a08eb8edbb8ae3): 메모리 호스트가 그 SDK로 이동했다.

이 흐름으로 책임은 네 층으로 갈렸다.

- 범용 코어는 에이전트 실행을 조율한다.
- 선택된 메모리 플러그인은 프롬프트·플러시·도구·엔진 정책을 소유한다.
- 호스트 SDK와 메모리 호스트는 플러그인이 사용할 공용 실행 기능을 제공한다.
- 임베딩 공급자는 내용을 벡터로 바꾸는 공급자별 구현을 맡는다.

> **변화의 동기.** 실제 목표는 메모리 전용 정책이 범용 에이전트 코어에 흩어져 대안 구현과 충돌하는 구조를 정리하는 일이었다. 동기 출처는 2026-03-26부터 2026-03-27까지 이어진 여섯 리팩터링 커밋의 소유권 이동이며, 증거 강도는 **코드에서 추론**이다. 플러시·도구·엔진은 플러그인 경계로, 호스트 기능은 SDK로 옮겨 한 소유자와 안정된 접점을 만드는 형태를 골랐다.

얻은 것은 눈에 띄는 새 사용자 기능보다 책임 경계가 분명한 아키텍처였다. 이 경계는 이후 Active Memory와 Dreaming의 도입, [QMD](01-current-architecture.md#qmd-explained) 강화, 임베딩 공급자 추출, 외부 엔진 확장이 메모리 정책을 범용 코어로 되돌리지 않고 발전할 기반이 되었다. 반대로 선택된 플러그인과 추가 기능이 가시성·인용·삭제 같은 공통 규칙을 함께 지키는지는 별도로 증명해야 하는 과제가 생겼다.

## CJK 보고가 어휘 검색의 정확성을 강제하다

**CJK**는 중국어(Chinese), 일본어(Japanese), 한국어(Korean)를 함께 가리키는 약칭이다. 이 언어들은 영어처럼 띄어쓰기만으로 검색 단위를 안정적으로 나누기 어렵다. 따라서 종합 테스트에서 FTS가 작동해도 실제 CJK 문장에서는 필요한 항목을 거의 찾지 못할 수 있었다.

여기서 **FTS**는 단어가 나타난 위치와 빈도를 이용하는 전체 텍스트 검색이고, **토크나이저**는 원문을 색인과 질의에 사용할 검색 단위인 토큰으로 나누는 규칙이다. [Issue #20730](https://github.com/openclaw/openclaw/issues/20730)은 SQLite FTS5의 기본 토크나이저를 사용한 BM25 검색이 중국어·일본어·한국어 텍스트에서 사실상 쓸 수 없음을 재현했다.

해결책은 `unicode61`과 `trigram` 토큰화 방식을 설정할 수 있게 하고, 토크나이저가 바뀌면 강제로 다시 색인하며, 한 글자와 두 글자 질의에는 부분 문자열 검색을 사용하는 것이었다. `unicode61`은 유니코드 문자와 단어 경계를 중심으로 토큰을 만들고, `trigram`은 연속된 세 문자를 겹쳐 나누어 띄어쓰기가 적은 텍스트도 찾게 한다. 세 글자보다 짧은 질의는 trigram 토큰을 만들 수 없으므로 별도의 부분 문자열 경로가 필요했다. [PR #56707](https://github.com/openclaw/openclaw/pull/56707)은 이 변경을 [`3ce48aff660a`](https://github.com/openclaw/openclaw/commit/3ce48aff660a0dca487fb195132d53e6e0e404ed)로 병합했고, `v2026.3.31-beta.1`에 처음 포함시켰다.

> **변화의 동기.** 실제 압력은 기본 FTS5 토크나이저가 중국어·일본어·한국어를 사실상 검색하지 못한다는 사용자 장애였다. 동기 출처는 재현 예시가 있는 Issue #20730과 이를 해결한 PR #56707이며, 증거 강도는 **명시적**이다. `unicode61`/`trigram` 선택, 정체성 변경 시 재색인, 짧은 질의의 부분 문자열 대체를 함께 골라 언어별 정확성과 색인 일관성을 동시에 지켰다.

여기서 두 가지 설계 교훈이 나온다.

1. “FTS가 작동한다”는 종합 판단만으로는 부족하다. 언어별 평가 구간은 전체 평균에 가려진 전면적 실패를 드러낼 수 있다.
2. 토크나이저는 단순한 질의 옵션이 아니라 색인을 만드는 규칙이다. 그러므로 토크나이저 설정은 색인의 정체성에 포함되어야 하며, 변경할 때는 기존 색인을 다시 만들어야 한다.

3월 말에는 **FTS 전용** 경로도 명확해졌다. 이는 임베딩 공급자와 벡터 검색 없이, 어휘 기반 FTS 색인과 검색만 사용하는 정상 동작 방식이다. 공급자 `none`을 다룬 [`41c30f0c5901`](https://github.com/openclaw/openclaw/commit/41c30f0c59012635220bde685468af009da6a60a)과 [`598f539be5e1`](https://github.com/openclaw/openclaw/commit/598f539be5e1585e450a324c506ced28d458d0a7)은 임베딩 공급자가 없더라도 FTS 표를 채우고 재색인 뒤 검색 가능한 상태를 유지하도록 했다. 이제 “임베딩이 없음”이 “메모리 색인이 비어 있음”을 뜻하지 않았다.

> **변화의 동기.** 임베딩 공급자가 없을 때 FTS 표가 채워지지 않거나 재색인이 기존 청크를 비우는 실패가 실제 사용자 환경에서 보고되었다. 동기 출처는 [Issue #42714](https://github.com/openclaw/openclaw/issues/42714), [PR #56473](https://github.com/openclaw/openclaw/pull/56473)과 두 수정 커밋이며, 증거 강도는 **명시적**이다. 벡터 폴백을 가장하는 대신 FTS 전용 색인을 독립된 정상 방식으로 채우고, 공급자 전환 뒤에도 재색인 상태를 보존했다.

## 외부 엔진이 전략의 복수성을 선명하게 만들다

플러그인 소유권이 정리되자 서로 다른 기억 모델을 같은 제품 안에서 선택할 수 있다는 의미도 선명해졌다. Honcho는 자동 대화 보존, 사용자와 에이전트에 관한 모델링, 의미적 결론, 답변 전 문맥 주입을 제공하는 외부 플러그인·서비스다. [공식 Honcho 문서](https://docs.openclaw.ai/concepts/memory-honcho)는 2026-03-30의 [`70b7f32c7efa`](https://github.com/openclaw/openclaw/commit/70b7f32c7efa6dee9306100b9346269d9f61f83a)에 추가되었다.

Honcho를 `memory-core`의 다음 구현 단계로 읽어서는 안 된다. 두 엔진은 같은 기능이 성숙한 전후 관계가 아니라, 기억을 무엇으로 보고 어떻게 갱신할지에 관해 서로 다른 전략을 가진 선택지다. 이 문서의 등장은 OpenClaw의 공개 메모리 설명이 하나의 파일·색인 구조에서 복수의 의미 모델로 넓어졌음을 보여 준다.

> **변화의 동기.** 실제 목표는 파일·색인 중심 구현과 다른 사용자 모델·자동 대화 보존 방식도 공식 선택지로 설명하는 일이었다. 동기 출처는 Honcho 문서를 추가한 커밋과 문서 내용이며, 증거 강도는 **맥락적이며 직접 인과는 입증되지 않음**이다. 외부 엔진을 `memory-core`의 다음 단계로 합치지 않고 별도 플러그인·서비스로 문서화해 전략의 복수성을 보존했다.

- 사람이 직접 관리하고 검토하는 투명한 기록
- 대안 플러그인이 관리하는 로컬 벡터 레코드
- OpenClaw가 실행과 색인 상태를 관리하는 로컬 사이드카
- 외부 서비스가 만드는 AI 기반 사용자 모델

여기서 **사이드카**는 OpenClaw 내부 함수가 아니라 같은 기기에서 별도 실행 파일이나 프로세스로 동작하는 보조 프로그램을 뜻한다. QMD가 대표적인 예다. OpenClaw가 사이드카를 관리하려면 설치와 버전, 에이전트별 격리, 색인 갱신, 프로세스 실패와 대체 동작까지 함께 책임져야 한다.

전략이 여러 개일수록 공통 계약은 더 중요해진다. 어떤 기억을 어느 대화에서 볼 수 있는지, 결과의 출처를 어떻게 인용하는지, 사용자가 무엇을 삭제하고 내보낼 수 있는지, 품질을 어떤 기준으로 평가하는지, 모델에게 어떤 지침을 주는지는 엔진마다 제각각이어서는 안 된다. 따라서 “메모리 플러그인”은 검색 도구 하나를 등록하는 확장점이 아니라, 기억의 수명주기와 모델 지침을 함께 소유하는 경계로 이해해야 한다.

## 다음 장으로

3월은 메모리를 하나의 하드코딩된 엔진에서, 선택된 소유자와 여러 의미 전략이 공존하는 구조로 바꾸었다. 로컬·멀티모달 경로는 실행 위치와 코퍼스의 선택권을 넓혔고, 내용 해시와 토크나이저 정체성은 색인의 최신성과 정확성을 실제 원본에 연결했다. 프롬프트·플러시·도구·엔진을 플러그인 경계로 옮긴 일은 그 선택이 모델 행동까지 일관되게 이어질 토대를 만들었다.

그러나 도구를 제공하는 것만으로 주 모델이 실제로 검색한다는 보장은 없었다. 검색 결과가 반복해서 쓰였다는 사실만으로 무엇을 장기 기억으로 승격할지 판단하기도 어려웠다. 4월에는 이 두 문제가 답변 전 에이전트형 회상과 회상 주도 승격으로 이어진다. 동시에 더 넓어진 코퍼스와 대화 기록 회상은 지연 시간, 노출 편향, 프라이버시 필터의 적용 순서를 측정 가능한 문제로 만든다.
