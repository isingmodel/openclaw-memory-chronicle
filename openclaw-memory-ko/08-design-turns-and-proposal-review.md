# 8장. 설계 전환과 2025년 제안의 재검토

2장부터 7장까지는 작은 파일 관례가 검색, 수명주기, 플러그인 소유권, 대화 기록, 보호된 대화 간 회상으로 자라난 시간을 따라갔다. 마지막 대화 간 회상은 아키텍처 기준일에는 `main`에만 있었고, 이후 `v2026.7.2-beta.3`과 `v2026.7.2-beta.4`에서 단계적으로 출시되었다. 이제 연대기에서 한 걸음 물러나, 그 변화들이 반복해서 선택한 설계 방향을 읽을 차례다. 개별 기능의 목록보다 중요한 것은 문제가 생길 때마다 책임이 어디로 이동했는가다.

가장 큰 흐름은 프롬프트에 맡긴 희망을 런타임의 강제로, 흩어진 부수 파일을 소유권이 분명한 SQLite 상태로, 경계 없는 회상을 범위를 따지는 검색으로 바꾼 과정이었다. 동시에 사람에게 보이는 의미 기억과 기계가 운영하는 상태를 갈라 놓았다. 이 세 전환은 서로 다른 시기에 일어났지만, 결국 같은 질문에 답한다. 기억의 정확성·복구 가능성·안전성을 누가 책임지는가?

이 장의 앞부분은 2026-07-18 기준으로 역사에서 확인되는 설계 원칙을 정리한다. 뒤의 2025년 제안 비교는 당시 구상이 실제 시스템에 얼마나 남았는지를 돌아보는 평가다. 아직 미완성인 의미 모델을 더 우선해서 평가해야 한다는 결론은 유지보수자가 채택한 로드맵이 아니라, 이후 장에서 결과 비교로 검증할 이 책의 문제 제기다.

## 변화의 이유는 어디에서 확인할 수 있는가

같은 코드 변경이라도 “왜”를 아는 방법은 서로 다르다. 어떤 변화는 사용자가 불편을 구체적으로 보고했고, 어떤 변화는 유지보수자가 원하는 제품 경계를 PR에 적었다. 실제 장애나 폴백이 계기가 된 경우도 있다. 반대로 커밋의 구조만 분명하고 저자의 설명은 남아 있지 않은 변화도 있다. 이 책은 그 차이를 지우지 않는다.

가장 강한 경우는 **명시적 요청이나 사건이 변경과 직접 연결된 때**다. [이슈 #102](https://github.com/openclaw/openclaw/issues/102)의 검색·승격 요청 자체는 명시적이지만, 후속 벡터 검색과 Dreaming이 이 이슈에 답했다는 직접 연결은 없어 기능적 대응 관계로만 다룬다. 반면 [이슈 #6877](https://github.com/openclaw/openclaw/issues/6877)은 플러시가 일일 파일을 덮어쓴 실제 손실과 수정 PR을, [이슈 #20730](https://github.com/openclaw/openclaw/issues/20730)은 CJK 어휘 검색 실패와 수정 PR을 직접 잇는다. [이슈 #90023](https://github.com/openclaw/openclaw/issues/90023)도 검색 실패가 약 70초의 전경 지연으로 바뀐 사건과 후속 변경을 연결한다. 이 세 경우에는 “사용자가 이런 문제를 겪었고 프로젝트가 이렇게 답했다”고 직접 말할 수 있다.

두 번째는 **PR이나 설계 문서가 선택 이유를 직접 설명한 경우**다. [PR #808](https://github.com/openclaw/openclaw/pull/808)의 논의는 하나의 메모리 플러그인만 기능을 소유해야 한다는 경계를 드러냈다. [PR #3160](https://github.com/openclaw/openclaw/pull/3160)은 QMD의 옵트인·격리·경로 안전·내장 백엔드 폴백 계약을 직접 명시하지만, QMD를 관리형 제품 백엔드로 채택한 더 넓은 선택 이유는 구현 계보에서 좁게 추론한다. [PR #13069](https://github.com/openclaw/openclaw/pull/13069)은 대규모 비동기 배치 처리량보다 보통 크기 재색인의 응답 시간을 우선한 이유를 수치와 함께 설명했다. 마지막 경우처럼 이유까지 적혀 있을 때만 구현 형태와 동기를 모두 명시적 근거로 삼는다.

세 번째는 **코드에서 좁게 추론한 설계 압력**이다. 3월의 소유권 리팩터처럼 프롬프트·플러시·도구·엔진이 선택된 플러그인 쪽으로 연속 이동한 사실은 코드와 테스트로 확정된다. 그러나 모든 커밋에 저자가 남긴 이유가 있는 것은 아니다. 이런 경우 이 책은 “대안 구현을 실제로 교체 가능하게 하려는 소유권 정리로 읽힌다”처럼 관찰된 구조가 허용하는 범위까지만 말한다.

마지막은 **맥락적 신호**다. [이슈 #48217](https://github.com/openclaw/openclaw/issues/48217)의 시작 직후 기억상실 보고와 런타임의 날짜별 노트 주입은 같은 실패 형태를 가리키지만, 구현 PR이 그 이슈를 원인으로 연결하지 않았다. Hindsight가 검색과 승격을 함께 생각하게 한 초기 제안의 배경이 된 것은 확인되지만, Dreaming PR이 Hindsight를 직접 근거로 삼았다는 증거도 없다. 이런 대응 관계는 아이디어의 계보를 설명할 수는 있어도 직접 인과로 쓰지 않는다.

따라서 “폴백 때문에 바뀌었다”는 말도 세분해야 한다. QMD가 없거나 검색에 실패할 때 내장 백엔드로 돌아가는 것은 **현재 코드의 복구 계약**이고, 그 계약의 범위는 PR 설명에서 확인한다. 반면 특정 폴백 사건이 다음 커밋을 직접 촉발했다고 쓰려면 연결된 이슈나 PR 문구가 따로 필요하다. 이 구분을 바탕으로 2장부터 7장은 각 변화 곁에 동기와 근거의 성격을 밝히고, [12장](12-landmark-index.md)은 41개 이정표를 한눈에 대조한다.

## 1. 프롬프트에 대한 희망을 런타임 강제로 바꾸다

가장 중요한 개선은 프롬프트를 더 유려하게 만든 일이 아니었다. 작업의 소유자를 바꾼 일이었다.

- 컴팩션이 전용 플러시 대화를 호출한다.
- 시작 문맥이 정확한 달력 날짜의 메모를 선택한다.
- Active Memory가 주 답변 전에 회상을 실행할지 결정한다.
- 대화 기록 접근은 정식 접근자를 통해 에이전트·세션 식별 정보를 운반한다.
- 오래된 상태는 런타임 폴백이 아니라 진단 도구가 마이그레이션한다.

프롬프트는 여전히 의미 판단에 유용하다. 그러나 이제 런타임이 판단이 **언제**, **어디서**, **어떤 범위 아래에서** 일어날지를 결정한다.

## 2. 코어 의미 메모리와 기계 상태를 분리하다

초기의 “Markdown은 기준 원본이고 인덱스는 재구축할 수 있다”는 생각은 `memory-core`에서 살아남았다. 달라진 것은 운영 상태의 정의다.

- 청크, 벡터, FTS 행, 리비전, 임베딩 캐시는 파생 인덱스 상태다.
- 회상 관찰, Dreaming 체크포인트, 잠금은 플러그인의 기계 상태다.
- 세션 이벤트는 정식 대화 상태다.
- Markdown은 기본 코어 경로에서 사람이 편집할 수 있는 의미 산출물로 남는다. 대안 플러그인은 별도의 의미 저장소를 소유할 수 있다.

이 분리는 복구를 가능하게 한다. 손상된 인덱스는 다시 만들 수 있고 이전 상태 파일은 옮길 수 있지만, 사용자의 메모를 불투명한 상태로부터 조용히 다시 생성해서는 안 된다.

## 3. 범위는 노출과 학습 전에 강제되지만, 일부는 검색 후 필터다

7월의 대화 간 경로는 서로 다른 범위 경계 두 개를 합성한다. 순서는 다음과 같다.

1. 신뢰된 `corpus=sessions` 회상은 순위화 전에 백엔드 소스 선택을 세션 컬렉션으로 제한할 수 있다.
2. `memory_search`는 그래도 `maxResults`를 백엔드에 전달한다.
3. 백엔드 검색이 끝난 뒤, 해당하는 세션별 사후 필터를 적용한다.
4. 이 필터를 통과한 검색 결과만 인용, 응답 노출, Dreaming 회상 추적으로 간다.

즉 **소스 선택은 백엔드 검색 전**, **세션별 권한 검사는 백엔드 검색 후**다. 두 경계를 하나로 뭉뚱그리면 실제 안전성과 결과 수를 잘못 이해하게 된다.

일반 세션 검색 결과에는 세션 도구 가시성과 에이전트 간 정책이 적용된다. 신뢰된 대화 간 검색 결과에는 다음 조건이 더 필요하다.

- 요청자가 신뢰되며 샌드박스 상태가 아닐 것
- 같은 에이전트 식별 정보일 것
- 앵커와 후보 별칭이 비공개일 것
- 현재 대화 기록이 아닐 것

DM 범위 설정은 기본 활성화와 키 형태에 영향을 주지만, 이 신뢰된 검색 결과별 판정식 자체를 대신하지 않는다. 필터는 인용, 응답 노출, Dreaming 회상 추적 전이지만 백엔드 검색이나 색인 뒤에 실행된다. 따라서 차단된 후보도 결과 슬롯을 소비할 수 있다. 현재의 [전체 순서](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/src/tools.ts#L620-L759)와 [사후 필터 분기](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/src/session-search-visibility.ts#L157-L275)가 이를 보여 준다.

반면 `sessions_search`는 다른 계약을 가진다. 보이는 대화 기록 검색 결과를 먼저 모으고 나서 최종 상한을 적용한다. 이는 [정확 검색 순서](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/src/agents/tools/sessions-search-tool.ts#L470-L510)에 명시되어 있다.

따라서 범위는 노출과 학습 전에 강제되지만, 백엔드 검색 단계에 포함되는 것은 소스 선택뿐이다. 세션별 권한 검사는 검색 후에 이뤄진다.

> **예시 — 합성 사례:** `memory_search`가 백엔드 상위 5개를 받은 뒤 두 검색 결과를 차단하면 세 개만 보일 수 있다. 반면 `sessions_search`는 보이는 검색 결과를 모은 뒤 최종 상한을 적용하므로 같은 최종 상한이라도 채우는 방식이 다르다. 이는 실행 순서를 설명하는 가상 예시이며 성능이나 실제 결과 수를 관측했다는 뜻이 아니다.

## 2025년 제안과 2026년 시스템 비교

이제 2025년 제안을 일종의 기준선으로 놓고 2026년 시스템을 다시 본다. 가운데 열은 현재까지 실제로 도달한 결과이고, 마지막 열은 구현 여부와 범위를 평가한다. 특히 기본 메모리 플러그인에서 실현된 원칙을 OpenClaw의 모든 메모리 구성에 보편적인 것으로 읽지 않는 것이 중요하다.

| 제안의 생각                           | 2026-07-18까지의 결과                                                                                     | 평가                                                      |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Markdown이 기준 원본이다              | 내장·QMD 경로가 보존했고 가져오기가 이동성을 강화했다. 대안 플러그인은 의도적으로 다른 저장소를 소유한다. | `memory-core`에서는 강하게 실현, 전체에 보편적이지는 않음 |
| 파생 SQLite 인덱스는 재구축할 수 있다 | 실현되었고, 나중에는 식별 정보와 원자적 게시를 갖춘 에이전트별 SQLite로 이동했다.                         | 강하게 실현                                               |
| FTS 우선, 임베딩은 나중               | 벡터가 먼저 출시되었고 하이브리드와 견고한 FTS 전용 동작이 뒤따랐다.                                      | 순서가 반대였음                                           |
| 오프라인 우선 운용                    | FTS 전용, 로컬 임베딩, Ollama, QMD를 사용할 수 있다. 초기·기본 의미 검색 설정은 OpenAI를 선호했다.        | 유일한 기본 경로가 아니라 선택지로 실현                   |
| 보존·회상·성찰 순환                   | 수명주기 포획, 메모리 도구, 회상 추적, Dreaming이 이제 이런 순환을 이룬다.                                | 다른 방식으로 실현                                        |
| 형식화된 엔터티·의견·신뢰도           | 내장 의미 메모리에는 포함되지 않았다.                                                                     | 대부분 미실현                                             |
| 출처와 모순                           | 검색 인용이 있으며 선택적 Memory Wiki가 더 풍부한 출처·린트를 추가한다.                                   | 인접 플러그인에서 부분 실현                               |
| 시간 충돌 처리                        | 날짜별 메모, 선택적 감쇠, 세션과 장기 기억의 순위화 시나리오, 행동 민감 지침이 있다.                      | 일급 진실 모델이 아니라 휴리스틱                          |
| 그래프 관계                           | 내장 메모리가 아니라 Memory Wiki 백링크로 존재한다.                                                       | 선택적·인접 기능                                          |
| 처음에는 무거운 SuCo 스택을 피한다    | SuCo/Subspace-Collision ANN 인덱스나 질의 구현을 채택하지 않았다.                                         | 따랐음                                                    |

표의 대비는 선명하다. 제안이 가장 정확했던 부분은 **구조**, 곧 투명한 원본과 파생 검색의 결합이었다. 가장 덜 실현된 부분은 **의미론**, 곧 형식화된 믿음, 신뢰도, 모순, 명시적 권한이었다. 그래서 이 책은 또 하나의 구분 없는 벡터 저장소를 더하는 일보다 이 의미론의 간극을 먼저 평가할 가치가 있다고 본다. 그러나 그것은 역사만으로 확정된 우선순위가 아니다. 결과 비교 증거가 실제 효용과 피해를 검증해야 한다.

## 다음 장으로

설계 원칙은 무엇을 지켜야 하는지는 말해 주지만, 다음 변화가 정말 더 나은지는 판정해 주지 않는다. 런타임이 작업을 맡았다고 해서 결과가 자동으로 좋아지는 것도 아니고, 더 많은 메모리가 검색되었다고 해서 미래 작업에 도움이 되었다고 말할 수도 없다.

다음 장에서는 역사 속 버그 보고, QA 카나리아, 인용, 회상 횟수, Dreaming 검토를 하나의 신호 장부로 모은다. 그런 다음 정보가 제시된 순간부터 나중 결과까지 어디에서 기억이 끊겼는지를 구분할 평가 언어를 세운다.
