# 2장. 기원: 메모리 모듈이 생기기 전

처음 해결하려던 문제는 거창한 지식 검색이 아니었다. 대화가 끊겨도 같은 세션을 이어 가고, 다음 시작 때 필요한 맥락을 다시 불러오며, 그 사이의 중요한 내용을 사용자가 직접 살펴볼 수 있는 곳에 남기는 일이었다. 그래서 OpenClaw 의미 메모리의 출발점은 데이터베이스가 아니라 사람이 읽고 고칠 수 있는 워크스페이스 파일이었다.

2025년 말에는 일일 기록과 장기 파일이라는 두 시간축이 생겼다. 이 단순한 구조는 투명성과 이동성을 얻었지만, 파일이 쌓일수록 무엇을 검색하고 무엇을 오래 남길지, 개인 정보를 어느 대화에서 불러와도 되는지라는 다음 문제가 드러났다. 파일명은 2025년의 기원을 강조하지만, 이 장은 그 압력이 수동 대화 기록 회상이라는 제품 표면으로 이어진 2026-01-07까지 추적한다.

## 0. 의미 메모리보다 먼저 존재한 세션 연속성 — 2025-11-24

가장 먼저 필요했던 것은 이미 시작한 대화를 다시 이어 가는 능력이었다. 이를 위해 발신자별·전역 Claude 세션 ID와 시각을 저장하고, 재개와 새 세션 인자, `/new`, 유휴 만료를 지원했다. 근거가 되는 [`9b4dceecfe69`](https://github.com/openclaw/openclaw/commit/9b4dceecfe69bb224a369a33a1c064003040aedd)는 `v0.1.0`에 처음 포함되었다.

> **변화의 동기.** 실제 압력은 재시작과 유휴 만료 뒤에도 대화의 연속성을 지키는 일이었다. 동기 출처는 초기 웹 공급자 구현의 커밋과 코드 구조이며, 증거 강도는 **코드에서 추론**이다. 대화 본문까지 보관하기보다 발신자별·전역 ID와 시각만 저장하는 최소 형태를 골라 세션 수명주기부터 해결했다.

이 선택으로 세션 연속성은 얻었지만 대화 본문이나 의미 있는 사실은 저장하지 않았다. 오늘날 세션 보관소로 이어지는 대화 연속성의 계보에 속할 뿐, 워크스페이스 의미 메모리의 시작으로 오인해서는 안 된다.

## 1. 사용자 전용 시작 메모리 파일의 등장 — 2025-11-27

세션 ID만으로는 사용자의 사실과 선호를 다음 시작에 되살릴 수 없었다. 2025-11-27의 Claude/WhatsApp 설정 예시는 그래서 워크스페이스에 메모리와 메모, 파일이 저장된다고 설명하고, 세션 시작 때 `peter.md`와 소문자 `memory.md`를 읽으라고 했다. 이 변경은 [`c43cdc5ac3d3`](https://github.com/openclaw/openclaw/commit/c43cdc5ac3d3058238b1ea5579d4700e5345c3b2)에 있으며, 선조 이력에서 찾은 가장 이른 출시 메모리 파일명이자 `v1.2.0`에 처음 포함된 형태다.

> **변화의 동기.** 실제 목표는 세션 ID로는 복원할 수 없는 사용자 사실과 선호를 시작 맥락에 다시 넣는 일이었다. 동기 출처는 사용자별 Claude/WhatsApp 설정 예시라는 설계 자료이고, 증거 강도는 **코드에서 추론**이다. 별도 데이터베이스보다 사람이 읽는 파일을 시작할 때 불러오는 형태가 당시 구성 방식과 가장 잘 맞았다.

사람이 읽는 파일이 시작할 때 인지 맥락으로 돌아온다는 방식은 얻었지만, 아직 저장소 전체의 워크스페이스 계약도 날짜별 기록 관례도 하위 시스템도 아니었다. 한 사용자에 맞춘 예시에 머물렀다는 것이 다음 한계였다.

## 2. 워크스페이스가 내구성 있는 에이전트 상태가 되다 — 2025-12-14

사용자 한 명의 설정 예시를 일반 에이전트의 내구성 있는 상태 계약으로 넓힐 필요가 있었다. 일반 에이전트 워크스페이스를 초기화하고 메모와 임시 파일, “메모리”가 그곳에 속한다고 명시한 [`073285409b4c`](https://github.com/openclaw/openclaw/commit/073285409b4cd24eb7888832b917f423b20b6d10)는 `v2.0.0-beta1`에 처음 포함되었다. 이어 [`a5b3b8743a27`](https://github.com/openclaw/openclaw/commit/a5b3b8743a2782856172975cb8896ca4978290d2)은 백업을 위해 비공개 Git 저장소를 권고했다.

> **변화의 동기.** 실제 압력은 한 사용자에게 묶인 예시를 모든 에이전트가 쓸 수 있는 내구성 계약으로 일반화하고, 그 상태를 사용자가 백업할 수 있게 하는 일이었다. 동기 출처는 워크스페이스 초기화와 백업 지침을 잇달아 정리한 설계 커밋이며, 증거 강도는 **코드에서 추론**이다. 그래서 상태의 소유 지점을 워크스페이스로 모으고, 기존 Git 도구로 복구할 수 있는 형태를 택했다.

이로써 내구성 있고 사용자가 소유하는 워크스페이스 상태가 일반화되었다. 다만 워크스페이스 템플릿에는 표준 메모리 파일명이 아직 없어, 같은 철학을 일관된 파일 관례로 만들 과제가 남았다.

## 3. 일일 Markdown이 메모리 관례가 되다 — 2025-12-19

일관된 파일명이 없으면 에이전트도 사람도 어디에 무엇을 남기고 다시 읽어야 하는지 알기 어려웠다. 중앙화된 워크스페이스 템플릿은 이 문제를 날짜별 Markdown 관례로 풀었다. 현재까지의 이력에서 찾은 가장 이른 표준 전용 메모리 배치는 [`590f3d0e8f28`](https://github.com/openclaw/openclaw/commit/590f3d0e8f285d02e594cd718bfe9350ea5ee267)이며, `v2.0.0-beta2`에 처음 포함되었다.

- 일일 기록을 `memory/YYYY-MM-DD.md`에 만든다.
- 세션 시작 때 오늘과 어제의 기록을 읽는다.
- 사실, 선호, 결정, 오래 유지할 맥락을 기록한다.
- 명시적으로 요청받지 않는 한 비밀 정보를 피한다.

> **변화의 동기.** 실제 목표는 에이전트와 사람이 기록 위치와 읽기 시점을 매번 새로 정하지 않게 하는 일이었다. 동기 출처는 중앙 워크스페이스 템플릿을 만든 설계 정리이고, 증거 강도는 **코드에서 추론**이다. 날짜별 Markdown과 평범한 파일 도구를 골라 투명성·이동성을 지키면서도 최소한의 공통 관례를 만들었다.

이 선택으로 **에이전트는 평범한 파일 도구로 자신의 메모리를 쓸 수 있고, 사람은 전용 서비스 없이 결과를 검사하거나 편집할 수 있게 되었다.** 그러나 검색 데이터베이스나 도구, 플러그인, 구조화된 스키마는 없었다. “모듈”은 워크스페이스 지침에 들어 있는 행동 규약에 불과했으므로, 파일이 늘어난 뒤 원하는 사실을 찾는 문제는 그대로 남았다.

> **예시 — 합성 사례:** 2025-12-19의 관례만으로도 에이전트는 `memory/2025-12-19.md`에 “사용자는 배포 전에 변경 요약을 원한다” 같은 문장을 쓸 수 있었다. 하지만 이를 의미 검색으로 찾거나 자동 승격하는 제품 하위 시스템은 아직 없었다. 이 문장은 형식을 설명하는 가상 내용이며 실제 기록이 아니다.

## 4. 최초의 표준 두 시간축 모델 — 2025-12-20

날짜별 기록은 쓰기 쉬웠지만, 오래 쓸 사실과 선호를 매번 연대기에서 다시 골라내기에는 불편했다. 그래서 일일 기록과 나란히 오래 유지할 사실, 선호, 결정을 위한 루트 소문자 `memory.md`를 두었다. 근거인 [`cfd3efb6e767`](https://github.com/openclaw/openclaw/commit/cfd3efb6e767bcab8bbc2617913be2259e953bbb)도 `v2.0.0-beta2`에 처음 포함되었다.

> **변화의 동기.** 실제 압력은 최근 기록의 상세함을 잃지 않으면서 반복해서 쓸 사실을 짧게 읽는 일이었다. 동기 출처는 템플릿 지침의 설계 변경이며, 증거 강도는 **코드에서 추론**이다. 기존 일일 기록을 대체하지 않고 루트 장기 파일을 나란히 두어 두 시간축을 분리했다.

이 선택으로 **상세한 최근 연대기와 압축된 장기 메모리**라는 두 계층 모델을 얻었다. 1월의 대문자 이름 변경이 이 모델을 처음 만든 것은 아니다. 다만 어떤 정보를 어느 계층으로 옮길지와 커지는 파일을 어떻게 검색할지는 아직 사람이나 모델의 규율에 달려 있었다.

## 5. 오프라인 메모리 제안 — 2025-12-23

두 파일 계층이 생기자 약점도 구체적으로 보였다. 일일 Markdown은 재현율 높은 조회, 개체 중심 질문, 신뢰도가 변하는 의견, 시간에 따른 충돌에 약했다. 나중에 삭제되었지만 원래 의도를 가장 명료하게 밝힌 설계 제안은 이 문제를 다음 목표로 정리했다. 제안은 [`760a83d256d6`](https://github.com/openclaw/openclaw/commit/760a83d256d63b55905681cadac60bebca684b73)에서 추가되어 `v2.0.0-beta3`에 처음 포함되었다.

> **변화의 동기.** 실제 압력과 목표는 파일 관례만으로 부족한 검색 재현율·시간 충돌·출처 설명을 보완하되, 사용자가 읽는 Markdown을 정본으로 지키는 일이었다. 동기 출처는 제안서 자체의 문제 진술이며, 증거 강도는 **명시적**이다. 그래서 곧바로 복잡한 SuCo를 채택하지 않고 재구축 가능한 SQLite FTS5와 선택적 임베딩부터 검증하는 점진적 형태를 골랐다.

- 오프라인 우선, 설명 가능, 절차가 간결한 점진적 운용
- 정본으로서의 Markdown
- 선택적 임베딩을 곁들인 재구축 가능한 SQLite FTS5 색인
- 명시적인 보존·회상·성찰 단계
- 이후 개체, 의견, 출처, 그래프형 연결 지원

제안은 [Letta 메모리 블록](https://docs.letta.com/guides/core-concepts/memory/memory-blocks)과 [맥락 계층](https://docs.letta.com/guides/core-concepts/memory/context-hierarchy), [Hindsight](https://arxiv.org/abs/2512.12818), [SuCo](https://arxiv.org/abs/2411.14754)를 인용했다. 이 이름들은 완제품 후보의 목록이 아니라, 서로 다른 설계 아이디어와 도입 시점을 비교하기 위한 나침반이었다.

| 이름      | 당시 제안에서 대표한 아이디어                                                                                | OpenClaw가 택했거나 미룬 것                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Letta     | 작고 중요한 기억은 늘 문맥에 두고, 나머지는 도구로 찾아 명시적으로 고치는 계층형 제어 방식                   | 작은 장기 파일과 필요할 때 찾는 기록을 나누는 방향에 영향을 주었지만 Letta 구현이나 형식을 가져오지는 않았다.               |
| Hindsight | 관찰·믿음·요약을 구분하고, 보존(retain)·회상(recall)·성찰(reflect)을 이어 신뢰도가 변하는 기억을 다루는 방식 | 제안의 북극성 모델이 되었고 뒤의 검색·승격 기능과 닮았지만, 후속 Dreaming 구현의 직접 원인이나 가져온 코드라는 증거는 없다. |
| SuCo      | 큰 벡터 코퍼스에서 부분 공간 충돌을 이용해 가까운 이웃을 빠르게 찾는 연구형 근사 검색                        | 제안은 **SuCo로 시작하지 말라**고 명시했고, 현재의 내장 코어도 이를 채택하지 않았다.                                        |
| HNSW      | 벡터 수가 많아 전수 비교가 느려질 때 쓰는 일반적인 그래프형 근사 검색                                        | 규모와 지연이 실제 병목이 된 뒤 검토할 후보로만 남았고 이 제안 단계에서는 채택하지 않았다.                                  |
| ScaNN     | 대규모 벡터 검색의 속도와 재현율을 절충하는 또 다른 근사 검색 계열                                           | HNSW와 마찬가지로 미래의 규모 문제가 정당화할 때만 검토할 후보였으며 채택하지 않았다.                                       |

따라서 실제 시작점은 재구축 가능한 SQLite 전문 검색(FTS5)과 선택적인 단순·전수 임베딩 검색이었다. 코퍼스 규모와 지연 시간, 회상 병목이 정당화할 때만 더 복잡한 근사 검색을 고려하라는 점진적 계획이었다. 이는 아키텍처에 준 영향이지 외부 코드를 가져온 것이 아니다.

제안은 투명한 원본과 파생 검색이라는 방향을 얻었지만, 이후 실제 구현은 유용한 방식으로 달라졌다.

- 제안된 FTS 우선 순서보다 벡터 검색이 먼저 출시되었다.
- 형식화된 개체·의견 저장소는 내장 코어가 되지 않았다.
- FTS 전용, 로컬 임베딩, QMD가 뒤에 오프라인 경로를 회복했다.
- Dreaming은 명시적인 의견 신뢰도 대신 관찰된 검색을 사용해 보존·회상·성찰 순환을 구현했다.
- Memory Wiki는 주장, 출처, 모순, 역방향 링크를 인접한 선택적 계층으로 제공했다.

## 6. 검색과 승격을 잇는 공개 유지관리자 요청 — 2026-01-02

파일을 찾는 일과 중요한 내용을 장기 계층으로 올리는 일은 서로 떨어진 문제가 아니었다. 제대로 된 벡터 기반 메모리 시스템과 일일 메모리를 장기 메모리로 승격할 방법을 함께 요구한 [Issue #102, “Better Memory System”](https://github.com/openclaw/openclaw/issues/102)은 후대 아키텍처의 두 절반을 연결하는 가장 명료한 공개 유지관리자 요청이며 Hindsight 논문도 링크했다.

> **변화의 동기.** 실제 목표는 검색과 승격을 하나의 메모리 문제로 다루는 일이었다. 동기 출처는 유지관리자가 작성한 Issue #102이고, 증거 강도는 그 요청 자체에는 **명시적**이다. 다만 뒤의 벡터 검색·Dreaming이 이 요청에 대응한다는 사실은 기능의 대응 관계일 뿐, 그 구현 형태가 Hindsight에서 직접 나왔다는 인과는 입증되지 않았다.

벡터 검색은 1월에 출시되었다. 에이전트 주도 승격은 먼저 1월 6일 워크스페이스 지침으로 출시되어, 하트비트 작업이 일일 기록을 검토하고 오래 유지할 항목을 `MEMORY.md`에 정제하도록 했다. 4월의 Dreaming은 승격을 관찰된 검색에 따라 점수화하고, 임계값과 일정, 상태를 두며, 측정할 수 있게 만들었다.

이것은 **기능의 대응 관계**이지 직접 인과관계의 증명이 아니다. 이 조사에서 찾은 후속 Dreaming PR이나 코드는 Hindsight를 인용하지 않는다.

여전히 승격과 검색을 어떻게 함께 설계할지는 열려 있었다. 초기 커뮤니티 구현 제안인 [PR #302](https://github.com/openclaw/openclaw/pull/302)는 수신함·사서 흐름, 명시적인 기억·회상·통합 도구, 예약 작업, 크기 상한, 퇴출, 그룹 격리를 탐색했다. 작성자가 더 많은 개인 테스트를 위해 닫았고 출시되지 않았다. 제품 설계가 안정되기 전부터 통합, 제한된 증가, 프라이버시가 결합된 문제로 인식되었다는 증거로 유용하다.

> **변화의 동기.** PR #302가 가정한 설계 압력은 통합 과정의 저장량 증가와 그룹 프라이버시였다. 이는 당시 커뮤니티가 탐색한 **맥락적 증거**이며 이후 구현의 직접 원인은 입증되지 않았다. 수신함·사서 구조는 한 후보였을 뿐이며, 닫힌 미출시 PR을 이후 제품 설계의 원인으로 읽어서는 안 된다.

## 7. 외부 QMD와 “기록하라”는 원칙 — 2026-01-03

자체 검색 엔진이 없던 시기에도 늘어난 파일에서 의미상 가까운 내용을 찾을 필요는 있었다. [QMD(Query Markup Documents)](01-current-architecture.md#qmd-explained)는 문서를 기기 안에서 색인하고 어휘·의미 질의를 수행하는 별도 로컬 검색 프로그램이다. 워크스페이스 에이전트에게 외부 `qmd` 명령으로 의미 회상을 수행하라고 가르친 [`7e4e9ecdeaf8`](https://github.com/openclaw/openclaw/commit/7e4e9ecdeaf8849dbe464f31e50f4932c88904a3)은 `v2.0.0-beta5`에 처음 포함되었다. 아직 OpenClaw QMD 백엔드는 아니었고, 안정된 검색 엔진 전에 시도한 로컬 의미 검색 실험이었다.

같은 날 [`c2a74d6d2a1b`](https://github.com/openclaw/openclaw/commit/c2a74d6d2a1bd57889ff4bb1d7e43621f49e3c63)은 명시적인 지속성 원칙을 추가했다. 머릿속 메모는 세션 재시작을 견디지 못하지만 파일은 견딘다는 원칙이다.

외부 명령에 기대는 방식은 제품이 소유하는 수명주기가 없다는 한계를 남겼다. 자체 검색이 자리 잡은 뒤 외부 QMD 지침은 1월 12일 [`31752aa9445c`](https://github.com/openclaw/openclaw/commit/31752aa9445cb4b16b14f0e3d5a0a822a25cd436)에 의해 제거되었다. QMD는 한 달 뒤인 2월에 수명주기를 제품이 관리하는 백엔드로 돌아왔다.

> **변화의 동기.** 외부 `qmd`로 의미 검색을 시도한 이유와 후속 제거 이유는 커밋 흐름에서 **코드로 추론**한다. 반면 [`c2a74d6d2a1b`](https://github.com/openclaw/openclaw/commit/c2a74d6d2a1bd57889ff4bb1d7e43621f49e3c63)은 “머릿속 메모는 세션을 넘지 못하지만 파일은 남는다”는 영속화 이유를 직접 밝혀 **명시적 증거**다. QMD 지침은 네이티브 검색 착지 뒤 제거되었지만, 제거 커밋이 그 인과를 설명하지는 않는다.

## 8. 대문자 선별 메모리에 명시적 프라이버시 의도가 생기다 — 2026-01-06

일일 기록은 덧붙이기에는 적합했지만 압축된 개념 모델이 아니었고, 오래 유지되는 개인 맥락은 노출 위험도 만들었다. 그 준비는 조금 앞서 있었다. 2025-12-22에 워크스페이스 템플릿에 들어온 스마트 하트비트 지침은, 사용자의 새 요청이 없어도 정해진 주기마다 에이전트가 스스로 도는 실행 시간을 메일·일정 점검과 배경 작업에 쓰게 했고 그 목록에 메모리 파일 정리를 포함했다. 그 흐름의 근거가 [`ca806897c251`](https://github.com/openclaw/openclaw/commit/ca806897c251cfbc333e11b4bdf71d18478783ae)이다.

선택은 장기 계층을 대문자 선별 파일 `MEMORY.md`로 다듬고 보안 원칙을 붙이는 것이었다. 개인 정보가 들어 있을 수 있으므로 공유 맥락이 아니라 주 세션이나 직접 세션에서만 불러오도록 했다. [`7d1fee70e76f`](https://github.com/openclaw/openclaw/commit/7d1fee70e76f2f634f1b41fca927ee663914183a)는 `v2026.1.8`에 처음 포함되었고, [`9ffea23f31ca`](https://github.com/openclaw/openclaw/commit/9ffea23f31ca1df5183b25668f8f814bee0fb34e)는 최근 기록을 다시 읽어 오래 유지할 사실을 정제하고 낡은 항목을 제거하는 하트비트 유지보수를 더했다.

> **변화의 동기.** 실제 압력은 일일 기록을 압축된 장기 모델로 정제하면서 개인 맥락이 공유 대화로 새지 않게 하는 일이었다. 동기 출처는 보안 경계와 정제 목적을 직접 밝힌 [`7d1fee70e76f`](https://github.com/openclaw/openclaw/commit/7d1fee70e76f2f634f1b41fca927ee663914183a)와 [`9ffea23f31ca`](https://github.com/openclaw/openclaw/commit/9ffea23f31ca1df5183b25668f8f814bee0fb34e)이며, 증거 강도는 **명시적**이다. 대문자 선별 파일, 주기적 정제, 주·직접 세션 제한을 함께 두어 장기 계층의 역할과 공개 범위를 분리했다.

1월이 두 계층 자체를 발명한 것은 아니다. 얻은 것은 장기 계층을 선별된 대문자 파일로 만들고, 주기적으로 관리하며, 명시적으로 비공개 취급한 일이었다. 그러나 정제는 여전히 에이전트의 판단과 주기적 지침에 의존했다. 이후 Dreaming이 같은 통합 개념을 자동화하고 계측하지만, 기본 비활성인 선택 기능이므로 이 지침을 걷어내지는 않는다. 기본 경로의 승격은 지금도 하트비트 정제로 남는다.

## 9. 수동 대화 기록 회상이 세션 로그에 닿다 — 2026-01-07

메모리 파일에 남기지 않은 사실도 과거 대화에는 있을 수 있었다. 이 공백을 메우기 위해 전체 대화 이력을 검색하는 `session-logs` 스킬이 생겼다. `jq`로 세션 JSONL에서 읽을 수 있는 텍스트를 추출하고 세션 간 어휘 검색을 사용한 [`388796253a03`](https://github.com/openclaw/openclaw/commit/388796253a0380f47cae15a434f1f1e33b034ce1)은 `v2026.1.8`에 처음 포함되었다.

> **변화의 동기.** 실제 압력은 메모리 파일에 선별되지 않은 사실도 과거 대화에서 되찾는 일이었다. 동기 출처는 대화 이력 검색 스킬을 추가한 구현 커밋이며, 증거 강도는 **코드에서 추론**이다. 통합 색인과 권한 계층이 없던 시기라 `jq`와 셸 어휘 검색을 쓰는 수동·저비용 형태를 택했다.

과거 대화 기록을 회상해야 한다는 별도의 제품 요구가 실험적인 임베딩 기반 세션 소스보다 열흘 앞서 드러났지만, 구현은 스킬이 이끄는 수동 셸 조회였다. 통합 색인, 권한 부여 계층, 모델 도구가 없다는 한계는 다음 시기의 과제가 되었다.

## 다음 장으로

2025년 말과 2026년 1월 초의 관례는 사람이 이해하고 소유할 수 있는 메모리 원본을 만들었다. 동시에 “써야 기억된다”, “파일이 있어도 찾아야 쓸 수 있다”, “개인 기억은 아무 대화에서나 불러오면 안 된다”는 세 압력을 함께 남겼다.

다음 장에서는 이 압력이 런타임의 마지막 저장 기회, 자체 검색, 두 가지 수집 모델, 배타적 플러그인 슬롯, 관리형 QMD로 구체화되는 2026년 1월과 2월을 따라간다.
