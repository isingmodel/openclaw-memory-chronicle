# 6장. 2026년 5월과 6월: 권한, 실패의 투명성, 데이터베이스 우선 상태

기억이 더 자주 검색되고 승격되자 관련성만으로는 답할 수 없는 질문이 생겼다. 과거 대화에서 찾은 문장이 지금 행동해도 된다는 승인인지, 임베딩 제공자가 바뀐 색인을 계속 믿어도 되는지, 재구축 가능한 상태를 버려도 되는지 같은 문제였다.

5월과 6월의 변화는 권한과 운영 상태를 분명히 했다. 행동 권한은 기억 본문에서 추론하지 않고 명시적으로 기록하며, 제공자와 색인의 정체성이 맞지 않으면 조용히 하향 전환하지 않았다. Dreaming 상태와 기억 색인은 SQLite로 옮기고 대화 기록 발견은 정식 접근자 뒤로 모았다. 얻은 것은 진단 가능성과 명확한 소유자였지만, 마이그레이션 비용과 문서 불일치가 새 과제로 남았다.

## 검색된 사실은 자동으로 행동 권한이 되지 않는다

기억 내용이 외부 행동에 영향을 줄 때 관련성과 신뢰도만으로는 “사용자가 한때 이것을 보내는 일을 논의했다”와 “사용자가 지금 이것을 보내도록 허가했다”를 구분할 수 없다. 해결책은 승인, 만료, 권한, 철회, “행동해도 안전함”의 경계를 선호처럼 보이는 문장에서 추론하지 않고 명시적으로 기록하는 것이었다. 행동에 민감한 메모리 지침(memory guidance)을 갱신한 [PR #82788](https://github.com/openclaw/openclaw/pull/82788)은 [`bd04b1ea7cc0`](https://github.com/openclaw/openclaw/commit/bd04b1ea7cc0ff51a423360d0eb1a543a9c07a25)으로 병합되었다.

코드가 아니라 문서만 바꾼 변경이지만 의미상의 전환은 컸다. 미래의 구조화된 기억은 권한과 시간적 유효성을 일급 차원으로 다뤄야 한다는 과제를 분명히 했다.

> **변화의 동기.** 유지보수자 제품 요청에서 나온 **명시적 증거**다. PR #82788은 평문 Markdown의 낮은 부담을 유지하면서도 승인, 임시 제약, 인계, 만료, 출처 권한이 필요한 메모리에는 행동 경계를 적어야 한다고 직접 설명했다. 모든 메모에 스키마를 강제하지 않고 행동에 민감한 기록만 명시적으로 보강한 것은, 단순한 사실 보존과 현재의 실행 허가를 구분하면서 기존 작성 방식을 지키기 위해서다.

> **예시 — 합성 사례:** “다음 회의 뒤 보고서를 팀에 보내는 방안을 검토하자”는 메모는 주제 관련성은 높아도 발송 승인이 아니다. 실제 승인 상태, 대상, 만료 시점이 별도 필드나 명시적 문장으로 없다면 이를 현재 권한으로 해석해서는 안 된다. 이는 원리를 설명하는 가상 예시다.

## 조용한 성능 저하를 명시적인 신뢰성 문제로 바꾸다

5월과 6월 초의 반복된 사용자 문제는 “검색 결과가 없다”는 증상만으로 원인을 알 수 없다는 것이었다. 작업자 정리, 임베딩 배치 한도, 대체 벡터 점수화(fallback scoring), FTS 오류, 제공자 초기화, 색인 정체성을 고친 변경들이 두 원칙으로 모였다.

- 일시적으로 임베딩 제공자를 사용할 수 없다고 해서, 이전까지 벡터를 지원하던 색인이 조용히 손상되거나 하향 전환되어서는 안 된다.
- 저장된 색인 정체성은 재사용 전에 제공자, 모델, 차원, 토크나이저, 코퍼스 가정과 일치해야 한다.

여기에는 서로 다른 실패가 섞여 있었다. 무엇이 보존되고 누가 고치는지를 먼저 나누면 뒤의 커밋 계보가 쉬워진다.

이 표는 수정들을 하나의 원인으로 합치지 않는다. 아래의 세부 이력은 각 행이 어떤 보고와 변경에서 나왔는지 보여 준다.

색인 정체성을 명시적으로 검증하고, 제공자 `none` 후속 변경에서는 오프라인 FTS 색인이 오해를 부르는 벡터 상태를 품지 않고 FTS 전용으로 남게 했다. 전자의 근거는 [`a4b4fed41287`](https://github.com/openclaw/openclaw/commit/a4b4fed41287e267735a93d82cc4ff7e8e180c5b)이다. 이 수정들은 관측 가능성을 “검색 결과가 없다”에서 진단 가능한 제공자·색인 계약으로 옮겼다.

> **변화의 동기.** 제공자 변경으로 생긴 회귀 위험과 유지보수자 요청에서 나온 **명시적 증거**다. PR #87907은 저장된 제공자·모델·설정과 현재 설정이 다를 때 낡은 벡터 색인을 신뢰하는 문제를 직접 밝혔다. 시작이나 첫 검색에서 비싼 전체 재색인을 조용히 실행하지 않고 검색을 멈춘 채 진단과 명시적 수리를 요구한 것은, 호환되지 않는 결과와 예기치 않은 비용을 모두 피하기 위해서다.

재구축 실패가 정상적으로 검색 가능한 기존 상태를 일부 결과로 덮는 문제도 막아야 했다. 재색인이 실패하면 운영 중인 SQLite 색인을 보존하고, 그림자 결과는 예상 리비전과 일치할 때만 게시하도록 바꾼 근거가 [`865fdab07501`](https://github.com/openclaw/openclaw/commit/865fdab07501b5d85b4057d06b22e0ce907300e7)이다.

> **변화의 동기.** 실제 재색인 실패인 Issue #91216에서 나온 **명시적 증거**다. 커밋 본문은 교체 도중 대상 데이터베이스가 비거나 WAL/SHM 보조 파일과 어긋날 수 있는 실패를 설명한다. 그래서 살아 있는 색인을 그대로 둔 채 그림자 데이터베이스를 완성하고 예상 리비전까지 확인한 뒤 한 번에 게시해, 복구 작업 실패가 정상 검색 상태를 파괴하지 않게 했다.

성능 실패는 벤치마크에만 머물지 않고 사용자에게 보였다. [Issue #81172](https://github.com/openclaw/openclaw/issues/81172)는 대체 코사인 스캔(fallback scan)이 Node를 1분 넘게 막아 Discord 연결을 끊었다고 보고했다. [PR #83758](https://github.com/openclaw/openclaw/pull/83758)은 점수를 바꾸지 않은 채 제한된 배치로 처리하고 이벤트 루프에 제어를 양보했다. [PR #91841](https://github.com/openclaw/openclaw/pull/91841)은 나중에 동기화마다 전체 디렉터리를 다시 훑는 대신 변경 표시된 대화 기록 세션만 대상으로 삼았다. [PR #73976](https://github.com/openclaw/openclaw/pull/73976)은 AND로 결합한 대화형 질의가 종종 FTS 검색 결과를 하나도 내지 못했기 때문에 키워드별 어휘 부채꼴에 상한을 추가했다.

> **변화의 동기.** 장애 보고와 운영 측정에서 나온 **명시적 증거**다. Issue #81172와 PR #83758은 동기식 전체 코사인 스캔이 수십 초 동안 이벤트 루프와 채널 연결을 막는다고 연결했고, PR #91841과 #73976은 반복 전체 탐색과 지나치게 엄격한 어휘 질의라는 별도 병목을 좁혔다. 점수식을 바꾸기보다 제한된 배치에서 제어권을 양보하고, 이미 더티로 표시된 세션과 제한된 키워드 부채꼴만 처리한 것은 기존 검색 의미를 지키면서 요청당 작업량을 상한 안에 두기 위해서다.

소유권 측면에서는 [PR #85072](https://github.com/openclaw/openclaw/pull/85072)가 기억 전용 임베딩 등록에서 공용 제공자 연결부로의 이동을 마무리했다. 하지만 제공자나 모델 변경을 확인하지 않으면 호환되지 않는 벡터가 섞이거나 예상치 못한 유료 재임베딩이 실행될 수 있다. [PR #87907](https://github.com/openclaw/openclaw/pull/87907)이 이 위험을 직접 설명한다. 더 안전한 상태는 명시적 복구 경로가 선택될 때까지 멈추고 진단하는 것이다.

파일이 올바르더라도 임베딩 설정과 온보딩 오류 때문에 기억이 고장 난 것처럼 보일 수 있다. [Issue #16670](https://github.com/openclaw/openclaw/issues/16670)은 여전히 유용한 사용자 수준 신호다. 다만 일부 세부 사항은 성숙한 FTS 전용 경로보다 오래되었으므로, 현재 모든 버전의 포괄적 결함으로 취급하지 말고 대상 버전에서 재현해야 한다.

> **변화의 동기.** 설계·소유권 정리와 제공자 전환 위험에 대한 **명시적 증거**다. PR #85072는 메모리 전용 등록을 일반 임베딩 제공자 연결부의 하위 호환 경로로 축소했고, PR #87907은 제공자·모델 변경 뒤 기존 벡터를 조용히 재사용하거나 유료 재임베딩하지 않아야 할 이유를 직접 적었다. 따라서 등록 소유자는 공용 연결부로 모으되, 정체성이 어긋난 색인은 명시적 수리 전까지 멈추고 진단하게 했다. Issue #16670은 설정 실패가 체감 품질을 낮춘다는 **맥락적 증거**이며, 이 두 PR의 직접 원인으로 연결되지는 않는다.

## Dreaming 기계 상태를 보조 JSON에서 SQLite로 옮기다

Dreaming이 커지면서 회상 상태, 단계 신호, 수집 체크포인트, 잠금을 `.dreams/` JSON 상태와 잠금 파일에 나눠 두는 방식이 어긋남과 소유권 모호성을 만들었다. 해결책은 이를 SQLite 기반 플러그인 상태로 옮기는 것이었다. [PR #91056](https://github.com/openclaw/openclaw/pull/91056)은 [`3f5e00184431`](https://github.com/openclaw/openclaw/commit/3f5e00184431f10a7ae55c59ce8d3c6cb0d0a0eb)을 통해 병합되어 `v2026.6.7-alpha.1`에 처음 포함되었다.

진단·수리 도구인 `doctor`는 영속 JSON 상태를 이관하고 보관하지만 일시적인 과거 잠금 파일은 가져오지 않고 의도적으로 제자리에 남긴다. 당시의 [`doctor` 계약](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/doctor-contract-api.ts#L1085-L1105)이 이 경계를 명시한다.

그 결과 아키텍처 경계는 다음과 같이 일관되게 정리되었다.

- 사용자에게 보이는 의미 산출물은 Markdown이나 텍스트로 남는다.
- 기계 상태, 커서, 잠금, 카운터는 SQLite를 사용한다.
- 오래된 파일 상태는 마이그레이션 입력일 뿐 런타임 대체 경로가 아니다.

현재 공식 문서는 이 변경을 따라잡지 못했다. 이 계약 차이는 이 책의 [현재 계약의 간극](10-current-contract-gaps.md)에서 별도로 다룬다.

> **변화의 동기.** 설계·소유권 정리에서 **코드로 추론한 증거**다. PR #91056은 지속 상태를 `.dreams/*.json`에서 SQLite 플러그인 상태로 옮기고, doctor가 영속 자료만 이관하며 일시적 잠금·캐시는 남긴다는 구현 범위는 명시하지만 별도의 선택 이유는 적지 않았다. 런타임에서 두 저장소를 함께 읽는 호환층 대신 일회성 doctor 마이그레이션을 택한 형태는 권위 저장소를 하나로 만들고 재구축 가능한 상태를 영구 호환 부채로 남기지 않으려는 소유권 정리로 읽힌다.

## 메모리 색인을 에이전트별 데이터베이스에 합치다

독립 색인은 에이전트 정체성, 정리, 백업, 권한 부여를 별도 보조 파일에 흩뜨렸다. 기억 색인을 에이전트별 SQLite 데이터베이스로 옮기고 설정 가능한 독립 `store.path`를 제거한 선택은 이 소유권을 모았다. [PR #94646](https://github.com/openclaw/openclaw/pull/94646)의 병합 묶음은 [`f324f7e2813a`](https://github.com/openclaw/openclaw/commit/f324f7e2813a52e07c515143e041be6ce7bca1d3)에서 시작해 [`65eb2ccd4ae2`](https://github.com/openclaw/openclaw/commit/65eb2ccd4ae254154a026d9883eb18b2eef27079)에 착지했고, `v2026.6.9-beta.1`에 처음 포함되었다.

이는 단순한 저장소 통합이 아니었다. 에이전트 범위의 소유권은 권한 부여, 정리, 백업, 정체성을 더 명확하게 하고 독립 보조 파일 사이의 어긋남을 줄였다. OpenClaw 소유 상태에 적용되는 저장소 전반의 데이터베이스 우선 원칙과도 기억을 맞췄다. 다만 첫 구현은 이전 독립 색인을 가져오지 않아 기존 파생 색인 내용을 뒤에 남겼다.

첫 구현은 마이그레이션 실패를 드러냈다. 한 보고자는 색인이 조용히 이동한 뒤 1,499개 파일을 다시 임베딩해야 했다. [PR #95631](https://github.com/openclaw/openclaw/pull/95631)은 [`414c250af90d`](https://github.com/openclaw/openclaw/commit/414c250af90d0e19d44b407cf31b32a2221956c4)으로 병합되었고 `v2026.7.1-beta.1`에 처음 포함되어 doctor 소유 보조 색인 가져오기를 추가했다.

이 사례는 강력한 업그레이드 교훈을 준다. “파생되어 재구축할 수 있다”는 말은 재구축에 시간, 대역폭, 비용이 들 때 “버려도 공짜다”라는 뜻이 아니다. 파생 상태에도 명시적인 마이그레이션·재구축 결정과 경고가 필요하다.

> **변화의 동기.** 근거 강도가 다른 두 단계를 나눠야 한다. PR #94646은 데이터베이스 우선 통합이라는 범위는 명시하지만, 에이전트 식별 정보·백업·정리를 한 경계로 모은 이점은 코드와 저장소 정책에서 **추론한 설계 동기**다. 반면 Issue #95495는 기존 보조 색인을 옮기지 않아 1,499개 파일을 다시 임베딩한 실제 업그레이드 비용을 보고했고, PR #95631은 이를 직접 닫은 **명시적 사건 근거**다. 후속 수정이 런타임 이중 읽기 대신 doctor의 검증된 가져오기와 재시도 가능한 원본 보존을 택한 것은, 정상 경로를 하나로 유지하면서 유료·장시간 파생 상태도 안전하게 승계하기 위해서다.

## 대화 기록 접근에 정식 코퍼스 경계를 세우다

소비자가 저장소 배치 가정에 기대 대화 기록을 반복해서 재발견하면 소유권과 정체성이 요청 경로마다 흔들릴 수 있었다. 이를 접근자 기반 코퍼스로 대체해 각 항목이 경로, 세션 ID와 키, 에이전트 소유권, 산출물·생성 세션 표지와 Dreaming, [QMD 세션 내보내기](01-current-architecture.md#qmd-explained), 세션 기억 동기화에 필요한 사실을 함께 운반하도록 했다. [PR #96162](https://github.com/openclaw/openclaw/pull/96162)는 [`c24d266b2d09`](https://github.com/openclaw/openclaw/commit/c24d266b2d0943a2376ae9ac87a2fd8e200920e1)로 병합되어 `v2026.6.11-beta.1`에 처음 포함되었다.

정식 접근자는 소유권과 정체성을 앞 단계에서 뒤 단계로 전달하므로 반복적인 파일시스템 탐색보다 안전하고 저렴했다. 동시에 7월의 SQLite 세션 마이그레이션 전에 필요한 토대가 되었고, 트랜스크립트 소비자들이 공통의 소유권·정체성 정보를 쓰는 코퍼스 경계를 제공했다.

> **변화의 동기.** 설계·소유권 정리에 대한 유지보수자 요청에서 나온 **명시적 증거**다. PR #96162는 Dreaming, QMD 내보내기, 세션 기억 동기화가 각각 파일 배치를 다시 탐색하면서 세션 식별 정보와 소유권을 잃는 문제를 직접 적었다. 접근자가 경로·세션 ID와 키·에이전트 소유자·산출물 종류를 한 항목으로 전달하게 한 것은, 소비자마다 같은 사실을 재발견하지 않고 다음 저장 단계까지 권한 문맥을 보존하기 위해서다.

## 다음 장으로

5월과 6월은 기억 내용의 권한, 색인의 정체성, 기계 상태의 소유자를 각각 분리했다. 그러나 세션과 대화 기록 자체가 정식 SQLite 상태가 아니면 목록, 이력, 정확 검색, 의미 코퍼스가 같은 가시성을 공유하기 어려웠다.

7월에는 이 마지막 저장소 경계를 닫고, 정확한 대화 기록 검색과 하네스 가져오기를 추가한 뒤, 같은 개인 에이전트가 비공개 표면을 넘나들며 기억하는 기능을 엄격한 자격 필터 위에 올린다.
