# 7장. 2026년 7월: 정식 대화 기록 검색, 가져오기, 보호된 교차 대화 메모리

7월에 풀어야 했던 문제는 더 많은 기억을 쌓는 일만이 아니었다. 평범한 검색 실패가 대화를 약 70초 멈출 수 있었고, 과거 대화에서 정확한 오류 하나를 찾으려 해도 이미 세션 키를 알아야 했다. 같은 개인 에이전트는 비공개 채널이 바뀌면 사용자를 잊었고, 다른 하네스에서 축적한 Markdown 기억을 안전하게 옮길 공식 경로도 없었다.

OpenClaw는 먼저 전경 검색과 복구 작업을 분리하고, 세션과 대화 기록을 SQLite의 정식 상태로 만들었다. 그 위에 정확한 `sessions_search`, 다른 하네스의 Markdown 기억 가져오기, 개인 에이전트의 제한된 대화 간 회상을 올렸다. 다만 마지막 기능과 일부 상태 통합은 조사 기준 시점에 `main`에만 있었고 아직 릴리스되지 않았다. 이 장은 출시된 기반과 아직 출시되지 않은 확장을 구분해 따라간다.

## 전경 검색이 예기치 않은 유지보수를 하지 않게 하다

평범한 결과 없음 [QMD](01-current-architecture.md#qmd-explained) 질의가 강제 동기식 유지보수를 시작하면, 기억을 찾지 못했다는 사실 하나가 대화형 차례를 약 70초 멈추는 전경 장애로 바뀐다. QMD는 이 장에서 새 기억을 쓰는 기능이 아니라 `memory-core`가 선택적으로 사용하는 별도 로컬 검색 사이드카다. 실제 사례는 [Issue #90023](https://github.com/openclaw/openclaw/issues/90023)에 보고되었다. 해결책은 검색 중에 복구를 끝내려 하지 않는 것이었다. `v2026.7.1`에 출시된 [PR #90030](https://github.com/openclaw/openclaw/pull/90030)은 장기 실행 QMD 관리자가 그 실패를 그대로 반환하게 하고, 명시적인 일회성 복구에만 기존 유지보수 동작을 남겼다.

이 선택으로 정상 대화의 응답 시간은 복구 비용에서 분리되었다. 대신 검색 실패 자체가 저장소를 고치지는 않는다. 전경 조회는 진단 가능한 실패나 성능 저하 결과를 반환하고, 소유자가 통제하는 동기화·doctor 경로가 상태 복구를 맡아야 한다는 경계가 남았다.

**변화의 동기.** 운영 장애에서 나온 **명시적 증거**다. Issue #90023과 PR #90030은 QMD의 평범한 검색 실패가 강제 동기화·임베딩으로 이어져 대화를 수십 초 멈춘 경로를 직접 연결한다. 장기 실행 QMD 관리자가 실패를 즉시 반환하고 명시적 일회성 경로에만 복구를 남긴 것은, 대화형 지연 상한과 색인 유지보수의 소유자를 분리하기 위해서다.

## 세션과 대화 기록을 정식 SQLite 상태로 만들다

복구 작업을 분리해도 세션과 대화 기록이 여러 활성 저장소에 걸쳐 있으면 목록, 이력, 검색, 압축, 기억 코퍼스 소비자가 서로 다른 대화 상태를 볼 수 있었다. 그래서 세션과 대화 기록 이벤트를 SQLite로 옮겼다. [PR #98236](https://github.com/openclaw/openclaw/pull/98236)은 [`0a8e3604ba24`](https://github.com/openclaw/openclaw/commit/0a8e3604ba24de4791d3505b7a442e8017276dd0)로 병합되었고 `v2026.7.2-beta.1`에 처음 포함되었다. 기존 `sessions.json`과 JSONL은 활성 폴백 저장소가 아니라 doctor 마이그레이션·보관 입력이 되었다.

이 변화는 오래 지속된 혼합 상태 어긋남의 근원을 닫고 소비자 사이에 트랜잭션 가시성을 만들었다. 그 대가로 예전 파일을 정상 운용 중 읽어 주는 폴백은 사라졌다. 이전 상태는 doctor 마이그레이션·보관 경로를 거쳐 정식 저장소로 들어와야 한다.

**변화의 동기.** 저장소 소유권 정리에 대한 유지보수자 요청에서 나온 **명시적 증거**다. PR #98236은 세션 메타데이터와 대화 기록 이벤트를 여러 활성 저장소에서 읽는 혼합 상태가 소비자마다 다른 현실을 만들 수 있다고 직접 설명했다. 에이전트별 SQLite를 유일한 런타임 저장소로 삼고 예전 JSON/JSONL을 doctor 입력이나 보관 산출물로만 둔 것은, 트랜잭션 가시성을 확보하고 정상 경로의 폴백 어긋남을 끝내기 위해서다.

## 의미 기억 검색을 보완하는 정확한 대화 기록 검색

대화 기록이 한 저장소에 모여도 발견 가능성의 공백은 남았다. 세션 목록은 메타데이터만 보여 주고, 이력은 이미 알려진 키가 있어야 하며, 기존 세션 기억 코퍼스는 실험적이고 임베딩에 의존했다. [Issue #100978](https://github.com/openclaw/openclaw/issues/100978)은 이 문제를 지적했다. OpenClaw는 의미 순위 결정기를 더 복잡하게 만드는 대신 SQLite FTS5 기반 `sessions_search`를 추가했다. [PR #105057](https://github.com/openclaw/openclaw/pull/105057)은 [`6fc564278dbb`](https://github.com/openclaw/openclaw/commit/6fc564278dbb61691b0b07ec269b0bb60d225111)으로 병합되었고 `v2026.7.2-beta.1`에 처음 포함되었다.

`sessions_search`는 의도적으로 `memory_search`의 다른 이름이 아니다.

- 권한이 확인된 원시 대화 기록 행을 검색한다.
- 임베딩이나 기억 설정이 필요 없다.
- 정확한 용어, 식별자, 오류, 인용문을 찾는 데 적합하다.
- `sessions_history`와 대화 기록 가시성 계약을 공유한다.

이 선택은 영속 의미 기억 회상과 정확한 보관 자료 조회를 서로 보완하는 도구로 만들었다. 대신 호출자는 뜻이 비슷한 기억을 찾는 일과 정확한 문자열을 찾는 일을 구분해야 한다. 제품 지침과 평가는 하나의 순위 결정기로 둘을 억지로 풀려 하지 말고 이 차이를 보존해야 한다.

**변화의 동기.** 사용자 요청에서 나온 **명시적 증거**다. Issue #100978과 이를 닫은 PR #105057은 목록은 본문을 찾지 못하고, 이력 조회는 이미 세션 키를 알아야 하며, 의미 검색은 실험 설정과 임베딩에 의존한다는 발견성 공백을 직접 밝혔다. 그래서 의미 순위 결정기를 확장하지 않고 대화 기록 행과 같은 트랜잭션에 FTS5 색인을 두고, `sessions_history`와 같은 가시성 판정을 쓰는 정확 검색 도구를 별도로 만들었다.

> **예시 — 합성 사례:** 과거 대화에 나온 정확한 오류 코드 `E_CONN_RESET_42`를 찾는 일은 `sessions_search`에 잘 맞는다. 반면 “이 사용자가 배포 전에 선호하는 검토 방식”처럼 의미가 비슷한 표현까지 찾아야 하는 일은 영속 의미 기억 회상의 영역이다. 이는 도구 구분을 설명하는 가상 예시다.

## 하네스 사이의 기억 이동성을 인정한 가져오기

기억이 사용자 소유의 Markdown이라면 하네스를 바꿀 때 다시 처음부터 가르치지 않고 옮길 수 있어야 했다. 그러나 기계별 내부 상태까지 복사하면 새 런타임의 경계와 충돌할 수 있었다. [Issue #106215](https://github.com/openclaw/openclaw/issues/106215)는 이 이동성 문제를 제기했고, [PR #106406](https://github.com/openclaw/openclaw/pull/106406)은 공유 기억 전용 가져오기 엔진과 Control UI에서 Codex·Claude Code의 영속 Markdown을 가져오는 기능을 추가했다. 이 PR은 [`4319ddbe8cb0`](https://github.com/openclaw/openclaw/commit/4319ddbe8cb08a49335eff22b82e3a7afe3d3201)으로 병합되었고 `v2026.7.2-beta.1`에 처음 포함되었다.

가져오기를 실제 설치 과정에서 발견할 수 있도록 한 다음 선택은 온보딩에 연결하는 일이었다. [PR #108977](https://github.com/openclaw/openclaw/pull/108977)은 감지된 가져오기를 다음 흐름에 노출하고 Hermes 기억 전용 가져오기도 추가했다. 이 PR은 [`e71ef76e8ed7`](https://github.com/openclaw/openclaw/commit/e71ef76e8ed74179699af1feacbd5a9042345c1c)으로 병합되었고 `v2026.7.2-beta.2`에 처음 포함되었다.

- 로컬 기본·안내형 CLI 온보딩
- 로컬 macOS 온보딩
- Linux 보조 앱에서 Control UI로 이어지는 온보딩 흐름

가져오기에는 미리보기 또는 감지를 전제로 한 선택, 원본 지문, 선택한 에이전트의 목적지, 백업·되돌리기, 링크를 따라가지 않는 경로 처리까지 포함된다. 이 경계 덕분에 원본 파일은 바꾸지 않고, 가져온 기억은 `memory/imports/` 아래에 둔다. 대신 가져오기는 기억 자산만 다루며 원본 하네스의 전체 실행 상태를 재현하지 않는다.

다음 표는 **기억 전용 가져오기**의 소스와 목적지를 고정한다. 전체 하네스 마이그레이션은 설정·인증·기술·플러그인 같은 다른 항목도 계획할 수 있지만, 그것들은 이 표의 대상이 아니다.

| ----------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Claude Code | 발견된 자동 기억 디렉터리 아래의 일반 `.md` 파일을 제한된 파일·탐색 항목 수 안에서 재귀적으로 찾는다. | 설정, 인증, 대화 보관 자료, 캐시·계획, 명령·기술 등 자동 기억 Markdown이 아닌 상태 | `memory/imports/claude-code/<collection-slug>-<id>/…`                      | 항목에 `sourceType=claude-auto-memory`, 컬렉션 ID·이름·상대 경로를 남긴다. 검토된 내장 흐름은 파일 바이트의 SHA-256 리비전을 적용 계획에 결박한다. | 기본은 기존 목적지와 충돌하면 쓰지 않는다. 덮어쓰기를 선택하면 항목별 백업과 충돌 복구 기록을 만든다.   |

Claude Code의 발견·복사 경계는 [자동 기억 계획](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/migrate-claude/memory.ts#L62-L181), Codex는 [기억 소스 발견](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/codex/src/migration/source-files.ts#L133-L185), Hermes는 [기억 계획](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/migrate-hermes/memory.ts#L43-L117)에 있다. 세 하네스 모두 공용 [안전한 메모리 복사](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/src/plugin-sdk/migration-runtime.ts#L245-L394)를 사용한다. 적용 전에 원본이 검토한 SHA-256과 달라지면 새 계획을 요구하고, 목적지를 덮어쓰는 도중 실패하면 준비된 복구 기록과 백업으로 원래 목적지를 복원하려 한다. 따라서 여기서 “되돌리기”는 원본 하네스 전체를 복원한다는 뜻이 아니라 **OpenClaw 목적지 파일 변경을 안전하게 복구할 근거를 남긴다**는 뜻이다.

이 변화는 초기에 Markdown을 선택한 전략적 가치를 보여 준다. 기억은 불투명한 모델 쪽 프로필만이 아니라, 사용자가 살펴보고 하네스 사이에서 옮길 수 있는 개인 자산이 되었다.

**변화의 동기.** 사용자 요청과 온보딩 관찰에서 나온 **명시적 증거**다. Issue #106215와 PR #106406은 Control UI에 Codex·Claude Code 기억을 검토해 가져올 공식 경로가 없음을 연결했고, PR #108977은 이미 있는 엔진을 CLI·macOS·Linux 첫 실행에서 발견할 수 없다는 공백과 Hermes 지원 부재를 직접 적었다. 설정 전체를 복제하지 않고 지문이 있는 기억 전용 계획·미리보기·백업·되돌리기를 택한 것은 사용자 자산만 옮기고 원본 하네스의 실행 상태와 새 런타임 경계를 섞지 않기 위해서다.

이 책은 Codex의 [`56395bddaf26`](https://github.com/openai/codex/tree/56395bddaf26eb2829387ca6a417bf9128e5b239) 리비전을 직접 확인했다. Codex는 실행 기억을 상태 데이터베이스에 추출하고, 전역 통합을 파일시스템 작업공간에 직렬화하며, 제한된 `memory_summary.md`를 주입하고, `MEMORY.md`를 검색 가능한 레지스트리로 사용한다. 근거는 Codex의 [파이프라인](https://github.com/openai/codex/blob/56395bddaf26eb2829387ca6a417bf9128e5b239/codex-rs/memories/README.md#L29-L120), [제한된 프롬프트 조립](https://github.com/openai/codex/blob/56395bddaf26eb2829387ca6a417bf9128e5b239/codex-rs/ext/memories/src/prompts.rs#L23-L50), [읽기 프롬프트](https://github.com/openai/codex/blob/56395bddaf26eb2829387ca6a417bf9128e5b239/codex-rs/ext/memories/templates/memories/read_path.md#L19-L46)다.

OpenClaw 가져오기 도구는 바로 `MEMORY.md`와 `memory_summary.md`만 발견하고, 심볼릭 링크나 일반 파일이 아닌 원본을 거부하며, Codex 내부 데이터베이스와 실행 기계 장치는 남겨 둔다. 이 경계는 OpenClaw의 [가져오기 탐색](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/codex/src/migration/source-files.ts#L133-L185)에서 확인된다.

## 개인 에이전트에 보호된 대화 간 회상을 추가하다

기억을 가져올 수 있어도 같은 개인 에이전트가 비공개 채널마다 사용자를 별개의 사람처럼 대하면 연속성은 깨졌다. [Issue #99611](https://github.com/openclaw/openclaw/issues/99611)은 한 채널에서 알던 사실을 다른 채널에서는 기억하지 못하는 이 현상을 “표면 간 기억상실”이라고 설명했다. OpenClaw는 이 대화 간 검색 경로에서 대화 기록을 새 영속 기억으로 승격하는 대신 회상 전용으로 색인하고, 보호된 Active Memory 답변 전 회상에만 사용하도록 범위를 정했다. [PR #100140](https://github.com/openclaw/openclaw/pull/100140)은 [`4b3ee5e7eb62`](https://github.com/openclaw/openclaw/commit/4b3ee5e7eb623368d367a5fc2fa3712bc8095f16)로 병합되어 이 동작을 `rememberAcrossConversations`로 추가했다.

이 기능을 이해하려면 먼저 “누가 누구의 과거를 찾는가”를 다섯 정체성으로 나눠야 한다.

| 판단 입력                                 | 뜻                                                                                                                 | 권한 검사에서 하는 일                                                                                                                                                                          |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 현재 요청과 기준 대화(`anchorSessionKey`) | 사용자가 지금 답을 받을 비공개 대화다. Active Memory 작업자는 이 키에 정해진 접미사를 붙인 요청자일 수 있다.       | 기준 대화 자체가 인식된 비공개 대화인지, 요청자가 기준 대화 또는 그 Active Memory 작업자인지 먼저 확인한다.                                                                                    |
| 에이전트 ID                               | 현재 요청과 후보 대화 기록을 소유한 OpenClaw 에이전트다.                                                           | 기준 대화와 후보가 같은 에이전트에 속해야 한다.                                                                                                                                                |
| 대화 정체성                               | `sessionId` 또는 같은 저장 대화 기록을 가리키는 파일 정체성이다.                                                   | 현재 대화와 같은 대화 기록은 다른 키로 보이더라도 제외한다.                                                                                                                                    |
| 대화 유형                                 | 정식 세션 행의 `chatType`·`origin.chatType`과 세션 키가 나타내는 `direct`, `group`, `channel`, 내부 실행 유형이다. | 직접·비공개로 확정되는 대화만 허용하고, 그룹·채널·공유 전역·내부 실행·유형 불명은 닫힌 채 차단한다.                                                                                            |
| 참여자와 세션 별칭                        | 참여자는 채널의 발신자이고, 세션 별칭은 하나의 대화 기록을 가리키는 여러 세션 키다.                                | 결과별 검사에서 참여자 동일성을 직접 비교하지는 않는다. 개인형 설치라는 기본값 판단은 DM 격리 설정으로 대신한다. 같은 대화 기록의 별칭은 모두 비공개여야 하며 하나라도 공유 유형이면 차단한다. |

여기서 **기준 대화**는 현재 답변의 목적지이고, **후보 대화**는 과거에서 찾은 결과의 출처다. `session.dmScope = main`의 `main`은 기본 활성화를 판단하는 DM 범위 값이지, 모든 `main` 세션을 자동으로 비공개라고 선언하는 표지가 아니다. **바인딩(binding)**은 채널·계정·상대 같은 입력을 에이전트와 세션 정책에 연결하는 설정이며, 바인딩 하나라도 DM 범위를 따로 지정하면 개인형 설치라는 자동 가정을 중단한다.

### 허용·차단 행렬

다음 행렬은 기능이 켜진 뒤 결과별로 적용되는 계약이다. “허용”은 후보가 다른 점검도 통과한다는 전제이고, 기본 활성화 여부는 그 다음 표에서 별도로 다룬다.

| 기준 또는 후보 상황                                            | 기준 대화로 사용                            | 과거 후보로 노출                       | 이유                                                                                     |
| -------------------------------------------------------------- | ------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------- |
| 직접 DM, 정식 `direct` 메타데이터, 모든 별칭이 비공개          | 허용                                        | 같은 에이전트의 **다른** 대화라면 허용 | 인식된 비공개 정체성이다.                                                                |
| 직접·비공개 주제 스레드                                        | `direct`로 분류되고 공유 별칭이 없으면 허용 | 같은 조건에서 허용                     | 스레드 접미사보다 저장된 대화 유형과 전체 별칭 판정이 우선한다.                          |
| 현재 대화 또는 같은 대화 기록을 가리키는 별칭                  | 기준 대화 자체는 허용                       | 차단                                   | 이미 현재 문맥에 있는 대화를 다시 주입하지 않는다.                                       |
| 그룹, 채널, 공유·그룹 스레드                                   | 차단                                        | 차단                                   | 공유 표면은 개인 간 회상 범위가 아니다.                                                  |
| 공유 전역 세션 또는 유형을 확정할 메타데이터가 없는 세션       | 차단                                        | 차단                                   | 비공개임을 증명하지 못하면 닫힌 채 실패한다.                                             |
| 한 별칭은 직접 대화이고 다른 별칭은 그룹·채널인 같은 대화 기록 | 차단                                        | 차단                                   | 별칭 사이의 프라이버시 판정이 충돌한다.                                                  |
| 다른 에이전트가 소유한 비공개 대화                             | 해당 없음                                   | 차단                                   | 범위는 `same-agent-private`다.                                                           |
| 샌드박스에서 요청한 회상                                       | 전체 회상 차단                              | 전체 회상 차단                         | 신뢰된 요청자 조건을 만족하지 않는다.                                                    |
| 정확한 `:active-memory:<12자리 16진수>` 접미사의 작업자 요청   | 비공개 기준 대화의 대리 요청자로 허용       | 작업자 자체의 생성 대화 기록은 차단    | 작업자는 기준 대화를 대신해 검색할 수 있지만 내부 생성 기록은 과거 사용자 대화가 아니다. |

구현은 기준 대화·요청자 신뢰를 먼저 확인하고, 각 `source=sessions` 결과를 같은 에이전트, 현재 대화 제외, 비공개 유형, 전체 별칭 일치 순으로 검사한다. 세부 판정은 [세션 결과 가시성 검사](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/src/session-search-visibility.ts#L157-L375)에 있다.

### 기본 활성화와 결과 권한은 다른 결정이다

| `rememberAcrossConversations` 설정 | 설치 형태 신호                                                                                     | 조사 기준 `main`의 기본값 |
| ---------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------- |
| 명시적 `true` 또는 `false`         | 어떤 DM 범위나 바인딩이 있어도 명시값이 우선                                                       | 명시값 사용               |
| 미설정                             | `session.dmScope`가 없거나 `main`이고, 어떤 바인딩도 별도 `session.dmScope`를 두지 않음            | 켬                        |
| 미설정                             | `per-peer`, `per-channel-peer`, `per-account-channel-peer`이거나 바인딩 하나라도 별도 DM 범위를 둠 | 끔                        |

이 기본값은 대화 기록을 검색 대상으로 준비할지 정할 뿐, 개별 결과를 허용하지는 않는다. 기능이 켜져 있어도 위 행렬의 그룹·다른 에이전트·현재 대화·혼합 별칭·샌드박스 결과는 계속 차단된다. 기본값 계산은 [메모리 호스트 설정](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/packages/memory-host-sdk/src/host/config-utils.ts#L177-L199)에 있다.

검색 실행 순서는 [1장의 정식 권한 순서](01-current-architecture.md#canonical-session-authorization)를 따른다. 세션 소스 선택은 순위화 전에 가능하지만, 같은 에이전트·비공개 대화 같은 결과별 검사는 백엔드 제한 뒤이자 인용·응답 노출·Dreaming 회상 추적 앞에 있다. `sessions_search`만은 보이는 결과를 모은 뒤 최종 상한을 적용한다.

이 권한 검사와 격리 조건을 전제로 개인형 설치의 조건부 기본값을 정했다. [PR #110597](https://github.com/openclaw/openclaw/pull/110597)은 [`01a9e1d398fd`](https://github.com/openclaw/openclaw/commit/01a9e1d398fd12970e936335811f13ee913e29c1)으로 병합되어 이 기능을 조건부 기본값으로 켰다. 앞 표처럼 전역 DM 범위가 없거나 `main`이고 어떤 바인딩에도 별도 DM 범위가 없을 때만 자동으로 켠다. 격리 신호가 하나라도 있으면 기본값은 꺼지며 명시적 설정은 언제나 우선한다.

2026-07-18의 조사 기준 시점에는 두 대화 간 회상 커밋 모두 출시 태그에 포함되지 않았다. 이 역사는 이를 **현재 `main` 동작이지만 아직 출시된 동작은 아님**으로 구분한다.

**변화의 동기.** 사용자 보고와 호환성에 민감한 유지보수자 요청에서 나온 **명시적 증거**다. Issue #99611을 닫은 PR #100140은 같은 개인 에이전트가 비공개 표면마다 문맥을 잃는 문제를 직접 해결했고, 후속 PR #110597은 개인형 설치에서만 그 보호된 경로를 조건부 기본값으로 열었다. 대화 기록을 새 영속 기억으로 복사하지 않고 회상 전용 색인과 검색 후 가시성 검사를 택한 명시적 이유는 연속성을 주되 현재 대화·공유 표면·다른 에이전트의 자료가 노출되지 않게 하는 데 있다. 차단된 적중이 Dreaming 회상 신호가 되지 않는다는 점은 조사 기준 코드의 실행 순서로 확인되는 **현재 계약**이지, PR이 별도로 밝힌 역사적 동기는 아니다. 두 변경 모두 조사 기준점에는 출시 태그가 없었다.

## 대안 저장소의 소유권을 바로잡다

같은 시기에는 대안 저장소 자체의 소유자가 모호한 문제도 수리했다. Memory Wiki에서는 검색·회상·가져오기·프롬프트 표면에 걸쳐 여러 에이전트가 하나의 전역 볼트를 공유할 수 있었다. [PR #103349](https://github.com/openclaw/openclaw/pull/103349)은 [`98b8c8c4ae29`](https://github.com/openclaw/openclaw/commit/98b8c8c4ae298c55ad42a99020ee689b1c3ed1c1)으로 병합되어 선택적인 에이전트별 볼트 격리를 추가했다. 전역 볼트는 호환성 기본값으로 남았다. 에이전트 범위는 정체성이 모호하면 닫힌 채 실패하고, 이미 섞인 볼트를 자동으로 분할하려 하지 않는다.

**변화의 동기.** 여러 에이전트가 지식 저장소를 공유한 실제 소유권 문제에서 나온 **명시적 증거**다. PR #103349은 지원 에이전트와 마케팅 에이전트가 같은 볼트를 검색·가져오기·프롬프트 주입에 쓸 수 있던 문제를 직접 적었다. 새 설치 전체를 즉시 분할하지 않고 선택적 에이전트별 볼트를 추가하며 전역 볼트를 호환 기본값으로 둔 것은, 새 격리 계약을 제공하되 이미 섞인 자료의 소유자를 추측해 자동 이동하지 않기 위해서다.

LanceDB에서도 이전의 공유 저장소는 에이전트를 넘나드는 목록·읽기·삭제·회상을 허용했다. [Issue #103590](https://github.com/openclaw/openclaw/issues/103590)은 `v2026.6.11` 설치에서 `main` 에이전트의 비공개 기억이 다른 에이전트의 프롬프트에 자동 회상되는 환경과 재현 절차를 기록했다. 이 이슈를 닫은 [PR #103799](https://github.com/openclaw/openclaw/pull/103799)은 2026-07-16에 병합되어 레코드를 에이전트 소유로 만들었다. 이로써 질의 자격이 저장된 정체성에 결박되었다. 기존 공유 테이블은 doctor 마이그레이션 전까지 실패 시 차단되고, 신뢰할 수 있는 행별 소유자가 없으므로 doctor는 이를 추론하지 않는다. 대신 모든 과거 행을 설정된 기본 에이전트에 일괄 할당한 뒤 스키마와 행 수를 검증한다. 소유권은 최선을 다하는 프롬프트 관례가 아니라 저장된 정체성과 질의 자격에 있어야 한다는 선택이었다.

**변화의 동기.** 사용자에게 관측된 에이전트 간 노출 사건과 격리 결함에서 나온 **명시적 증거**다. Issue #103590의 실제 재현과 이를 닫은 PR #103799가 원인과 수리를 직접 잇는다. 모든 저장·검색·삭제 경로에 정규화된 소유 에이전트 ID를 요구한 것은 프롬프트나 자동 검색 토글이 아니라 저장 행과 질의 자격 자체에서 경계를 강제하기 위해서다. 과거 행에 신뢰할 수 있는 소유자가 없다는 한계 때문에 마이그레이션은 기본 에이전트로의 명시적 귀속을 택했으며, 이 선택은 소유자를 사후에 증명한 것과는 다르다.

소유권을 바로잡아도 영속 변경이 중간에 끊기면 사용자의 기억 파일은 손상될 수 있었다. 같은 시험 릴리스에서 [`0317d7e62801`](https://github.com/openclaw/openclaw/commit/0317d7e628010d6e51a2a09f9d7e9af677216981)은 Dreaming이 `MEMORY.md`에 쓰는 승격 내용을 원자적으로 만들었고, [`48866bbc405f`](https://github.com/openclaw/openclaw/commit/48866bbc405f09f1a924e87ede89a82cbd391666)은 연결된 `MEMORY.md` 동작을 보존했다. 이제 중단에 견디면서 사용자의 파일시스템 계약도 존중하지만, 좋은 후보를 고르는 승격 자격과 쓰기 자체의 안전성은 여전히 별개의 문제다.

**변화의 동기.** 구체적으로 입증된 잠재 파일 쓰기 실패 경로에서 나온 **명시적 증거**다. PR #108397은 예약된 승격 중 `fs.writeFile`이 일부만 기록하면 `MEMORY.md`의 뒤쪽 장기 기억이 영구 손실될 수 있음을 코드 경로로 설명했지만, 실제 데이터 손실 사건이 보고되었다고 주장하지는 않는다. 후속 #108921은 원자적 이름 바꾸기가 심볼릭 링크 대상을 바꾸는 호환 문제를 고쳤다. 임시 파일·동기화·원자적 교체를 쓰되 링크의 쓰기 가능한 실제 대상을 보존한 것은 중단 내구성과 사용자의 파일시스템 계약을 함께 지키기 위해서다.

2026-07-18 조사 기준 시점의 마지막 `main` 전용 상태 통합은 다음 세 가지다. 이름은 비슷해 보여도 손실의 의미가 서로 다르다.

| 이동한 상태                                                                                                     | 누가 쓰고 읽는가                                                                                                               | 운영 목적과 SQLite가 맞는 이유                                                                                                                                                   | 손실되면 무엇이 사라지는가                                                                                                                                                                                   | 기준점 상태    |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------- |
| [QMD 조정 상태](https://github.com/openclaw/openclaw/commit/e873a7f955f8b354b8d0d3cb82da1da3dc5b161b)           | QMD 관리자와 컬렉션 제어기가 에이전트별 갱신·임베딩 작업을 시작할 때 임대를 쓰고 읽으며, doctor가 퇴역한 파일 잠금을 정리한다. | 여러 프로세스의 컬렉션·갱신·임베딩 쓰기를 직렬화하고 에이전트 사이의 임베딩 동시성을 제한한다. 원자적 임대와 명시적 소유자가 필요한 조정 상태이므로 파일 잠금보다 SQLite가 맞다. | 사용자 Markdown이나 QMD 자체 색인이 의미 원본으로 사라지는 것은 아니다. 조정 임대를 다시 얻고 필요한 동기화를 해야 한다. 세션 유래 결과의 정체성 매핑을 확인할 수 없으면 해당 결과는 닫힌 채 제외될 수 있다. | 출시 태그 없음 |

마지막 변경은 SQLite를 권위 상태로 삼으면서도 범위가 제한되고 이름이 정해진 `memory/events/.../memory-host-events.jsonl` 공개 내보내기를 유지했다. 세 변경은 각각 이를 포함하는 `v*` 태그가 하나도 없었다. 이들은 내장 의미 기억으로서 Markdown의 역할을 바꾸지 않은 채 기계 상태 마이그레이션을 계속한다.

**변화의 동기.** 데이터베이스 우선 소유권 정리에 대한 유지보수자 요청에서 나온 **명시적 증거**다. 세 PR은 QMD 잠금 보조 파일의 정체·경쟁, Memory Wiki 프롬프트 경로의 낡은 캐시 소유자, 여러 JSONL 런타임 저널의 분산된 수명주기를 각각 직접 설명했다. 그래서 조정·캐시·권위 저널은 SQLite 소유 상태로 모으고, 외부 계약인 제한된 이벤트 내보내기만 이름 있는 산출물로 남겼다. 조사 기준점에는 세 변경 모두 출시 태그가 없었으며, 이는 Markdown 의미 기억을 SQLite로 대체한 변화가 아니다.

## 다음 장으로

7월까지 OpenClaw는 사람이 편집하는 기억, 검색용 색인, 정식 대화 기록, 플러그인별 대안 저장소의 책임을 더 뚜렷하게 나눴다. 정확한 대화 기록 검색과 의미 회상을 분리하고, 전경 실패와 복구를 분리하며, 소유자를 알 수 없는 데이터에는 실패 시 차단하는 방식으로 각 경계의 실패 형태도 정했다. 동시에 일부 교차 대화 회상과 상태 통합은 아직 `main`에만 남아 있어, 현재 코드와 출시된 제품을 같은 것으로 읽어서는 안 된다는 한계가 남았다.

다음 장은 연대기에서 한 걸음 물러난다. 2025년 제안부터 2026년 7월까지 반복해서 등장한 문제를 설계 전환으로 묶고, 초기에 제안된 거대한 시스템을 실제로 구현된 더 작은 경계들과 비교해 재검토한다.
