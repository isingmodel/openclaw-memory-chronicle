# 5장. 2026년 4월: 점수화된 성찰과 경계가 있는 에이전트형 회상

3월까지 OpenClaw는 기억을 저장하고 검색할 엔진과 소유자를 갖췄다. 하지만 사람이 실제로 겪는 문제는 한 단계 뒤에 있었다. 관련 기억이 있어도 주 모델이 도구를 부르지 않을 수 있었고, 수많은 작업 메모 가운데 무엇을 장기 기억으로 올릴지도 계속 사람과 프롬프트의 재량에 남아 있었다.

4월에는 회상 자체를 관측하고, 답변 전에 별도 에이전트가 제한적으로 기억을 찾으며, 시작 메모를 런타임이 결정적으로 주입하는 흐름이 생겼다. 이로써 프롬프트에 건 기대는 측정 가능한 단계로 바뀌었다. 동시에 노출 편향이 있는 승격, 전경 지연, 구조화된 주장의 무게, 대화 기록 프라이버시라는 새 비용도 드러났다.

## 반복해서 유용했던 작업 기억을 승격하는 Dreaming

작업 기억을 오래 남길지 결정할 객관적 단서가 부족했다. Dreaming은 검색된 내용을 단기 회상 관찰로 기록하고, 반복해서 유용해 보인 후보를 임계값에 따라 승격하는 방식을 택했다. [PR #60569](https://github.com/openclaw/openclaw/pull/60569)는 2026-04-04에 [`4c1022c73b39`](https://github.com/openclaw/openclaw/commit/4c1022c73b3910ed68d0c4c72767e7465067c6a7)로 병합되었고 처음 포함된 릴리스는 `v2026.4.5`였다.

- 자격을 갖춘 각 검색은 무엇이 어떤 질의로 검색되었는지 기록할 수 있었다.
- 초기 후보 점수는 관련성, 회상 빈도, 질의 다양성, 최신성에 가중치를 두었다.
- 기본 임계값은 점수 `0.75`, 최소 3회 회상, 서로 다른 질의 최소 2개였다.
- `memory promote`와 선택적 예약 Dreaming은 반복해서 쓰인 작업 기억을 선별된 자료로 바꿀 수 있었다.

같은 릴리스가 나오기 전에 [`0609bf858175`](https://github.com/openclaw/openclaw/commit/0609bf858175818b79dba514cc3b10e744d5fa72)가 통합과 개념적 가치 요인을 추가하고 가중치를 다시 조정했다. 두 커밋을 구분하는 것은 중요하다. 첫 구현은 회상 주도 승격을 세웠고, 후속 변경은 `v2026.4.5`에서 볼 수 있는 6요인 점수기를 완성했다.

> **후속 변화의 동기.** 이 변경은 사용자 장애나 폴백 사건보다 출시 전 설계 보강에 가깝다. 커밋 제목과 묶음은 Dreaming의 감사·수리 흐름을 단단히 하고 다국어 개념 어휘를 보태려는 목표를 **명시적으로** 밝히지만, 왜 각 가중치를 골랐는지까지 설명하지는 않는다. 따라서 통합·개념 풍부성 요인을 더하고 다국어 후보를 다루기 쉬워졌다는 것은 확인할 수 있어도, 특정 사용자 보고가 이 점수기를 촉발했다고 읽지는 않는다.

2026-01-02에 열린 [Issue #102](https://github.com/openclaw/openclaw/issues/102)는 제대로 된 벡터 회상과 일별 기억을 장기 기억으로 끌어올리는 기능을 함께 요청했다. 1월의 하트비트 지침은 이미 승격을 에이전트의 선별 작업으로 만들었다. Dreaming은 이를 관측된 회상 점수와 임계값·예약 실행을 통한 승격으로 바꾸었다. 기능의 대응 관계는 분명하지만, Dreaming PR이나 코드 어디에도 Hindsight가 4월 알고리즘을 직접 결정했다는 증거는 없다.

> **변화의 동기.** PR #60569는 회상 기록, 가중 신호, 초기 임계값, 수동·예약 승격 흐름이라는 **명시된 기능 목표와 계약**을 남겼다. 그러나 왜 빈도·질의 다양성·최신성을 그 가중치와 수치로 골랐는지는 설명하지 않으므로, 그 선택 이유는 **코드에서 추론**하는 데 그친다. 새 진실 모델보다 관측된 검색을 실용적 승격 대리 신호로 삼았다는 해석도 같은 한계를 가진다. Issue #102와 Hindsight는 검색과 장기 승격이라는 같은 기능 문제를 먼저 보여 주는 **맥락적 증거**일 뿐, 이 PR의 직접 원인으로 입증되지는 않았다.

운영과 검토가 필요해지면서 후속 커밋들은 Light/REM/Deep 단계 개념, 꿈 일지, 근거가 있는 과거 자료 채우기, 검토와 그림자 모드, 메모리 이벤트 저널 연결부를 추가했다. [PR #70737](https://github.com/openclaw/openclaw/pull/70737)은 나중에 관리형 Dreaming 예약 작업을 하트비트 일정에서 분리해, 관련 없는 주기 실행 메커니즘에 얹혀 있던 수명주기를 하나의 소유자에게 돌려주었다.

세 이름은 사용자가 따로 고르는 세 모드가 아니라, 한 번의 Dreaming 순회가 **Light → REM → Deep** 순서로 밟는 내부 단계다. 조사 기준점의 역할을 하나의 표로 모으면 다음과 같다.

| 단계                         | 주된 입력                                                                   | 사람이 확인하는 출력                                                                             | 내구성 있는 의미 변화                                                      | 기계 상태의 소유자                                                         | 운영 승격에 미치는 영향                                                   |
| ---------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Light                        | 최근 회상 흔적, 일일 메모리, 사용할 수 있을 때 패턴으로 가린 대화 기록 증거 | 일일 파일의 관리 블록 또는 `memory/dreaming/light/` 보고서, 선택적 `DREAMS.md` 일지              | `MEMORY.md`를 직접 바꾸지 않는다.                                          | `memory-core`의 에이전트별 SQLite 상태가 단계 신호와 수집 진행을 기록한다. | 후보를 정리하고 Light 강화 신호를 남겨 Deep 순위에 간접 반영될 수 있다.   |
| REM                          | Light가 고른 후보를 우선하며, 없으면 최근 회상 흔적을 사용한다.             | 반복 주제·성찰·가능한 장기 사실을 담은 관리 블록 또는 `memory/dreaming/rem/` 보고서, 선택적 일지 | `MEMORY.md`를 직접 바꾸지 않는다.                                          | 같은 SQLite 상태가 REM 검토·강화 신호를 기록한다.                          | 반복 패턴을 후보 신호로 남겨 Deep 순위에 간접 반영될 수 있다.             |
| Deep                         | 단기 후보, 기본 6요인 점수, Light·REM 강화 신호와 임계값                    | `DREAMS.md`의 Deep 요약과 선택적 `memory/dreaming/deep/` 보고서                                  | 자격을 모두 통과하고 원문에서 다시 확인된 후보만 `MEMORY.md`에 쓸 수 있다. | 같은 SQLite 상태가 회상·단계·승격 진행을 관리한다.                         | 실제 운영 승격을 수행하는 유일한 단계다.                                  |
| 섀도 시험(세 단계 밖의 검토) | 기준 답변과 후보 기억을 허용한 답변, 판정과 위험 표지                       | `memory/dreaming/shadow-trials/` 아래의 검토 보고서                                              | 어떤 판정도 `MEMORY.md`를 쓰지 않는다.                                     | 보고서 파일이 검토 결과를 소유한다.                                        | `promote`·`defer`·`reject`는 **권고 표지**일 뿐, 운영 승격 호출이 아니다. |

이 표의 핵심은 “보고서에 후보가 나타남”, “Deep 순위에 신호가 더해짐”, “`MEMORY.md`가 실제로 바뀜”을 서로 다른 사건으로 읽는 것이다. 특히 섀도 시험의 검토 점수와 Deep의 운영 승격 점수는 이름이 비슷해도 같은 실행 경로가 아니다.

> **변화의 동기.** 유지보수자 요청과 수명주기 장애에서 나온 **명시적 증거**다. PR #70737은 기본 에이전트의 하트비트가 꺼져 있으면 Dreaming도 실행되지 않는 결합을 직접 지목했다. 그래서 하트비트 설정을 고치는 대신 격리된 에이전트 실행과 전용 관리 일정으로 옮겨, 선택 기능의 실행 여부를 Dreaming 소유자가 독립적으로 통제하게 했다.

조사 기준 동작에서 트랜스크립트 수집은 별도 토글이 아니다. Dreaming이 활성화된 상태에서 Light나 REM이 실행되면 해당 단계가 워크스페이스와 연결된 에이전트의 트랜스크립트 코퍼스를 직접 수집하고 `memory/.dreams/session-corpus/`에 증거를 만들어 단기 승격에 공급할 수 있다. 이는 [Light 호출](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/src/dreaming-phases.ts#L1681-L1715), [REM 호출](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/src/dreaming-phases.ts#L1790-L1820), [승격 소비](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/src/short-term-promotion.ts#L1832-L1874)에서 확인된다. 따라서 보호된 `memory_search`의 검색 적격성과 Dreaming의 포획·승격 적격성은 같은 경계가 아니다.

또 다른 경계도 구분해야 한다. 내장 스캐너는 `memory/` 아래의 적격 Markdown을 재귀적으로 찾으므로, 기준점에서는 `memory/dreaming/`의 단계 Markdown이 일반 메모리 검색에 들어갈 수 있다. 반면 단기 승격 경로는 그 디렉터리를 제외한다. `memory/.dreams/session-corpus/`의 증거 수집과 `memory/dreaming/` 단계 산출물의 검색 가능성을 같은 경로로 오인해서도 안 된다. **검색 적격성과 승격 적격성은 별개의 계약이다.**

점 하나 차이인 두 경로를 표로 나누면 그 경계가 선명해진다.

| 경로                             | 만드는 단계                                        | 담는 내용                                     | 일반 메모리 검색                                                       | 장기 승격 입력                                                   | 프라이버시 처리                                                                                                       | 기준점 상태                                                                        |
| -------------------------------- | -------------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `memory/.dreams/session-corpus/` | Light·REM의 대화 기록 수집                         | 패턴 기반으로 가린 대화 기록 증거(`.txt`)     | 내장 Markdown 스캐너의 일반 검색 대상이 아니며 Dreaming이 직접 읽는다. | 가능하다. 단기 승격 후보의 근거가 될 수 있다.                    | 보호된 대화 간 검색의 대화 종류·비공개 필터를 재사용하지 않고, 워크스페이스 연결 에이전트의 코퍼스를 별도로 수집한다. | 현재 증거 산출물이다. 같은 `.dreams/` 아래의 옛 JSON 기계 상태와 혼동하면 안 된다. |

| 위치                                                   | 무엇을 담는가                                           | 누가 읽고 쓰는가                    | 현재 의미                                                                                            |
| ------------------------------------------------------ | ------------------------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------- |

이 점수 모델은 기억 품질을 측정하는 중요한 진전이었지만 통계적 함정도 있다. **회상 횟수는 일부가 현재 순위 결정기 때문에 생긴다.** 자주 노출된 기억은 더 많은 증거를 쌓고 다시 승격될 수 있다. 질의 다양성은 도움이 되지만 위치·노출 편향을 없애지는 못한다. 또한 기억의 진실성, 권한, 현재 유효성을 입증하지도 않는다.

> **예시 — 합성 사례:** 두 메모의 실제 유용성이 같아도 현재 순위 결정기(ranker)가 A를 늘 상위에 놓으면 A만 회상 횟수와 질의 다양성 점수를 축적할 수 있다. 이는 메커니즘을 설명하기 위한 가상 예시이며, 관측된 OpenClaw 사례가 아니다.

그림자 평가 자체도 변했다. [`b2f71db7bb46`](https://github.com/openclaw/openclaw/commit/b2f71db7bb46eda5a45fe932b014046574f3b44a)는 보고 전용 시험을 추가했다. [`70c59f59b258`](https://github.com/openclaw/openclaw/commit/70c59f59b25839038a968e75c5c99379e45ca13b)은 도움됨·중립·해로움 판정으로 보고서 안의 후보 점수와 순위를 계산하는 보조 함수를 더했지만, 반환값은 처음부터 `scoringAction: "report-only"`였고 실제 운영 승격(production promotion) 호출 경로에는 연결되지 않았다. [`7679872ddf3d`](https://github.com/openclaw/openclaw/commit/7679872ddf3db5cff42f14fc9f839eff73b3376b)은 이 사용되지 않는 점수 보조 연결부를 제거했다. 조사 기준 시점에는 보고 실행기만 남아 있고 실제 운영 승격은 그림자 판정을 사용하지 않는다. 당시 Dreaming 문서는 보고서 안의 후보 정렬 설명과 “실제 운영 동작을 바꾸지 않는다”는 설명을 함께 두고 있어 경계가 모호했다.

> **변화의 동기.** 보고 전용 실험 경계를 정리한 **명시적 근거와 코드 추론**이다. `70c59f59b258`의 커밋 본문과 타입은 점수 계산도 보고 전용이라고 명시하고, `7679872ddf3d`는 이를 사용되지 않는 보조 코드로 제거한다. 그러므로 이 계보에서 확정할 수 있는 것은 검토용 점수 실험과 죽은 코드 정리뿐이다. 실제 운영 승격 정책을 한동안 바꾸었다가 되돌렸다는 역사는 만들 수 없으며, 왜 이 보조 함수가 실제 호출자 없이 추가되었는지는 남은 자료만으로 알 수 없다.

## 구조화된 지식 계층을 탐색한 Memory Wiki

평면 Markdown은 짧은 메모에는 편하지만 영속적인 주장의 출처, 관계, 모순을 표현하기에는 부족했다. Memory Wiki는 이를 모든 기억의 새 스키마로 강제하지 않고, 수집·컴파일·검사, 출처, 백링크, 모순 중심 이슈, 통제된 변경, 가져오기 동기화, 공유 회상 연결부를 갖춘 선택적 볼트로 옆에 두었다. 시작점은 [`57d1685a65f5`](https://github.com/openclaw/openclaw/commit/57d1685a65f59a808305ec7fb708269d2031616b)다.

이 선택은 2025년 제안이 예견한 구조화된 지식의 필요에 답하면서도 평면 Markdown 기억을 대체하지 않았다. 짧은 메모의 낮은 작성 부담을 지켰지만, 별도의 컴파일 산출물과 스키마를 관리해야 하는 무게는 남았다.

초기의 LLM 기반 스택은 같은 날 [`94256ea1a076`](https://github.com/openclaw/openclaw/commit/94256ea1a07689d7c3bf8791a3d1271019ba6852)에서 되돌려졌다. 원래 커밋이 `v2026.4.5`의 조상에 있기는 하지만, 그 릴리스 트리에는 Memory Wiki 기능이 없다. [`5716d83336fd`](https://github.com/openclaw/openclaw/commit/5716d83336fd3411ba515659af4879ae8518563f)이 경계를 좁힌 형태로 기능을 복원했고, 실제 기능이 들어간 첫 태그는 `v2026.4.7`이다. 이 플러그인은 컴파일된 위키 페이지를 보존된 출처·사람 작성 블록을 지닌 파생 산출물로 설명하며, 새로운 궁극적 진실로 취급하지 않는다.

> **변화의 동기.** 설계·소유권 정리에서 **코드로 추론한 증거**다. 추가·되돌림·복원 순서는 평면 기억 전체를 새 스키마로 바꾸지 않고 선택적 플러그인 안에 구조화 지식의 무게를 가두려 한 방향을 보여 준다. 다만 복원 커밋은 경계를 좁힌 이유를 상세히 설명하지 않으므로, 되돌림이 특정 장애 때문에 일어났다고 단정하지 않는다. 파생 컴파일 산출물과 출처 블록을 택한 것은 사람이 관리하는 원본과 검색용 구조를 분리하기 위해서다.

## 답변 전에 제한적으로 탐색하는 Active Memory

도구가 존재한다고 주 모델이 반드시 호출하는 것은 아니었다. 관련 기억이 있는데도 검색 없이 자신 있게 답하는 문제를 줄이기 위해, 답변 전 별도의 제한된 에이전트가 현재 요청 차례(turn)를 살펴보고 메모리 도구를 호출한 뒤 압축된 결과를 주 모델의 프롬프트에 주입하도록 했다. Active Memory를 도입한 [PR #63286](https://github.com/openclaw/openclaw/pull/63286)은 [`b83726d13e33`](https://github.com/openclaw/openclaw/commit/b83726d13e336643d0b68d8aae79f222b8d26e90)으로 병합되어 `v2026.4.10`에 처음 포함되었다.

얻은 것은 회상 결정을 프롬프트 속 제안에서 명시적인 런타임 단계로 옮긴 일이었다.

> **변화의 동기.** 유지보수자 제품 요청에서 나온 **명시적 증거**다. PR #63286은 사용자가 주 모델에 검색을 따로 요구하지 않아도 선호·습관·개인 사실을 선제적으로 떠올리게 하려는 목표를 직접 밝혔다. 그래서 주 모델의 프롬프트를 더 강하게 쓰는 대신, 별도의 제한된 하위 에이전트가 도구를 쓰고 압축된 관련 내용만 주 답변에 주입하도록 했다.

답변 전 회상에는 반대 비용도 있었다. 회상이 응답을 막을 수 있었고, 별도 로컬 검색 사이드카인 [QMD](01-current-architecture.md#qmd-explained) 초기화는 다중 에이전트 게이트웨이(Gateway)가 시작될 때 요청이 한꺼번에 몰리는 현상(burst)을 만들 수 있었다. 이 문제는 [Issue #72015](https://github.com/openclaw/openclaw/issues/72015)에 보고되었다. 현재 코드는 별도의 마감 시간(deadline), 실행 자격 검사(eligibility check), 제한된 출력, 실패해도 주 답변은 계속하는 방식(fail-open)을 갖추었지만 이 이슈는 열린 상태였다. 따라서 회상률, 지연 시간, 아무 일도 하지 않은 실행(no-op) 비율, 사용자가 체감하는 효용을 함께 평가해야 한다.

전경 지연을 줄이기 위해 Active Memory의 QMD 경로는 상속받은 전체 질의 파이프라인 대신 어휘 `search`를 기본으로 쓰고 명시적 재정의를 유지하게 되었다. [Issue #64829](https://github.com/openclaw/openclaw/issues/64829)은 당시 `query`를 약 4초, `search`를 약 0.2초로 관측했고 Active Memory의 두 차례 모델 실행까지 합치면 첫 답변이 20~25초로 늘어나는 사례를 제시했다. 이 이슈를 직접 참조한 [PR #65068](https://github.com/openclaw/openclaw/pull/65068)이 제품 맥락에 맞는 절충을 구현했다. 최고의 오프라인 재순위화기가 자동으로 최고의 답변 전 경로가 되는 것은 아니다.

> **변화의 동기.** 사용자 운영 측정과 유지보수자 제품 판단에서 나온 **명시적 증거**다. Issue #64829의 지연 수치와 PR #65068의 직접 참조가 원인과 변경을 잇는다. 전체 질의 파이프라인을 없애지 않고 명시적 재정의를 남긴 것은, 대화형 기본값의 응답성과 더 비싼 재순위화가 필요한 설치의 선택권을 함께 보존하기 위해서다.

## 시작 기억도 모델 재량에서 런타임으로 이동하다

내용 없는 `/new`나 `/reset`의 첫 답변도 모델이 시작 파일을 스스로 발견하길 기다릴 수 없었다. 런타임이 오늘과 어제의 날짜별 메모를 선택하고, 설정한 시간대의 달력 날짜를 사용하며, 내용의 크기를 제한하고 신뢰할 수 없는 문맥임을 표시해 인용 블록으로 감싸도록 했다. [PR #65055](https://github.com/openclaw/openclaw/pull/65055)는 [`94340b959830`](https://github.com/openclaw/openclaw/commit/94340b959830b8d7dd70d486617963ad2999409c)으로 병합되어 `v2026.4.12-beta.1`에 처음 포함되었다.

시작 파일을 발견하고 읽으라는 모델 지침이 결정적 런타임 동작으로 바뀌었다. 더 일찍 제기된 [Issue #48217](https://github.com/openclaw/openclaw/issues/48217)은 같은 초기 시작 실패 형태를 설명하지만 PR은 이 이슈를 연결하지 않는다. 따라서 이 책은 이슈를 입증된 원인이 아니라 **맥락적 증거**로 다룬다.

> **변화의 동기.** 유지보수자 요청에서 나온 **명시적 증거**다. PR #65055는 비어 있는 `/new`와 `/reset`이 모델의 자율적인 시작 절차에 의존하던 문제를 직접 설명했다. 런타임이 달력 날짜와 시간대를 적용해 한 번만 시작 문맥을 앞에 붙이는 형태를 택한 이유는 첫 응답의 재현성을 확보하면서 이후 대화마다 같은 메모리를 되풀이해 주입하지 않기 위해서다. Issue #48217은 같은 실패 형태를 보여 주지만 PR과 직접 연결되지 않은 **맥락적 증거**다.

## 루트 파일과 임베딩 제공자의 소유권을 더 조이다

같은 정책이 여러 곳에 남으면 루트 파일 이름과 임베딩 제공자의 실제 소유자가 흐려진다. 임베딩 구현은 제공자 플러그인으로 옮겼고, 런타임의 루트 기억 발견은 대문자 파일만 대상으로 제한했다. 소문자 `memory.md`만 존재하면 더 이상 읽지 않았으며, doctor에는 좁은 범위의 분리 상태 병합 복구가 남았다. 근거는 차례로 [`77e6e4cf87f7`](https://github.com/openclaw/openclaw/commit/77e6e4cf87f7a0b6343b48328050e0f31a282117), [`10a9acbf2936`](https://github.com/openclaw/openclaw/commit/10a9acbf29361744ff8a9920cc07c7d285e831bd), 정책과 복구 경계를 중앙화한 [`deb1364dfbe6`](https://github.com/openclaw/openclaw/commit/deb1364dfbe6e4561f1d6f388a837832186b3c7f)이다. 이 변경들은 중복 정책을 줄이고 임베딩 제공자와 런타임의 소유권을 더 큰 플러그인 아키텍처와 맞췄다.

> **변화의 동기.** 설계·소유권 정리에서 **코드로 추론한 증거**다. 세 커밋은 임베딩 구현, 루트 파일 이름, 복구 정책을 각각 한 소유자에게 모은 사실을 보여 주지만 공통 사건을 원인으로 명시하지는 않는다. 런타임은 정식 대문자 파일만 읽고, 과거의 대소문자 충돌은 doctor가 수리하게 해 정상 경로에 영구 호환 분기를 남기지 않는 형태를 택했다.

## 규모와 대화 기록 프라이버시를 측정 가능한 문제로 만들다

코퍼스가 커졌을 때 전체 벡터 스캔 비용이 대화형 경로를 위협했다. 10,827개 청크를 측정한 결과 JavaScript 전체 벡터 스캔은 약 8.5초, sqlite-vec 후보 조회는 약 50 ms였다. [PR #69680](https://github.com/openclaw/openclaw/pull/69680)은 KNN 후보 선택 뒤에도 코사인 재점수화를 유지해 최적화가 순위 의미를 몰래 바꾸지 않도록 했다. 대표 코퍼스 크기와 보존된 점수 계약을 성능 변경에 함께 연결했다는 점에서 특히 가치 있는 증거다.

> **변화의 동기.** 운영 측정에서 나온 **명시적 증거**다. PR #69680은 10,827개 청크에서 전체 스캔과 KNN 후보 조회의 지연 차이를 직접 제시했다. 네이티브 KNN으로 후보 수를 먼저 줄이되 기존 코사인 재점수화를 유지한 것은 속도를 얻으면서도 이미 노출된 점수 의미와 순위 계약을 바꾸지 않기 위해서다.

더 심각한 문제는 대화 기록 기반 기억 검색 결과가 세션 도구 가시성과 에이전트 간 정책을 우회할 수 있다는 점이었다. 반환된 세션 검색 결과에 인용 장식과 회상 추적 전에 실패 시 차단하는 **검색 후** 권한 필터를 추가했다. [PR #70761](https://github.com/openclaw/openclaw/pull/70761)은 [`2c716f5677de`](https://github.com/openclaw/openclaw/commit/2c716f5677de4db99ecaab058b4f375009468c86)로 병합되어 `v2026.4.24-beta.1`에 처음 포함되었다.

이와 별도로 명시적인 `corpus=sessions`와 `corpus=memory` 요청은 순위화와 상위 N개 선택 전에 백엔드 소스 선택을 제한하도록 했다. 그러나 세션별 가시성은 백엔드 검색이 `maxResults`를 받은 뒤에 여전히 실행된다. 따라서 차단된 검색 결과는 노출되거나 인용을 받거나 통합 신호를 학습시킬 수 없지만, 백엔드 결과 슬롯 하나를 소비해 보이는 결과 수를 줄일 수 있다. 이 구분은 조사 기준 시점의 [도구 실행 순서](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/src/tools.ts#L647-L759)에도 남아 있었다.

> **변화의 동기.** 보안 경계에 대한 유지보수자 요청에서 나온 **명시적 증거**다. PR #70761은 색인된 회상이 다른 세션 도구와 같은 가시성 규칙을 지켜야 한다고 명시했다. 백엔드별 색인을 다시 설계하는 대신 반환된 세션 검색 결과를 인용·노출·회상 추적 전에 실패 시 차단하는 공통 필터를 택해 두 백엔드에 같은 정책을 적용했다. 다만 이는 검색 후 필터이며, 결과 상한 이전의 세션별 권한 검사라고 확대해서는 안 된다.

> **예시 — 합성 사례:** 백엔드가 `maxResults=3`으로 세 검색 결과를 반환했고 첫 결과가 세션 권한 필터에서 차단되면, 사용자는 최대 두 결과만 볼 수 있다. 차단된 결과는 인용이나 Dreaming 학습 신호가 되지 않지만 이미 백엔드 상위 3개 슬롯은 사용했다. 이는 순서를 설명하는 가상 예시이지 실제 관측 기록이 아니다.

내부 압축 플러시 프롬프트가 사용자 메시지로 나타나면 런타임 출처가 나중의 대화 증거로 오염될 수 있었다. [PR #73380](https://github.com/openclaw/openclaw/pull/73380)은 그 프롬프트를 사용자 대화 기록에서 제외했다. 이로써 내부 유지보수 지침이 나중에 검색 가능한 “사용자” 이력으로 바뀌는 일을 막았다.

> **변화의 동기.** 장애·회귀 사건에서 나온 **명시적 증거**다. PR #73380은 Issue #54408과 중복 보고 #58956을 연결해, 압축 전 플러시 프롬프트가 일반 사용자 메시지로 저장·투영되던 문제를 고쳤다. 별도의 내용 필터보다 내부 실행 또는 명시적 내부 출처를 택한 것은, 문구가 달라져도 런타임 지시와 사용자 발화를 출처 단계에서 구분하기 위해서다.

## 다음 장으로

4월은 회상과 승격을 런타임 단계와 관찰 대상으로 만들었고, 성능과 프라이버시도 숫자와 필터 순서로 설명하기 시작했다. 그러나 검색된 기억이 정말 행동 권한인지, 제공자가 실패했을 때 색인이 어떤 상태인지, 늘어나는 기계 상태를 누가 마이그레이션해야 하는지는 아직 분명하지 않았다.

5월과 6월에는 이 문제가 권한 메타데이터, 진단 가능한 색인 정체성, 원자적 게시, 데이터베이스 우선 상태로 이어진다.
