# 6장. 2026년 5월과 6월: 권한, 실패의 투명성, 데이터베이스 우선 상태

4월까지 OpenClaw는 기억을 더 자주 찾아 답변 전에 불러오고, 반복해서 쓰인 내용을 장기 기억으로 승격하는 단계에 이르렀다. 그러자 검색의 정확도만으로는 풀 수 없는 문제가 앞에 놓였다. 과거 대화에서 찾은 문장이 지금 행동해도 된다는 승인인지, 임베딩 공급자가 바뀐 뒤에도 기존 인덱스를 믿을 수 있는지, 다시 만들 수 있는 상태라면 업그레이드 중에 버려도 되는지를 따로 판단해야 했다.

5월과 6월의 변화는 이 문제들을 하나의 거대한 기능으로 풀지 않았다. 기억한 **지식**과 현재의 **행동 권한**을 구분하고, 검색 실패는 답변 전체로 번지지 않도록 시간과 자원을 제한했다. 공급자와 인덱스의 정체성이 어긋나면 조용히 다른 방식으로 넘어가는 대신 원인을 드러냈다. Dreaming 상태와 기억 인덱스는 SQLite로 옮겼고, 대화 기록을 찾는 절차는 정식 접근자 뒤로 모았다.

그 결과 어떤 정보가 기준 원본인 **정본**이고, 누가 상태를 소유하며, 실패했을 때 무엇을 보존해야 하는지가 전보다 선명해졌다. 대신 기존 상태를 새 저장소로 옮기는 비용, 다시 만들 수 있는 인덱스의 실제 재구축 비용, 구현을 따라오지 못한 문서가 새로운 과제로 남았다.

## 검색된 사실은 자동으로 행동 권한이 되지 않는다

기억 속 **지식**은 과거에 무엇이 사실이었고 무엇을 논의했는지를 알려 준다. 반면 **행동 권한**은 지금 누구를 상대로 어떤 일을 어디까지 수행해도 되는지를 정한다. 관련성이 높고 출처가 믿을 만한 기억이라도 그 자체가 현재의 실행 허가는 아니다. “사용자가 한때 보고서 발송을 논의했다”와 “사용자가 지금 이 보고서를 보내도록 승인했다”는 서로 다른 상태다.

따라서 승인 여부, 허용 범위, 만료 시점, 철회, 인계 같은 행동 경계는 선호처럼 보이는 문장에서 추론하지 않고 명시적으로 기록해야 했다. **메모리 지침**(memory guidance)은 에이전트가 무엇을 기억으로 남기고, 나중에 그 기록을 어떻게 해석해야 하는지 정하는 작성·사용 규칙이다. 행동에 민감한 메모리 지침을 갱신한 [PR #82788](https://github.com/openclaw/openclaw/pull/82788)은 [`bd04b1ea7cc0`](https://github.com/openclaw/openclaw/commit/bd04b1ea7cc0ff51a423360d0eb1a543a9c07a25)으로 병합되었다.

이 변경은 런타임 코드나 모든 메모에 적용할 새 스키마를 도입하지 않았다. 평문 Markdown이라는 낮은 작성 비용은 유지하되, 행동에 영향을 주는 기록에는 권한과 시간적 유효성을 함께 적어야 한다는 의미상의 경계를 분명히 했다. 미래에 구조화된 기억을 더한다면 이 두 차원을 부가 설명이 아니라 독립된 판단 기준으로 다뤄야 한다는 과제도 남겼다.

> **변화의 동기.** 유지보수자 제품 요청에서 나온 **명시적 증거**다. PR #82788은 평문 Markdown의 낮은 부담을 유지하면서도 승인, 임시 제약, 인계, 만료, 출처 권한이 필요한 메모리에는 행동 경계를 적어야 한다고 직접 설명했다. 모든 메모에 스키마를 강제하지 않고 행동에 민감한 기록만 명시적으로 보강한 것은, 단순한 사실 보존과 현재의 실행 허가를 구분하면서 기존 작성 방식을 지키기 위해서다.

> **예시 — 합성 사례:** “다음 회의 뒤 보고서를 팀에 보내는 방안을 검토하자”는 메모는 주제 관련성은 높아도 발송 승인이 아니다. 실제 승인 상태, 대상, 만료 시점이 별도 필드나 명시적 문장으로 없다면 이를 현재 권한으로 해석해서는 안 된다. 이는 원리를 설명하는 가상 예시다.

## 기억은 지시가 아니다: 오염과 간접 프롬프트 주입

“관련성은 행동 권한이 아니다”에는 대칭인 원칙이 하나 더 필요하다. **기억은 지시가 아니다.** 과거에 저장된 문장이 현재 질의와 관련 있더라도, 그 문장을 지금 따라야 할 시스템·개발자·사용자 지시로 승격해서는 안 된다.

이 구분이 없으면 메모리는 간접 프롬프트 주입을 여러 대화에 걸쳐 증폭할 수 있다. 그룹 참여자의 발화, 웹 도구가 읽어 온 내용, 다른 하네스에서 가져온 Markdown처럼 신뢰하지 않은 자료 안에 “이전 지시를 무시하라”는 문장이 있다고 하자. 그 문장이 현재 호출에서 데이터로만 보이는 동안에는 외부 내용 경계가 작동할 수 있다. 그러나 에이전트나 훅이 그 내용을 일반 `memory/` 노트로 복사하고, 나중의 비공개 대화에서 시작 컨텍스트나 검색 결과로 다시 주입하면 원래 출처와 신뢰 등급이 흐려진다. 짧은 입력 공격이 영속 오염으로 바뀌는 지점이다.

```mermaid
flowchart LR
    U[신뢰하지 않은 입력<br/>그룹·웹·외부 하네스] --> C[포획 또는 가져오기]
    C --> M[일반 Markdown·Dreaming 증거]
    M --> R[다음 대화의 부트스트랩·검색·승격]
    R --> A{데이터인가<br/>현재 지시인가}
    A -->|구분 실패| X[지속적 행동 조종]
    A -->|출처·권한 재검사| Q[인용·격리·승인 요청]
```

이 흐름이 모든 외부 내용을 자동으로 저장한다는 뜻은 아니다. 위험은 **신뢰하지 않은 입력이 포획·가져오기·승격을 통과했을 때** 생긴다. 현재 구조에는 이 위험의 재료가 서로 다른 곳에 이미 보인다.

- `session-memory` 훅은 `/new`와 `/reset`에서 대화 꼬리를 일반 Markdown으로 구체화할 수 있지만, 고정본에는 대화 유형 관문이 없다.
- Dreaming의 Light·REM은 준비된 대화 기록 코퍼스를 증거 파일로 만들고, 그 증거가 승격 후보에 영향을 줄 수 있다.
- 하네스 가져오기는 외부 Markdown을 사용자가 검토·복구할 수 있는 파일로 옮기지만, “외부에서 왔다”는 사실만으로 내용이 안전해지지는 않는다.
- 웹 도구의 외부 내용 표지는 현재 도구 결과의 신뢰 경계를 표현한다. 모델이 내용을 새 Markdown으로 다시 쓰더라도 그 표지가 영속 출처 정보로 자동 보존되지는 않는다.

따라서 방어는 검색 결과 끝에 경고 한 줄을 붙이는 것으로 끝나지 않는다. 포획할 때 원래 출처, 소유 에이전트, 대화 유형, 신뢰 등급과 정책 버전을 함께 보존해야 한다. 지시문처럼 보이는 외부 문장은 사실 주장과 분리해 인용하거나 격리하고, 장기 기억으로 승격하거나 행동에 사용하기 전에는 현재 사용자의 승인과 권한을 다시 확인해야 한다. 삭제·교정 요청은 파생 인덱스뿐 아니라 구체화된 복사본에도 적용할 수 있어야 한다.

이 책의 표현으로 정리하면 다음과 같다.

> 회상된 기억을 과거의 **자료**로 읽어라. 현재 행동을 지시하는 **권한**은 현재 대화와 명시적인 정책에서 다시 얻어라. 출처와 신뢰 경계를 잃은 기억은 자동 승격하거나 실행하지 말고 검토 대상으로 격리하라.

이 절은 2026년 5월과 6월에 완성된 하나의 기능을 주장하지 않는다. 당시의 행동 권한 분리 원칙을, [1장의 삭제 계약](01-current-architecture.md#삭제는-검색의-반대말이-아니다)과 [10장의 대화 기록 구체화 간극](10-current-contract-gaps.md#현재-흐름과-제안하는-안전-흐름)에 연결해 현재 구조의 신뢰 경계로 확장한 분석이다.

## 회상 실패를 답변 전체에서 격리하다

Active Memory처럼 답변 전에 실행되는 회상은 검색이 멈추면 주 답변의 시작도 늦춘다. 이 경로에는 두 종류의 제한이 필요했다. **시간 제한**(timeout)은 한 번의 회상에 허용할 최대 대기 시간을 정하고, 그 시간이 지나면 더 기다리지 않는 장치다. **회로 차단기**(circuit breaker)는 같은 에이전트와 모델에서 시간 초과가 연속해서 발생하면 일정한 냉각 시간 동안 새 회상을 건너뛰는 장치다. 이미 반복해서 실패하는 외부 작업을 매 요청마다 다시 시작해 지연을 키우지 않기 위한 것이다.

회로 차단기의 기반은 4월 말 [`89cd2b63624b`](https://github.com/openclaw/openclaw/commit/89cd2b63624b67d845ec215c4f81eb50008af5ef)에 들어왔다. 5월 초에는 결과가 없거나 검색 도구를 사용할 수 없다는 사실이 이미 확정된 실행을 즉시 끝내고, 시간 초과 안내 문구를 유용한 회상 결과처럼 전달하지 않도록 [`ae82a39150f9`](https://github.com/openclaw/openclaw/commit/ae82a39150f9e02668ea34ca5955ccfc9bd67b70)이 보강했다. [`f2efe33afc5d`](https://github.com/openclaw/openclaw/commit/f2efe33afc5d27f583e5520c4db9e311c33f087c)은 최신 사용자 메시지에서 길이를 제한한 별도 검색어를 만들고, 채널 메타데이터나 전체 대화 컨텍스트를 그대로 검색 도구의 질의로 쓰지 않게 했다.

시간 제한 뒤에 작업이 계속 남는 문제도 따로 수리했다. [`1c1c75df7278`](https://github.com/openclaw/openclaw/commit/1c1c75df72783007eeff6f3f647f7b95c24c6dbd)은 Active Memory가 시간 초과되면 해당 에이전트의 로컬 임베딩 공급자와 검색 관리자를 정리할 수 있는 수명주기를 추가했다. [`9e2bd8b2f7eb`](https://github.com/openclaw/openclaw/commit/9e2bd8b2f7ebbd059e1a448af518463b8d3a826b)은 임베딩 회상이 멈춰도 메모리 검색 호출이 실패 상태를 반환하도록 해, 회상 실패가 전체 실행을 끝없이 붙들지 않게 했다.

6월에는 도구가 먼저 시간 초과 결과를 반환했는데도 내부 작업은 계속되는 문제까지 닫았다. [`8d72cb9401e5`](https://github.com/openclaw/openclaw/commit/8d72cb9401e5f94105854f8dafb3160aca130425)은 `memory_search`의 15초 제한이 끝나면 임베딩 재시도도 함께 취소하게 했다. 같은 취소 신호를 QMD 하위 프로세스까지 전달한 변경은 [`78184ea7e42f`](https://github.com/openclaw/openclaw/commit/78184ea7e42f2f0509d57de5ecc5ccbd4982873c)와 [`73dd758310e8`](https://github.com/openclaw/openclaw/commit/73dd758310e8b36b39912fe5392a6a2f6634c982)이다. 호출자에게는 이미 끝난 검색의 임베딩 재시도나 별도 QMD 프로세스가 뒤에서 자원을 계속 쓰지 않게 한 것이다.

이 흐름에서 **실패 가시성**은 단순히 오류 메시지를 많이 남긴다는 뜻이 아니다. 결과가 정말 없는지, 도구를 사용할 수 없는지, 시간 제한에 걸렸는지, 공급자와 인덱스의 계약이 어긋났는지를 구분해 다음 판단에 쓸 수 있게 한다는 뜻이다. 반대로 실패한 회상이 주 답변을 무기한 막지 않게 하는 것은 **실패 시 계속 진행**(fail-open) 경계다. 이는 기억을 반드시 찾았다고 가장하는 대체 결과가 아니라, 기억 없이 원래 답변을 계속할 수 있게 하는 가용성 선택이다.

> **변화의 동기.** 시간 제한 뒤에도 회상·임베딩·QMD 작업이 계속되거나, 결과가 없다는 사실을 늦게 확정하던 구체적 실행 경로에서 나온 **명시적 증거**다. 각 커밋은 서로 다른 누수를 고친다. 회로 차단기는 연속 실패의 재시도를 잠시 멈추고, 빠른 종료는 이미 확정된 실패를 즉시 반환하며, 취소 신호 전파는 호출자가 떠난 뒤의 내부 작업을 끝낸다. 이들을 하나의 원인이나 하나의 수정으로 합쳐 읽어서는 안 된다.

## 조용한 성능 저하를 진단 가능한 신뢰성 문제로 바꾸다

회상이 제시간에 끝나더라도 “검색 결과가 없다”는 증상만으로는 원인을 알 수 없었다. 끝난 작업자 정리, 한 요청에 묶어 보낼 임베딩 개수의 상한, 대체 벡터 점수화, FTS 오류 처리, 공급자 초기화, 인덱스 정체성 검증에 관한 변경들은 다음 두 원칙으로 모였다.

- 일시적으로 임베딩 공급자를 사용할 수 없다고 해서, 이전까지 벡터를 지원하던 인덱스가 조용히 손상되거나 다른 검색 방식으로 바뀌어서는 안 된다.
- 저장된 인덱스는 재사용 전에 공급자, 모델, 벡터 차원, 토크나이저, 검색 대상 문서 집합이 현재 설정과 일치하는지 확인해야 한다.

여기서 **대체 벡터 점수화**(fallback scoring)는 데이터베이스의 벡터 검색 기능을 쓸 수 없을 때 JavaScript가 저장된 벡터를 차례로 비교해 코사인 유사도를 계산하는 경로다. **토크나이저**는 문장을 검색 가능한 단어 단위로 나누는 규칙이고, **코퍼스**는 인덱싱하고 검색할 문서들의 집합이다. 이 값들은 같은 문서라도 서로 다른 벡터와 검색 결과를 만들 수 있으므로 인덱스의 정체성에 속한다.

여기에는 직접 원인과 수리 책임이 다른 실패가 섞여 있었다. 다음 표는 무엇을 보존해야 하고 어느 경계에서 고쳐야 하는지를 먼저 나눈다.

**이벤트 루프**는 Node가 여러 연결과 작업을 번갈아 처리하는 실행 순환이다. 긴 동기 계산이 이를 계속 점유하면 검색과 무관한 채널 연결도 멈출 수 있다.

| 사용자에게 보인 증상                                 | 직접 원인                                                                       | 보존할 상태                                   | 수리 경계와 결과                                                                                                      |
| ---------------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 벡터 검색이 갑자기 비거나 시작하지 않는다.           | 임베딩 공급자를 사용할 수 없거나 초기화가 실패했다.                             | 마지막으로 정상 동작한 인덱스와 Markdown 원문 | 공급자 연결과 설정을 진단한다. 의도적으로 설정한 경우에만 FTS 전용 경로를 쓰며, 실패를 벡터 검색처럼 가장하지 않는다. |
| 설정을 바꾼 뒤 호환되지 않는 결과가 나올 수 있다.    | 저장된 공급자·모델·차원·토크나이저·코퍼스 정체성과 현재 설정이 다르다.          | 기존 인덱스와 정체성 메타데이터               | 첫 검색에서 비싼 재임베딩을 몰래 시작하지 않는다. 불일치를 설명하고 명시적 재인덱싱·수리 전까지 검색을 멈춘다.        |
| 재인덱싱 도중 정상 검색까지 사라진다.                | 완성되지 않은 새 데이터베이스나 예상과 다른 리비전이 운영 인덱스를 덮으려 한다. | 현재 서비스 중인 SQLite 인덱스                | 별도 데이터베이스를 완성해 예상 리비전을 확인한 뒤 한 번에 게시한다. 실패하면 기존 검색을 계속 제공한다.              |
| 검색 한 번이 채널 연결까지 멈춘다.                   | JavaScript 코사인 전수 스캔이 이벤트 루프를 오래 점유한다.                      | 기존 점수식과 인덱스                          | 제한된 묶음마다 실행 제어권을 돌려주어, 같은 점수 의미를 유지하면서 다른 연결도 처리하게 한다.                        |

| 대화형 FTS 질의가 결과를 하나도 내지 않는다.         | 모든 단어를 만족해야 하는 AND 질의가 지나치게 엄격하다.                         | FTS 인덱스                                    | 키워드마다 제한된 후보를 모으되 전체 후보 수에 상한을 두어, 결과 없음은 줄이고 과도한 확장은 막는다.                  |
| 공급자 설정과 메모리 전용 등록이 서로 다르게 보인다. | 임베딩 공급자 소유권이 메모리 전용 경로와 공용 연결부에 나뉘어 있다.            | 현재 인덱스와 공급자 정체성                   | 공급자 등록을 공용 연결부에 모은다. 정체성이 다른 기존 벡터는 명시적으로 수리하기 전까지 재사용하지 않는다.           |

이 표의 행들은 하나의 장애가 아니다. 아래 이력은 각 증상과 변경의 근거를 따로 연결한다.

인덱스 정체성을 명시적으로 검증한 [`a4b4fed41287`](https://github.com/openclaw/openclaw/commit/a4b4fed41287e267735a93d82cc4ff7e8e180c5b)은 저장된 공급자·모델·설정이 현재 구성과 다르면 낡은 벡터를 그대로 쓰지 않게 했다. 별도로 현재 계약에서 공급자 `none`은 오프라인 인덱스가 오해를 부르는 벡터 상태를 품지 않고 FTS 전용으로 남는다는 뜻이다. [메모리 설정 기준](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/docs/reference/memory-config.md#L101-L134)이 이 구분을 명시한다. 두 규칙은 관측 가능성을 막연한 “검색 결과가 없다”에서 진단 가능한 공급자·인덱스 계약으로 옮겼다.

> **변화의 동기.** 공급자 변경으로 생긴 회귀 위험과 유지보수자 요청에서 나온 **명시적 증거**다. PR #87907은 저장된 공급자·모델·설정과 현재 설정이 다를 때 낡은 벡터 인덱스를 신뢰하는 문제를 직접 밝혔다. 시작이나 첫 검색에서 비싼 전체 재인덱싱을 조용히 실행하지 않고 검색을 멈춘 채 진단과 명시적 수리를 요구한 것은, 호환되지 않는 결과와 예기치 않은 비용을 모두 피하기 위해서다.

재구축 실패가 정상적으로 검색 가능한 기존 상태를 일부 결과로 덮는 문제도 막아야 했다. 여기서 **리비전**은 재인덱싱을 시작할 때 기준으로 삼은 원본 상태의 버전 표지다. 재인덱싱이 실패하면 운영 중인 SQLite 인덱스를 보존하고, 별도로 만든 결과는 예상 리비전과 일치할 때만 게시하도록 바꾼 근거가 [`865fdab07501`](https://github.com/openclaw/openclaw/commit/865fdab07501b5d85b4057d06b22e0ce907300e7)이다.

> **변화의 동기.** 실제 재인덱싱 실패인 Issue #91216에서 나온 **명시적 증거**다. **WAL·SHM**은 SQLite가 트랜잭션 복구와 동시 접근에 사용하는 보조 파일이다. 커밋 본문은 교체 도중 대상 데이터베이스가 비거나 이 보조 파일과 본체가 어긋날 수 있는 실패를 설명한다. 그래서 살아 있는 인덱스를 그대로 둔 채 별도의 그림자 데이터베이스를 완성하고 예상 리비전까지 확인한 뒤 한 번에 게시해, 복구 작업 실패가 정상 검색 상태를 파괴하지 않게 했다.

성능 실패는 벤치마크에만 머물지 않고 사용자에게 보였다. [Issue #81172](https://github.com/openclaw/openclaw/issues/81172)는 대체 코사인 스캔(fallback scan)이 Node를 1분 넘게 막아 Discord 연결을 끊었다고 보고했다. [PR #83758](https://github.com/openclaw/openclaw/pull/83758)은 점수를 바꾸지 않은 채 제한된 배치로 처리하고, Node가 다른 연결 작업도 번갈아 처리하도록 이벤트 루프에 제어권을 돌려주었다. [PR #91841](https://github.com/openclaw/openclaw/pull/91841)은 동기화마다 전체 디렉터리를 다시 훑는 대신 변경 표시된 대화 기록 세션만 대상으로 삼았다. [PR #73976](https://github.com/openclaw/openclaw/pull/73976)은 AND로 결합한 대화형 질의가 종종 FTS 검색 결과를 하나도 내지 못했기 때문에, 키워드별로 후보를 넓히되 전체 후보 수에는 상한을 두었다.

> **변화의 동기.** 장애 보고와 운영 측정에서 나온 **명시적 증거**다. Issue #81172와 PR #83758은 동기식 전체 코사인 스캔이 수십 초 동안 이벤트 루프와 채널 연결을 막는다고 연결했고, PR #91841과 #73976은 반복 전체 탐색과 지나치게 엄격한 어휘 질의라는 별도 병목을 좁혔다. 점수식을 바꾸기보다 제한된 배치에서 제어권을 양보하고, 이미 변경 표시된 세션과 제한된 키워드 후보만 처리한 것은 기존 검색 의미를 지키면서 요청당 작업량을 상한 안에 두기 위해서다.

소유권 측면에서는 [PR #85072](https://github.com/openclaw/openclaw/pull/85072)가 기억 전용 임베딩 등록에서 공용 공급자 연결부로의 이동을 마무리했다. 하지만 공급자나 모델 변경을 확인하지 않으면 호환되지 않는 벡터가 섞이거나 예상치 못한 유료 재임베딩이 실행될 수 있다. [PR #87907](https://github.com/openclaw/openclaw/pull/87907)이 이 위험을 직접 설명한다. 더 안전한 상태는 명시적 복구 경로가 선택될 때까지 멈추고 진단하는 것이다.

파일이 올바르더라도 임베딩 설정과 온보딩 오류 때문에 기억이 고장 난 것처럼 보일 수 있다. [Issue #16670](https://github.com/openclaw/openclaw/issues/16670)은 여전히 유용한 사용자 수준 신호다. 다만 일부 세부 사항은 성숙한 FTS 전용 경로보다 오래되었으므로, 현재 모든 버전의 포괄적 결함으로 취급하지 말고 대상 버전에서 재현해야 한다.

> **변화의 동기.** 설계·소유권 정리와 공급자 전환 위험에 대한 **명시적 증거**다. PR #85072는 메모리 전용 등록을 일반 임베딩 공급자 연결부의 하위 호환 경로로 축소했고, PR #87907은 공급자·모델 변경 뒤 기존 벡터를 조용히 재사용하거나 유료 재임베딩하지 않아야 할 이유를 직접 적었다. 따라서 등록 소유자는 공용 연결부로 모으되, 정체성이 어긋난 인덱스는 명시적 수리 전까지 멈추고 진단하게 했다. Issue #16670은 설정 실패가 체감 품질을 낮춘다는 **맥락적 증거**이며, 이 두 PR의 직접 원인으로 연결되지는 않는다.

## Dreaming 기계 상태를 보조 JSON에서 SQLite로 옮기다

여기서 **기계 상태**는 사람이 기억의 내용으로 읽고 편집하는 정보가 아니라, 프로그램이 작업을 이어 가고 중복 실행을 막기 위해 관리하는 운영 정보다. 어디까지 수집했는지를 나타내는 체크포인트, 다음에 읽을 위치인 커서, 현재 실행 단계를 알리는 신호, 동시 실행을 막는 잠금, 횟수를 세는 카운터가 여기에 속한다. 이 정보가 틀리면 실행은 오작동할 수 있지만, 그 자체가 사용자의 사실이나 선호는 아니다.

Dreaming이 커지면서 회상 상태, 단계 신호, 수집 체크포인트, 잠금을 `.dreams/` JSON 상태와 잠금 파일에 나눠 두는 방식은 서로 어긋날 가능성과 소유권의 모호함을 키웠다. 해결책은 이 기계 상태를 SQLite의 플러그인 전용 영역으로 옮겨 한 데이터베이스가 일관되게 쓰고 읽도록 하는 것이었다. [PR #91056](https://github.com/openclaw/openclaw/pull/91056)은 [`3f5e00184431`](https://github.com/openclaw/openclaw/commit/3f5e00184431f10a7ae55c59ce8d3c6cb0d0a0eb)을 통해 병합되어 `v2026.6.7-alpha.1`에 처음 포함되었다.

진단·수리 명령인 `doctor`는 다음 실행에도 필요한 영속 JSON 상태를 SQLite로 이관하고 원본을 보관한다. 반면 이전 실행에만 의미가 있던 잠금 파일은 가져오지 않고 의도적으로 제자리에 남긴다. 당시의 [`doctor` 계약](https://github.com/openclaw/openclaw/blob/a115af277410a91fb039d2ed699eafad706f5c73/extensions/memory-core/doctor-contract-api.ts#L1085-L1105)이 이 경계를 명시한다.

그 결과 아키텍처 경계는 다음과 같이 일관되게 정리되었다.

- 사용자에게 보이는 사실·선호·요약 같은 의미 산출물은 Markdown이나 텍스트로 남는다.
- 실행을 조정하는 커서·체크포인트·잠금·카운터 같은 기계 상태는 SQLite에 둔다.
- 오래된 파일 상태는 `doctor`가 한 번 읽어 옮기는 마이그레이션 입력일 뿐, 정상 런타임이 계속 함께 읽는 대체 저장소가 아니다.

현재 공식 문서는 이 변경을 따라잡지 못했다. 이 계약 차이는 이 책의 [현재 계약의 간극](10-current-contract-gaps.md)에서 별도로 다룬다.

> **변화의 동기.** 설계·소유권 정리에서 **코드로 추론한 증거**다. PR #91056은 지속 상태를 `.dreams/*.json`에서 SQLite 플러그인 상태로 옮기고, `doctor`가 영속 자료만 이관하며 일시적 잠금·캐시는 남긴다는 구현 범위는 명시하지만 별도의 선택 이유는 적지 않았다. 런타임에서 두 저장소를 함께 읽는 호환층 대신 일회성 `doctor` 마이그레이션을 택한 형태는 권위 저장소를 하나로 만들고 재구축 가능한 상태를 영구 호환 부채로 남기지 않으려는 소유권 정리로 읽힌다.

## 메모리 인덱스를 에이전트별 데이터베이스에 합치다

이전의 메모리 인덱스는 설정 가능한 `store.path`에 별도 SQLite 파일로 놓일 수 있었다. 그러면 어느 에이전트의 인덱스인지, 무엇과 함께 정리·백업해야 하는지, 누가 접근할 수 있는지를 보조 파일과 경로 규칙으로 다시 맞춰야 했다. **에이전트별 데이터베이스**는 한 에이전트가 소유하는 세션·인덱스·운영 상태를 그 에이전트의 정식 SQLite 저장소에 모은 것이다. 모든 에이전트가 한 데이터베이스를 공유한다는 뜻이 아니다.

기억 인덱스를 이 에이전트별 데이터베이스로 옮기고 독립 `store.path` 설정을 제거한 선택은 인덱스의 소유권을 에이전트 정체성과 결박했다. [PR #94646](https://github.com/openclaw/openclaw/pull/94646)의 병합 묶음은 [`f324f7e2813a`](https://github.com/openclaw/openclaw/commit/f324f7e2813a52e07c515143e041be6ce7bca1d3)에서 시작해 [`65eb2ccd4ae2`](https://github.com/openclaw/openclaw/commit/65eb2ccd4ae254154a026d9883eb18b2eef27079)에 착지했고, `v2026.6.9-beta.1`에 처음 포함되었다.

이는 단순히 파일 수를 줄인 변경이 아니었다. 권한 부여, 정리, 백업, 정체성을 같은 에이전트 경계에 맞추고, 독립 보조 파일 사이의 어긋남을 줄였다. 메모리 인덱스도 OpenClaw가 소유하는 운영 상태를 데이터베이스에 모으는 저장소 전반의 원칙에 맞췄다. 다만 첫 구현은 이전 독립 인덱스를 새 데이터베이스로 가져오지 않아 기존 파생 인덱스를 뒤에 남겼다.

> **변화의 동기.** PR #94646은 데이터베이스 우선 통합이라는 범위는 명시하지만, 에이전트 식별 정보·백업·정리를 한 경계로 모은 이점은 코드와 저장소 정책에서 **추론한 설계 동기**다. 첫 구현이 기존 독립 인덱스를 승계하지 못한 비용과 7월의 후속 수리는 다음 장에서 이어서 다룬다.

## 대화 기록 접근에 정식 코퍼스 경계를 세우다

Dreaming, [QMD 세션 내보내기](01-current-architecture.md#qmd-explained), 세션 기억 동기화는 모두 대화 기록을 읽지만 필요한 결과는 서로 달랐다. 각 소비자가 파일 배치를 직접 추측해 대화 기록을 다시 찾으면 같은 파일을 여러 번 훑을 뿐 아니라, 세션과 에이전트의 정체성을 전달하는 방식도 달라질 수 있었다.

이를 해결한 **코퍼스 접근자**는 검색 대상인 대화 기록 집합을 정식 방식으로 열거하고, 각 항목의 본문 위치와 정체성 정보를 함께 돌려주는 공용 인터페이스다. 소비자는 “대화 기록 파일이 어느 디렉터리에 있을 것”이라고 추측하지 않고 접근자에게 항목을 요청한다. 접근자가 반환하는 각 항목에는 다음 사실이 함께 실린다.

- 대화 기록의 경로
- 같은 대화를 식별하는 세션 ID와 세션 키
- 기록을 소유한 에이전트
- 일반 사용자 대화인지, 다른 처리에서 만들어진 산출물·생성 세션인지 구분하는 표지

[PR #96162](https://github.com/openclaw/openclaw/pull/96162)는 이 접근자 기반 코퍼스를 도입했고, [`c24d266b2d09`](https://github.com/openclaw/openclaw/commit/c24d266b2d0943a2376ae9ac87a2fd8e200920e1)로 병합되어 `v2026.6.11-beta.1`에 처음 포함되었다.

정식 접근자는 소유권과 정체성을 파일 발견 단계에서 Dreaming·QMD·동기화 단계까지 그대로 전달한다. 반복적인 파일 시스템 탐색보다 작업량이 적고, 소비자마다 서로 다른 대화를 같은 것으로 보거나 같은 대화를 서로 다른 것으로 보는 위험도 줄인다. 이는 7월의 SQLite 세션 마이그레이션 전에 필요한 토대이자, 모든 대화 기록 소비자가 같은 코퍼스 경계를 쓰게 한 변화였다.

> **변화의 동기.** 설계·소유권 정리에 대한 유지보수자 요청에서 나온 **명시적 증거**다. PR #96162는 Dreaming, QMD 내보내기, 세션 기억 동기화가 각각 파일 배치를 다시 탐색하면서 세션 식별 정보와 소유권을 잃는 문제를 직접 적었다. 접근자가 경로·세션 ID와 키·에이전트 소유자·산출물 종류를 한 항목으로 전달하게 한 것은, 소비자마다 같은 사실을 재발견하지 않고 다음 저장 단계까지 권한 맥락을 보존하기 위해서다.

## 다음 장으로

5월과 6월은 세 가지 경계를 세웠다. 기억한 지식과 현재의 행동 권한을 분리했고, 회상 실패의 시간·자원 범위를 제한하면서 원인은 구분해 드러냈다. 사용자에게 보이는 의미 메모리와 프로그램이 관리하는 기계 상태도 서로 다른 정본에 놓고, 인덱스와 대화 기록에는 에이전트 소유권과 정식 접근 경로를 부여했다.

그러나 세션과 대화 기록 자체가 아직 정식 SQLite 상태가 아니면 목록, 이력, 정확 검색, 의미 코퍼스가 같은 가시성을 공유하기 어려웠다. 접근자가 정체성을 운반할 수는 있어도 그 정체성의 권위 있는 저장소까지 대신할 수는 없었다.

7월에는 이 마지막 저장소 경계를 닫고, 정확한 대화 기록 검색과 하네스 가져오기를 추가한 뒤, 같은 개인 에이전트가 비공개 표면을 넘나들며 기억하는 기능을 엄격한 자격 필터 위에 올린다.
