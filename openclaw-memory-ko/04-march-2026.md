# 4장. 2026년 3월: 로컬 실행, 언어, 소유권 재편

검색이 제품 기능이 된 뒤의 문제는 “검색이 있느냐”보다 “누구의 환경과 언어에서 정확히 작동하느냐”였다. 초기 OpenAI 기본 경로는 오프라인 목표와 긴장했고, 영어 중심 FTS는 CJK 텍스트에서 거의 쓸 수 없었으며, 대안 메모리 플러그인을 선택해도 코어 프롬프트가 내장 도구를 가르쳤다.

3월의 작업은 코퍼스 선택, 내용 정체성, 언어 구간, 소유자 경계를 명시했다. 로컬·멀티모달 임베딩으로 선택지를 넓히되 무단 미디어 수집을 막았고, 프롬프트와 엔진 소유권을 플러그인 쪽으로 옮겼다. 그 결과 구현은 유연해졌지만 여러 엔진이 공유해야 할 가시성, 인용, 삭제, 평가 계약이 더 중요해졌다.

## 로컬·멀티모달 임베딩이 코퍼스를 넓히다

원격 공급자에 기대지 않고 벡터 검색을 운영하려는 요구에 Ollama 임베딩이 답했다. 완전히 로컬인 벡터 경로를 더 쉽게 만들고 원래의 오프라인 목표와 초기 OpenAI 기본 구현 사이의 긴장을 줄인 변경은 [PR #26349](https://github.com/openclaw/openclaw/pull/26349)와 병합 커밋 [`3eec79bd6cb7`](https://github.com/openclaw/openclaw/commit/3eec79bd6cb71f2e11dea10a10bd93922d9a7345)에 남아 있다.

> **변화의 동기.** Ollama를 공급자와 대체 경로로 추가한다는 기능 목표는 PR #26349에 **명시되어 있다**. 이를 원격 API 없는 벡터 경로와 초기 오프라인 목표의 긴장을 줄인 선택으로 읽는 것은 **코드에서 추론**한 설계 해석이다. 기존 공급자 인터페이스를 재사용해 새 메모리 엔진 없이 로컬 선택지를 넓혔다.

텍스트 밖의 명시적 자료도 검색하려는 요구에는 범위를 좁힌 멀티모달 경로를 택했다. 설정된 추가 경로에서만 Gemini 멀티모달 임베딩 모델로 이미지와 오디오를 색인하는 선택 기능이었다. [PR #43460](https://github.com/openclaw/openclaw/pull/43460)은 [`d79ca5296054`](https://github.com/openclaw/openclaw/commit/d79ca5296054058930bd97dd43540fd52ede15a3)로 병합되었고 `v2026.3.11-beta.1`에 처음 포함되었다.

범위는 의도적으로 좁았다.

- 워크스페이스 메모리가 조용히 미디어 수집기로 변하지 않았다.
- 설정된 추가 경로만 자격이 있었다.
- 지원되지 않는 공급자·대체 경로 조합은 닫힌 채 실패했다.
- 텍스트 Markdown이 기본 계약으로 남았다.

> **변화의 동기.** 이미지·오디오 색인이라는 기능 목표와 명시적 선택(opt-in) 범위는 PR #43460에 **명시적**이다. 반면 워크스페이스 전체 수집의 비용·프라이버시 위험 때문에 이 형태를 택했다는 해석은 **코드에서 추론**한 설계 압력이며, 실제 무단 수집 사건이 관측되었다는 뜻은 아니다. 설정된 추가 경로와 특정 Gemini 모델만 허용하고 지원되지 않는 조합은 실패 시 닫았다.

명시적으로 코퍼스를 선택하게 함으로써 검토 가능성과 비용 경계를 보존한 기능 확장의 좋은 예다.

> **예시 — 합성 사례:** 사용자가 사진 폴더를 추가 경로로 명시하지 않았다면, 멀티모달 기능이 켜져 있다는 이유만으로 워크스페이스 전체의 이미지를 자동 수집하는 구조가 아니었다. 이 예시는 명시적 코퍼스 선택 계약을 풀어쓴 것이며 실제 사용자 설정을 인용한 것이 아니다.

## 생명주기 정확성은 이벤트가 아니라 내용을 따르다

이벤트가 발생했다는 사실만으로 어떤 내용 개정본이 최신인지 알 수 없었다. 압축된 대화 기록 갱신 이벤트를 내보내고, 세션 소스의 압축 후 강제 갱신이 켜졌을 때 그 대화 기록만 프롬프트 색인 대상으로 삼되 더 넓은 메모리 파일 작업은 정기 동기화에 맡긴 [PR #25561](https://github.com/openclaw/openclaw/pull/25561)이 첫 선택이었다.

플러시 중복 제거도 압축 이벤트 카운터가 아니라 대화 기록 내용 해시에 묶었다. [PR #34222](https://github.com/openclaw/openclaw/pull/34222)가 이 변경을 담았다.

두 문제는 모두 “이벤트가 몇 번 왔는가”와 “내용이 실제로 달라졌는가”를 혼동한 데서 생겼다. 바뀌기 전과 뒤의 순서를 나란히 놓으면 차이가 분명하다.

| 상황                        | 이전 순서와 실패                                                                      | 바뀐 순서                                                                                  | 개정본을 식별한 값·줄어든 중복                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 압축 뒤 대화 기록 색인 갱신 | `압축으로 대화 기록 내용 변경 → 갱신 이벤트 없음 → 세션 색인은 이전 개정본을 계속 봄` | `내용 변경 → 대화 기록 갱신 이벤트 → 바뀐 그 대화 기록만 즉시 프롬프트 색인 대상으로 지정` | 갱신된 대화 기록 개정본을 대상으로 삼고, 더 넓은 메모리 파일 동기화와 분리했다.                |
| 압축 플러시 재시도          | `같은 내용 → 중단·재시도로 이벤트 카운터 증가 → 같은 플러시가 4–7회 기록될 수 있음`   | `같은 내용 → 같은 내용 해시 → 이미 처리한 플러시를 건너뜀`                                 | 이벤트 번호 대신 대화 기록 내용 해시를 중복 제거 키로 사용해 동일 내용의 반복 플러시를 막았다. |

두 변경이 전하는 교훈은 같다. 수명주기 카운터는 힌트일 뿐이다. 중복 제거와 대상별 최신성은 기준이 되는 내용 개정본에 결합되어야 한다.

> **변화의 동기.** PR #25561은 압축 실행 경로가 대화 기록 갱신을 알리지 않아 세션 색인이 오래될 수 있는 코드상 신선도 결함을 직접 설명했다. 연결된 [Issue #19207](https://github.com/openclaw/openclaw/issues/19207)은 압축 뒤 정확한 식별자를 잃은 사용자 보고지만, 오래된 색인 자체를 관측한 보고로 확대해서는 안 된다. 반면 [Issue #30115](https://github.com/openclaw/openclaw/issues/30115)과 PR #34222는 압축 중단·재시도 때 같은 내용이 4–7회 기록된 실제 장애를 직접 연결한다. 두 근거 모두 **명시적**이되, 전자는 입증된 코드 경로이고 후자는 관측 사건이다. 전자는 갱신된 대화 기록만 즉시 색인 대상으로 삼고, 후자는 이벤트 횟수 대신 내용 해시를 사용해 최신성과 중복 제거를 실제 내용에 결박했다.

## 대안 메모리 플러그인이 프롬프트 소유권 버그를 드러내다

초기 시스템 프롬프트는 항상 내장 Markdown 도구를 설명했다. 대안 메모리 플러그인이 슬롯을 소유하면 이 설명은 틀렸다.

해결책은 선택된 플러그인이 자체 메모리 프롬프트 구역을 제공하게 하는 것이었다. [PR #40126](https://github.com/openclaw/openclaw/pull/40126)은 [`fd2b3ed6af9c`](https://github.com/openclaw/openclaw/commit/fd2b3ed6af9c3ec6ee9e5e0f16410cf286159002)로 병합되었다.

> **변화의 동기.** 실제 압력은 대안 플러그인을 선택해도 시스템 프롬프트가 `memory-core` 전용 도구를 가르치는 소유권 오류였다. 동기 출처는 이 문제와 범위를 직접 적은 PR #40126이며, 증거 강도는 **명시적**이다. 선택된 플러그인이 프롬프트 구역을 등록하게 해 도구 소유자와 모델 지침의 소유자를 일치시켰다.

코어가 계속 모델에게 예전 플러그인의 도구와 작업 흐름을 가르친다면 플러그인 대체는 실제가 아니다. 얻은 것은 단순한 확장성이 아니라 모델 경계의 행동 계약을 수리한 일이었다. 다만 프롬프트 한 조각만 고쳐서는 엔진·플러시·도구·호스트의 소유권 전체가 정리되지 않았다.

## 하위 시스템이 에이전트 코어 밖으로 이동하다

프롬프트 소유권에서 드러난 문제를 하위 시스템 전체에서 해결하려면 메모리 정책과 구현을 범용 에이전트 코어 밖으로 옮겨야 했다. 이전에는 범용 코어가 메모리 프롬프트·플러시·도구·엔진을 직접 알고 있었다. 리팩터링 뒤에는 범용 코어가 선택된 플러그인을 공통 접점을 통해 부르고, 플러그인이 메모리 정책을 결정하며, 공용 호스트 기능은 SDK 뒤에 놓였다.

```text
이전: 범용 에이전트 코어 ──직접 소유──> 프롬프트 · 플러시 · 도구 · 엔진

이후: 범용 에이전트 코어 ──호출──> 범용 플러그인 어댑터 ──전달──> 선택된 메모리 플러그인
                                                        │
                                                        └──사용──> 호스트 SDK ──노출──> 메모리 호스트 기능
```

이 그림의 이름이 비슷한 네 역할을 입력과 출력으로 다시 풀면 다음과 같다.

| 역할                 | 받는 것                                               | 내보내는 것                                  | 소유하지 않는 것                          |
| -------------------- | ----------------------------------------------------- | -------------------------------------------- | ----------------------------------------- |
| 메모리 엔진          | 설정된 원문·검색 설정·질의                            | 색인 동기화, 검색 결과, 상태                 | 범용 에이전트 실행 전체                   |
| 범용 플러그인 어댑터 | 코어에서 온 생명주기·도구 호출                        | 현재 선택된 플러그인으로 전달한 공통 호출    | 특정 메모리 구현의 정책                   |
| 호스트 SDK           | 플러그인이 요청하는 공용 호스트 기능                  | 플러그인이 의존할 수 있는 안정된 형식과 함수 | 어느 플러그인을 선택할지에 관한 제품 결정 |
| 메모리 호스트        | SDK를 통해 들어온 파일·저장·공급자·프로세스 관련 요청 | 실제 호스트 환경에서 수행한 결과             | 선별·회상·승격 같은 플러그인 고유 정책    |

2026-03-26부터 2026-03-27까지 이어진 리팩터링은 이 소유권 이동을 다음 커밋으로 한 흐름에 묶었다.

- [`e0dfc776bba8`](https://github.com/openclaw/openclaw/commit/e0dfc776bba8ca9d235e5a8124344abac6aee931): 플러시 소유권이 메모리 플러그인으로 이동했다.
- [`e955d574b237`](https://github.com/openclaw/openclaw/commit/e955d574b237a68632ebaa899d37928270d0171d): 도구가 `memory-core`로 이동했다.
- [`cad83db8b2f7`](https://github.com/openclaw/openclaw/commit/cad83db8b2f7664230df50f63cfff3106a5a8154): 엔진이 플러그인으로 이동했다.
- [`dbf78de7c680`](https://github.com/openclaw/openclaw/commit/dbf78de7c680405245cadee06a8ddb9e787616aa): 엔진의 직접 소유를 범용 플러그인 어댑터가 대체했다.
- [`bd6c7969ea9c`](https://github.com/openclaw/openclaw/commit/bd6c7969ea9c40c56ccdbe50301aeb8621321ba4): 호스트 SDK가 추출되었다.
- [`eebce9e9c7cb`](https://github.com/openclaw/openclaw/commit/eebce9e9c7cb423794d3fde480a08eb8edbb8ae3): 메모리 호스트가 그 SDK로 이동했다.

이 리팩터링이 현재의 분리를 만들었다.

- 범용 코어는 에이전트 실행을 조율한다.
- 선택된 메모리 플러그인은 메모리 동작을 소유한다.
- SDK는 안정된 호스트 기능을 노출한다.
- 임베딩 공급자는 임베딩을 소유한다.

> **변화의 동기.** 실제 목표는 메모리 전용 정책이 범용 에이전트 코어에 흩어져 대안 구현과 충돌하는 구조를 정리하는 일이었다. 동기 출처는 2026-03-26부터 2026-03-27까지 이어진 여섯 리팩터링 커밋의 소유권 이동이며, 증거 강도는 **코드에서 추론**이다. 플러시·도구·엔진은 플러그인 경계로, 호스트 기능은 SDK로 옮겨 한 소유자와 안정된 접점을 만드는 형태를 골랐다.

얻은 것은 새로운 사용자 기능이라기보다 소유권이 명확한 아키텍처였다. 이후 Active Memory, Dreaming, [QMD](01-current-architecture.md#qmd-explained) 강화, 임베딩 공급자 추출, 외부 엔진을 가능하게 하면서도 메모리 전용 정책을 범용 코어로 되돌리지 않게 한 기반이었다. 그만큼 선택된 소유자와 추가 기능 사이의 공통 계약을 따로 증명해야 하는 과제도 커졌다.

## CJK 보고가 어휘 검색의 정확성을 강제하다

종합 테스트에서 FTS가 작동해도 실제 언어에서는 실패할 수 있었다. [Issue #20730](https://github.com/openclaw/openclaw/issues/20730)은 기본 FTS5 토크나이저 때문에 중국어, 일본어, 한국어 텍스트에서 BM25가 사실상 쓸 수 없었음을 보여 주었다.

해결책은 설정 가능한 `unicode61`/`trigram` 토큰화, 토크나이저 정체성 변경 시 강제 재색인, 한 글자와 두 글자 질의를 위한 부분 문자열 대체 검색이었다. [PR #56707](https://github.com/openclaw/openclaw/pull/56707)은 [`3ce48aff660a`](https://github.com/openclaw/openclaw/commit/3ce48aff660a0dca487fb195132d53e6e0e404ed)로 병합되었고 `v2026.3.31-beta.1`에 처음 포함되었다.

> **변화의 동기.** 실제 압력은 기본 FTS5 토크나이저가 중국어·일본어·한국어를 사실상 검색하지 못한다는 사용자 장애였다. 동기 출처는 재현 예시가 있는 Issue #20730과 이를 해결한 PR #56707이며, 증거 강도는 **명시적**이다. `unicode61`/`trigram` 선택, 정체성 변경 시 재색인, 짧은 질의의 부분 문자열 대체를 함께 골라 언어별 정확성과 색인 일관성을 동시에 지켰다.

두 가지 교훈이 따른다.

1. “FTS가 작동한다”는 말은 영어 중심의 종합 판단이었다. 언어별 구간은 거의 전면적인 실패를 드러냈다.
2. 토크나이저 설정은 색인 정체성의 일부다. 재색인 검증 없이 이를 바꾸면 조용한 미탐이 생긴다.

3월 말 공급자 `none` 커밋인 [`41c30f0c5901`](https://github.com/openclaw/openclaw/commit/41c30f0c59012635220bde685468af009da6a60a)과 [`598f539be5e1`](https://github.com/openclaw/openclaw/commit/598f539be5e1585e450a324c506ced28d458d0a7)은 명시적 FTS 전용 경로를 완성했다. 임베딩 공급자가 없다고 빈 메모리 색인을 뜻하지 않게 되었다.

> **변화의 동기.** 임베딩 공급자가 없을 때 FTS 표가 채워지지 않거나 재색인이 기존 청크를 비우는 실패가 실제 사용자 환경에서 보고되었다. 동기 출처는 [Issue #42714](https://github.com/openclaw/openclaw/issues/42714), [PR #56473](https://github.com/openclaw/openclaw/pull/56473)과 두 수정 커밋이며, 증거 강도는 **명시적**이다. 벡터 폴백을 가장하는 대신 FTS 전용 색인을 독립된 정상 방식으로 채우고, 공급자 전환 뒤에도 재색인 상태를 보존했다.

## 외부 엔진이 전략의 복수성을 선명하게 만들다

한 메모리 구현으로 모든 의미 모델을 설명할 수 없다는 사실도 분명해졌다. 자동 대화 보존, 사용자·에이전트 모델링, 의미 결론, 프롬프트 전 주입을 갖춘 외부 플러그인·서비스인 Honcho가 공개 메모리 서사에 들어왔다. [공식 Honcho 문서](https://docs.openclaw.ai/concepts/memory-honcho)는 2026-03-30의 [`70b7f32c7efa`](https://github.com/openclaw/openclaw/commit/70b7f32c7efa6dee9306100b9346269d9f61f83a)에 추가되었다.

Honcho는 `memory-core`의 구현 단계가 아니다. 그러나 진화의 일부로 중요하다. OpenClaw의 공개 메모리 서사가 하나의 파일·색인 설계에서 여러 의미론으로 넓어졌기 때문이다.

> **변화의 동기.** 실제 목표는 파일·색인 중심 구현과 다른 사용자 모델·자동 대화 보존 방식도 공식 선택지로 설명하는 일이었다. 동기 출처는 Honcho 문서를 추가한 커밋과 문서 내용이며, 증거 강도는 **맥락적이며 직접 인과는 입증되지 않음**이다. 외부 엔진을 `memory-core`의 다음 단계로 합치지 않고 별도 플러그인·서비스로 문서화해 전략의 복수성을 보존했다.

- 수동으로 관리하는 투명한 기록
- 대안 로컬 벡터 레코드
- 관리형·로컬 사이드카
- AI 기반 사용자 모델

이 복수성은 가시성, 인용, 삭제, 내보내기, 평가, 프롬프트 소유권에 관한 공통 계약의 가치를 높인다. “메모리 플러그인”을 단순히 “검색 도구를 등록한다”는 뜻으로만 사용해서는 안전하지 않다.

## 다음 장으로

3월은 메모리를 하나의 하드코딩된 엔진이 아니라 선택된 소유자와 여러 의미 전략의 생태계로 바꾸었다. 그러나 도구를 제공하는 것만으로 주 모델이 검색한다는 보장은 없었고, 검색 결과가 반복해서 쓰였다는 사실만으로 장기 승격의 근거가 충분하지도 않았다.

4월에는 이 두 압력이 답변 전 에이전트형 회상과 회상 주도 승격으로 이어진다. 동시에 더 넓은 코퍼스와 대화 기록 회상이 지연 시간, 노출 편향, 프라이버시 필터 순서를 측정 가능한 문제로 만든다.
